# Автоматическая выдача и линейки квестов — проект архитектуры

Статус: проект для правки и передачи агенту-исполнителю. Проверка текущей реализации: 2026-09-22; обновлён 2026-09-25: решения по разбору плана (раздел 17), уточнения раздела 2, этапы работ (раздел 14). Подтверждённые игровые требования перечислены отдельно; контракты и правила реализации ниже являются техническим предложением, а не описанием уже существующих API.

Цель: автоматически выдавать квесты по состоянию мира и продолжать связанные задания, сохранив существующие этапы, условия, действия, награды, диалоги и журнал. Документ дополняет нарративную архитектуру из [[HANDOFF]], правила взаимодействия из [[NpcInteractions]] и проект [[UsableItemsArchitecture]].

## 1. Подтверждённые требования и границы

| Требование | Следствие для системы |
| --- | --- |
| Части истории бывают самостоятельными квестами с собственными наградами либо этапами одного квеста. | Сохранить оба уровня; переход этапа не создавать как отдельный квест. |
| Способ завершения индивидуален: автоматически по целям либо после явной сдачи. | Режим завершения в определении квеста. |
| Источники: новая игра, посещение области, значение факта, получение/использование предмета, завершение боя, взаимодействие с объектом. | События оставляют устойчивые свидетельства; условия читают эти свидетельства. |
| Автоматический источник сразу добавляет квест в активные, без предложения принять. | Нет нового состояния «предложен» и окна подтверждения. |
| Если продолжение пока недоступно, оно ожидает. | Ожидание переживает сохранение и не требует повторного завершения предшественника. |
| Выполненные ранее условия учитываются. | При запуске/восстановлении сверять сохранённое состояние, а не ждать нового события. |
| Нужны последовательность, параллельные продолжения и ветвления. | Поддержать независимые выходы и выбор одного выхода. |
| Отказ от предложения, провал и отказ от активного задания могут открывать продолжения. | Различать причину завершения попытки и итоговый QuestStatus. |
| Автоматическое принятие происходит после возвращения в мир. | В бою, диалоге, загрузке и переходе между локациями хранить ожидание. |

Область действия — журнал игрока в текущем прохождении. Новый запуск игры очищает прогресс и ожидания; загрузка продолжает их. NPC могут оставаться источниками диалогов и участниками условий, но собственные журналы и выполнение квестов NPC здесь не проектируются.

В объём входят JSON, runtime, сохранения, интеграции источников, журнал/уведомления и редактор. Наполнение начальной истории, баланс наград и конкретные сюжетные условия остаются отдельным авторингом. Система используемых предметов из связанного документа ещё не является готовой зависимостью.

## 2. Что реализовано сейчас

| Существующая часть | Проверенное поведение | Требуемое расширение |
| --- | --- | --- |

| Факты | LocationFactTracker сохраняет посещения; есть убийства, экипировка и другие семейства. Семейства `Item_Used` в `FactKeys` нет: его и писателя вводят usable items (#704, #705). | Дополнить недостающие свидетельства; не путать наличие ключа и работающий трекер. |
| Приёмка и сдача | Квест принимается только диалогом (`AcceptQuest`) или отладочной консолью; завершение всегда идёт через `TurnIn` (`IQuestLogService`: «Completion is never automatic»). | Начальный квест usable items (#716) без этого плана не выдаётся и не завершается: ему нужны корневое правило новой игры и `completionMode: Automatic` (решение Q01). |
| Слой данных | `GameDataService` вызывает `Apply` на каждый файл; шага после чтения всех каталогов нет. | Перекрёстные проверки — в новом шаге после загрузки (решение T03 архитектуры временных эффектов). |
| Сохранение | `CanSave` — одно выражение с прямыми зависимостями. | Защита операции журнала и автоматики — через общий `ISaveBlocker` (решение T02 там же). |
| Инструменты | NarrativeEditor/DataEditor используют общие DTO, схемы, NarrativeVocabulary, NarrativeChecks и песочницу. | Показать правила/продолжения, проверить связи и дать прогон ожиданий. |

## 3. Предлагаемое устройство

Сохранить QuestLogService единственным владельцем жизненного цикла и наград. Добавить QuestAutomationService: он определяет, какие автоматические команды созрели, хранит ожидания и вызывает журнал через общий вход. Он не меняет QuestState напрямую, не выдаёт награды и не вызывает действия вместо журнала.

В QuestEntry добавить три поля:

- completionMode: ExplicitTurnIn по умолчанию или Automatic.
- activationRules: независимые правила первоначальной автоматической выдачи этого квеста. Пустой список сохраняет ручное получение.
- continuations: группы продолжений после определённого завершения попытки данного квеста.

Отдельный QuestChain со своим прогрессом не нужен: граф образуют ссылки между определениями, а состояние исполнения уже принадлежит квестам и ожиданиям. Объединение параллельных ветвей задаётся условиями над историей завершения нескольких квестов. Этапы остаются внутренним графом одного определения.

Разделить «событие произошло» и «квест можно принять сейчас». История посещения/получения/использования хранится в фактах. Условия правила обнаруживают причину запуска; acceptConditions целевого квеста остаются последним барьером, например необходимым уровнем репутации. Историческое свидетельство не исчезает вместе с предметом, но требование иметь предмет сейчас проверяется через HasItem.

## 4. Основные сущности и контракты

Все новые названия в таблицах — предлагаемые. Не создавать отдельный класс там, где достаточно небольшого record или приватного помощника указанного сервиса.

### 4.1. Определения

| Сущность | Поля / ответственность |
| --- | --- |
| QuestCompletionMode | ExplicitTurnIn, Automatic. Одинаковый режим для успешных исходов одного квеста; неуспешный исход всё равно проваливает задание. |
| QuestActivationRuleDefinition | Id, Conditions. Правило принадлежит целевому квесту. Все условия списка обязательны; AnyOf выражает альтернативы. Пустой список означает получение при первой готовности мира. |
| QuestContinuationGroupDefinition | Id, On: список QuestResolutionKind, необязательный OutcomeId, Selection, Routes. Привязана к квесту-предшественнику. |
| QuestRouteSelection | All — независимые выходы; FirstMatch — ровно один выход, порядок массива задаёт приоритет. |
| QuestContinuationRouteDefinition | Id, QuestId, Conditions. Условия выбирают маршрут, acceptConditions целевого квеста определяют возможность исполнения выбранного запуска. |
| QuestResolutionKind | Completed, Failed, Declined, Abandoned. Это причина окончания/отклонения попытки, а не замена QuestStatus. |

| QuestHistoryCondition / Factory | Новое безопасное условие QuestHistory: questId, resolution, опционально outcomeId. Проверяет наличие успешно зафиксированной записи истории; по смыслу «когда-либо в этом прохождении». |

Определения живут в провайдере; при принятии создаётся QuestState, а не копия определения. Все ожидающие операции принадлежат прохождению, поэтому выгрузка боковой локации не уничтожает их.

### 4.3. Команды и сообщения

| Контракт | Назначение |
| --- | --- |
| AcceptQuestRequest → QuestOperationResult | QuestId, Origin, AutomationKey?, NarrativeContext. Handler делегирует журналу; автоматическое происхождение требует открытого gate. |
| CompleteQuestRequest → QuestOperationResult | Общий вход явной сдачи и автозавершения; Handler использует один путь проверки/выдачи награды. |
| QuestCommandOrigin | Explicit — действие игрока/диалога; Automatic — правило или продолжение. Значение определяет внутренний адаптер, UI не выбирает обход gate. |
| QuestResolutionCommittedMessage : IMessage | Неизменяемая QuestResolutionRecord. Публикуется после фиксации операции, будит автоматику; не является единственным хранилищем причины. |
| QuestOperationCommittedMessage : IMessage | ID квеста, попытки и операции, AutomationKey?, результат. Позволяет погасить все ожидания на уже принятое задание. |
| PlayerItemAcquiredMessage : IMessage | OperationId, LineId, DefinitionId, Amount, AcquisitionKind. Подтверждённое внешнее поступление игроку, а не любое изменение количества в сумке. |
| PlayerBattleResolvedMessage : IMessage | BattleId, Results. Одно логическое завершение боя игрока; включает идентичность, которой нет в нынешнем BattleEndEvent. |
| WorldInteractionCommittedMessage : IMessage | OperationId, LocationId, ObjectId, ActionId. Подтверждённое действие с устойчивой целью. |

Существующие QuestStatusChangedEvent и QuestStageAdvancedEvent оставить для UI. Новые межсистемные команды идут через GameMessageBus Request/Response, оповещения — IMessage. Сервис внутри своего модуля может вызвать общий внутренний метод напрямую. Существующие bool-методы IQuestLogService допустимо временно оставить адаптерами; логика не должна дублироваться.

GameMessageBus выполняет несколько обработчиков сообщения через Task.WhenAll. Поэтому обработчики новых сообщений только сохраняют свидетельство/ставят dirty-флаг на игровом потоке. Они не запускают рекурсивную цепь Accept/Complete и не полагаются на порядок подписчиков. Изменения игрового состояния не отправлять в Task.Run.
QuestExecutionFault — сохраняемый record с фазой операции и индексом остановившегося действия. ICheckedNarrativeAction и NarrativeActionCheckResult / NarrativeActionExecutionResult — предлагаемый проверяемый вход для автоматически выполняемых действий; подробные гарантии и ограничения приведены в разделе 9.2. QuestConditionWakeupAdapter и конкретные fact-трекеры — небольшие адаптеры существующих событий, не самостоятельные владельцы квестового прогресса.

## 5. Правила запуска, ветвления и повторения

### 5.1. Корневое правило

1. При готовности данных и после восстановления мира проверить activationRules всех загруженных определений.
2. Если Conditions выполнены, создать одно ожидание с ключом Root(QuestId, RuleId). Само правило больше не требует повторного события; последующая смена его условий не удаляет ожидание.
3. Перед принятием заново проверить gate и acceptConditions. Невыполненные условия дают Waiting, а не удаление записи.
4. После фактического принятия погасить все корневые правила этого квеста и все его уже существующие ожидания. Ручное принятие тоже удовлетворяет ожидающий запуск.

Условия правил проверяются при обработке согласованного состояния, не на промежуточных уведомлениях операции. Во время боя исторические факты продолжают накапливаться, а проверка/принятие выполняются после возврата в мир. Сценарий «получил и потратил предмет в бою» обязан использовать Item_Acquired, а не HasItem. Автоматика не обещает запомнить каждый краткий переход произвольного текущего предиката.

### 5.2. Продолжения

Каждая зафиксированная QuestResolutionRecord открывает подходящие группы continuations: фильтр On и, если указан, OutcomeId. Ключ экземпляра группы — (ResolutionId, GroupId), маршрута — (ResolutionId, GroupId, RouteId). Повторное сообщение с тем же ResolutionId ничего не создаёт.

| Selection | Правило |
| --- | --- |
| All | Каждый маршрут независимо ждёт своих Conditions. Как только они выполнены, фиксирует выбор и создаёт ожидание принятия. Остальные маршруты продолжают ждать. Это позволяет параллельный старт сразу или с разной задержкой. |
| FirstMatch | Пока ни один маршрут не выбран, проверять Conditions в порядке массива. Первый подходящий фиксируется; остальные закрываются навсегда для этого экземпляра группы. Если выбранный квест пока недоступен, ждать его, не перескакивать на другую ветвь. |

Для FirstMatch выбор происходит на первом безопасном проходе с подходящей ветвью. Безусловный последний маршрут — немедленный запасной выход: он не ждёт, пока когда-нибудь откроются более приоритетные. Для обязательного ожидания автор не добавляет безусловный выход. Эта семантика является техническим предложением для правки.

OutcomeId читается из неизменяемой записи завершения, а не из текущей повторной попытки предшественника. Условия маршрутов читают текущее согласованное состояние; сюжетные выборы должны быть записаны в устойчивые факты либо OutcomeId.

Слияние ветвей: у целевого квеста корневое правило AllOf из двух QuestHistory(Completed). История сохраняет результат даже после повторного принятия предшественника; QuestStatus(Completed) проверяет только текущий статус и для такого сценария недостаточен.

### 5.3. Повторы и вмешательство игрока

- Квест, уже Active или ReadyToTurnIn, удовлетворяет новый запрос запуска без повторного OnAccept.
- Уже Completed-квест удовлетворяет автоматический запрос без повторного старта, даже если Repeatable=true. Автоматический фарм повторяемых квестов здесь не вводится. Ручное повторение сохраняется.
- Корневой автозапуск одноразовый в прохождении. После отказа от автоматически выданного квеста он не появляется снова из-за постоянно истинного факта.
- Явный Decline или Abandon отменяет существующие ожидания на этот квест и погашает его корневые правила. Альтернативы запускаются по новой записи причины. Новый маршрут от будущей попытки другого квеста может снова предложить автоматический запуск, если CanAccept разрешает; это новый источник, не повтор старого ожидания.
- Failed блокирует автоматическое принятие по действующим правилам журнала: ожидание становится Cancelled с объяснением, а не бесконечно Waiting.
- Недостающий уровень, репутация или ещё не истёкший cooldown — временный отказ и Waiting. Ручной Decline во время этого ожидания имеет приоритет и отменяет именно существующее ожидание.
- Два маршрута к одному квесту не создают две попытки. Все принятые команды и результаты обрабатываются последовательно; успешное принятие удовлетворяет остальные ожидания.
Состояние Faulted проверяется прежде AlreadySatisfied. Частично созданная Active-попытка с ошибкой OnAccept не считается успешно выданной, её ключ не погашается как Fulfilled и она не продвигается до явного восстановления. Исторические корневые правила отменяются по сохранённым отметкам отказа, даже если Conditions такого правила впервые стали истинны уже после отказа.

## 6. Причины завершения и идентичность попыток

QuestStatus сохранить совместимым с существующим UI. Добавить независимую историю переходов в QuestLogService; не кодировать её десятками произвольных мировых фактов.

| Операция | Kind в истории | ResultingStatus |
| --- | --- | --- |
| Успешная сдача / автозавершение | Completed | Completed |
| Дедлайн, потеря всех допустимых адресатов, неуспешный исход | Failed | Failed |
| Отклонение предложения | Declined | Declined либо Failed по политике |
| Отказ от Active / ReadyToTurnIn | Abandoned | Declined либо Failed по политике |

При DeclinePolicy.Fail записывается одна первичная причина Declined или Abandoned, а не две записи вместе с Failed. Если автор хочет одинаковое продолжение для всех неудач, перечисляет все три Kind в On. ReasonCode уточняет дедлайн/потерю адресата/исход и предназначен прежде всего для диагностики; свободный текст причины не является ключом ветвления.

Для отклонения предложения расширить вход Decline параметром OfferId; значение создаёт диалоговый раннер один раз для пары (сессия разговора, квест), повторные клики используют тот же ID. Журнал проверяет доступность нового предложения по своей политике и хранит ID обработанного предложения вместе с причиной. У Abandon цель — текущий AttemptId, отдельный оффер не нужен.

AttemptId — монотонный номер попытки данного квеста. Принятие после отклонения/повторение создаёт следующий номер. Отклонение ещё не принятого предложения также создаёт попытку. Повторный Decline уже отклонённой попытки — no-op, пока не возник новый допустимый оффер; его идентичность задаёт журнал, а не случайное число на каждом клике. Новая возможность оффера появляется после возвратной политики/cooldown и явного открытия новой сессии предложения; при реализации диалоговый адаптер должен передавать стабильный OfferId для этого предложения. Закрытие диалога само по себе не считается отказом.

ResolutionId — монотонный long в пределах прохождения; счётчик сохраняется. История хранит только завершения/отказы попыток, а не все изменения мира. OnAccept/OnEnter/OnComplete не повторяются при восстановлении. Команды с уже применённым AutomationKey не создают новую попытку.

## 7. Когда разрешено выполнять автоматику

IQuestExecutionGate открыт только при одновременном выполнении условий:

1. Каталоги загружены; игровой хост закончил создание и регистрацию объектов мира.
2. Нет pending load, ILoadScope.IsLoading=false; все секции восстановлены и игрок размещён.
3. IUiContextService.Current == World, живой игрок существует, не сражается; диалог не активен.
4. Нет перехода локации, запуска/закрытия арены и смены сессии.
5. В данный момент не исполняется другая операция журнала/награды.

Добавить явную готовность хоста для автоматики: Main сообщает её после завершения стартового размещения, загрузки и cleanup боя/путешествия; перед этими операциями снимает. Готовность — отдельный сервис (решение Q09), который выставляют конкретные точки Main: `LocationCoordinator.Attach` и отложенный старт в настроенной локации, `CompleteLoad(true)` вместе с `GameLoadedEvent` от `SaveDirector`, `finally` боя в `Main` после возврата мирового HUD, фиксация путешествия, оживление игрока. Не использовать один кадр ожидания как доказательство готовности. UiContextService остаётся владельцем UI-контекста, а готовность хоста отражает только жизненный цикл сцены.

В текущем Main глобальный BattleEndEvent публикуется до завершения finally с освобождением контекста и сменой HUD. Он будит проверку, но не является разрешением принять квест немедленно. При поражении ждать PlayerRevivedEvent и готовности мира; в GameOver запуска нет. После сбоя создания боя готовность открывается только если хост действительно восстановлен; сообщение успешного результата боя не синтезировать.

Существующие реакции фактов/инвентаря/часов заменить на постановку переоценки в очередь. Автоматические переходы этапов и их действия у всех квестов выполняются в безопасном мире (решение Q02): это предотвращает SpawnNpc и вложенный AcceptQuest из OnComplete во время боя (класс ошибок #576). Значения прогресса можно читать в бою, но переход, автосдача и следующий квест фиксируются после возврата. Проверка дедлайна при таком проходе использует текущие игровые минуты; приоритет дедлайна перед завершением сохранить из нынешнего EvaluateQuest.

Явное принятие и сдача через текущий диалог остаются допустимы в принадлежащем ему контексте. Их продолжения откладываются до конца разговора. AcceptQuest в действиях квеста помечается как Automatic и создаёт ожидающий запрос, а не обходит gate; прямой выбор AcceptQuest игроком в диалоге имеет Explicit. Происхождение задаётся раннером, не самим JSON. У нового графа и старого AcceptQuest есть общая защита от дублей, но для ожиданий/ветвей автор использует continuations.

## 8. Источники выдачи и мировая память

| Сценарий | Устойчивый источник | Кто пишет / когда |
| --- | --- | --- |
| Новая игра | Пустые Conditions корневого правила + отсутствие отметки о получении. | Первый безопасный проход после запуска. После загрузки такого же ещё не выданного квеста правило тоже доступно. |
| Посещение области | Существующий Location_Discovered:<markerId>. | LocationFactTracker по LocationDiscoveredEvent. Для перехода в локацию без маркера добавить отдельное семейство Location_Visited:<locationId> в адаптере успешного размещения. |
| Мировой факт | Существующий Fact(key,count), композиты. | Система-владелец игрового события; автоматика только читает. |
| Получение предмета | Новое Item_Acquired:<DefinitionId>, суммарное число полученных единиц. | PlayerItemAcquiredFactTracker после подтверждённого поступления игроку. |
| Использование предмета | Item_Used:<DefinitionId> и необязательный авторский факт. | ItemUseFactTracker, предусмотренный в [[UsableItemsArchitecture]], после успешной фиксации использования. |
| Завершение боя | Новые Player_Battle_Completed и Player_Battle_Result:<BattleResults>. | PlayerBattleFactTracker по одному PlayerBattleResolvedMessage на бой игрока, после логического завершения. |
| Взаимодействие с объектом | Новое World_Interaction:<locationId>:<objectId>:<actionId>. | WorldInteractionFactTracker после успешного конкретного действия. |

Новые ключи создаются через константы/строители FactKeys и регистрируются в FactKeyRegistry с источниками допустимых ID. Валидатор проверяет непустые компоненты и запрещает разделитель ':' внутри каждого компонента составного ключа либо применяет одну общую схему экранирования. Предлагаемый начальный вариант — запрет разделителя в ID.

### 8.1. Получение предмета

Нельзя вычислять получение только по ItemAmountChanges: событие содержит итоговое количество, восстановление сумки также меняет его, снятие экипировки не означает новое приобретение, уведомления могут объединяться.

Подключить подтверждение поступления к границам операций: подбор, перенос из внешнего контейнера (сундук и тело `DeadBody` через общее ядро контейнера usable items), покупка, выдача награды/диалога, крафт нового предмета, возврат ресурсов при разборе, новый аугмент из конвертации 3→1, выдача предметом `GiveItem` usable items (решение Q04). Золото уходит в кошелёк мимо сумки и приобретением предмета не считается; извлечение аугмента или орнамента из сокета — тоже. Сообщение содержит фактически полученное количество, включая частичный перенос. Перестановка слотов, экипировка/снятие, сортировка, rollback и Restore ничего не начисляют. Результат изготовления считать приобретением; превращение существующего предмета при заточке/реролле — нет. Продажа и обратная покупка считаются новым внешним поступлением; это статистика поступлений, не число уникальных физических вещей.

Каждая граница выпускает один OperationId и ровно одно подтверждение на позицию; не публиковать повторно из общего TryAddItem и из вызывающего торгового/квестового сервиса. Для состава операции ключ дедупликации — (OperationId, LineId); повтор доставки внутри сессии игнорируется трекером. Завершённые сообщения не переигрываются из сейва, сами факты сохраняются. События подтверждения должны быть обработаны до разрешения сохранения операции. Отдельная постоянная очередь сообщений не вводится.

### 8.2. Использование, бой и взаимодействия

Не начислять Item_Used при нажатии Use или по bool CanUse. Текущий void-контракт поведения не доказывает успех. До реализации согласованного результата использования этот источник имеет статус недоступной интеграции, видимый в диагностике редактора. Не писать второй Item_Used из подписчика на ItemUseCommittedMessage: связанный проект уже включает запись фактов в общую фиксацию.

Бой: BattleId брать у активного BattleContext/маркера; не считать локальный BattleEventBus и его повторную публикацию глобальным результатом. NPC-стычки не увеличивают статистику боёв игрока. Полный список значений результата берётся из существующего BattleResults, без ручного зеркального enum. Один бой может дать Completed и ровно один Result — пакет фактов виден согласованно.

Взаимодействие: открытие общего меню выбора не считается действием; InteractionService.Activate за показ меню возвращает `Started`. Писатель стоит после успешного исполнения выбранного действия либо в адаптере его позднего завершения. Результат Started сам по себе не подтверждает успех. Не писать за отмену, недоступность, старый handle или неудачный перенос. Для «обыск завершён» и «открыт сундук» нужны разные авторские actionId/факты. Сохранённый ключ использует LocationId/ObjectId/ActionId; runtime binding generation не сохраняется. Для динамических целей без устойчивого ObjectId использовать явно заданный авторский факт, не случайный ID нового экземпляра.

## 9. Исполнение и согласованность

### 9.1. Общая очередь

События источников только ставят dirty. Один драйвер на игровом потоке выполняет проход после завершения исходной операции. Последовательность: актуализировать принятые квесты → обработать историю разрешений → условия корневых правил и маршрутов → автоматические команды. После команды пройти вновь, если изменилось состояние. При закрытии gate остановиться, сохранив оставшуюся работу.

Порядок детерминирован: ResolutionId, затем порядок групп/маршрутов в JSON; независимые корневые правила — по QuestId/RuleId (Ordinal). Между независимыми заданиями это технический порядок, не способ выразить сюжетную зависимость: её задают условиями.

Не опрашивать всё каждый кадр. Будить по фактам, инвентарю, статусам/истории квестов, контексту, готовности хоста, игровым часам, изменению мастерства/атрибутов/репутации для поддержанных условий. QuestConditionWakeupAdapter связывает эти существующие уведомления с RequestEvaluation; для нового вида условия обязательна регистрация источника переоценки. Первая версия может проверять весь небольшой каталог на одном dirty-проходе; индекс зависимостей — оптимизация после измерения.

Поставить бюджет операций на кадр в настройках драйвера; остаток переносится на следующий безопасный кадр. Он защищает от длинного каскада, но не заменяет проверку циклов. Один Waiting без изменения входного состояния не помечает очередь dirty повторно.

### 9.2. Завершение и награды

Automatic и ExplicitTurnIn используют один внутренний TryComplete. В первом режиме ReadyToTurnIn — также состояние ожидания свободного места для награды. До успешной выдачи А продолжение с On=Completed не открывается.

1. Проверить ожидаемую попытку, ReadyToTurnIn, отсутствие исполняемой операции и допустимость происхождения команды.
2. Определить награды выбранного OutcomeId либо общие награды. Применить существующий реестр уникальных предметов.
3. Проверить возможность выдачи всех обязательных предметов. Существующее сравнение свободных слотов с числом записей не доказывает вместимость с учётом amount/стаков: выделить общий план размещения наград, согласованный с правилами инвентаря. Это один планировщик размещения в `Core/Inventory` для наград квестов и для выдачи предметов usable items (#748), а не два (решение Q07). До мутаций держать созданные конкретные предметы в плане; при нехватке не выдавать часть и не начислять опыт. Применять план на игровом потоке без await и без внешних вызовов между вставками; использовать существующую область отложенных уведомлений инвентаря, чтобы подписчик не занял зарезервированное планом место посреди выдачи. До публикации уведомлений весь список предметов уже размещён. После этого действия награды исполняются со своими явно ограниченными гарантиями.
4. При обычном временном отказе вернуть Deferred(RewardCapacity), оставить ReadyToTurnIn; повторить после изменения вместимости и при открытом gate. Не повторять тост каждый кадр.
5. Установить внутренний guard операции, исполнить общую выдачу и действия награды один раз, без await внутри изменения журнала. Вложенные квестовые команды поставить в очередь.
6. Зафиксировать Completed, успешную QuestResolutionRecord и исполнение ключа команды. Только затем публиковать квестовые уведомления; очередь продолжения исполняется позже.

Для Automatic не требовать NPC сдачи и не проваливать задание из-за исчезновения такого NPC. Непустой turnInNpcIds при Automatic — ошибка данных: автор должен устранить противоречие. Дедлайны и canFail сохраняют самостоятельный смысл.

Это не общая транзакция между А и Б: успешно завершённый А не откатывается, если Б недоступен. Все ожидаемые проверки награды выполняются до её выдачи, но существующий INarrativeAction.Execute не даёт гарантии отката произвольного списка действий. Не называть весь список награды атомарным.

Для технического исключения хранить QuestExecutionFault с QuestId, AttemptId, Phase и индексом действия; исполнение и автоматическое повторение этой попытки блокируются, успешной записи Completed не возникает. До начала side effects отметить операцию Running; на исключении перевести в Faulted. Восстановленная Running трактуется как Faulted. Сохранение промежуточной Running запрещено guard-ом, Faulted сохраняется явно. Автоматический повтор частично выполненного списка запрещён, восстановление — через предыдущий сейв либо отдельную диагностическую команду разработчика. Не выдавать обещания exactly-once после аварийного завершения процесса между игровым изменением и записью сейва.

Некоторые нынешние действия сами поглощают ошибку и возвращают void (например, SpawnNpc). Для автоматически исполняемых списков добавить минимальный проверяемый контракт ICheckedNarrativeAction: Check(context) без побочных эффектов и ExecuteChecked(context) с Applied/Deferred/Failed. До старта операции выполнить общую предварительную проверку списка и динамическую проверку первого шага; Deferred до мутаций допускает ожидание. Legacy-действие без результата не допускается в автоматически выполняемый список без явного адаптера. Этапы продвигаются автоматически у всех квестов, поэтому адаптер получают все фабрики действий, кроме `StartTrade`: оно открывает окно и в автоматически исполняемых списках запрещено валидатором (решение Q08). Адаптер должен получать реальный результат доменной операции; обёртка над void, безусловно возвращающая Applied, не считается проверкой. Check проверяет требования текущего шага до его эффектов; общая предварительная проверка списка проверяет структуру и мировые зависимости. Если динамическое требование позднего шага зависит от раннего, оно проверяется непосредственно перед этим шагом, а отказ после уже выполненных эффектов даёт Faulted. Все ожидаемые ограничения типовой выдачи предметов покрывает отдельный план наград, не произвольный список actions. Ошибка после начала изменений — Faulted, а не повтор всего списка. Эта же граница применяется к OnAccept/OnEnter/OnComplete/OnFail автоматически продвигаемых квестов. Не расширять это в универсальный движок транзакций.

Стартовый SpawnNpc дополнительно проверяет регистрацию нужной точки в доступной локации. Неподгруженная точка даёт ожидание требуемого мира; не подменять её точкой с совпавшим именем. Если сюжет должен создавать NPC в выгруженной локации, нужна отдельная возможность отложенного создания в её snapshot — в текущем расширении она не предполагается.

### 9.3. Условия без побочных эффектов

Правила автоматики, маршруты и acceptConditions автоматически запускаемых квестов должны быть безопасны для повторной проверки в NarrativeContext.Empty. Проверять IsPreviewSafe рекурсивно; дополнительно валидировать отсутствие требований к живому собеседнику. NpcRelation нельзя считать подходящим только потому, что чтение безопасно.

QuestOfferRoll и косвенный CanAcceptQuest в автоматических условиях запрещены: проверка не должна роллить RNG, менять факты или скрыто обходить ограничения. Для «доступен следующий квест» используется отдельный вызов журнала при исполнении, а не такой предикат в JSON. Ручные диалоги сохраняют существующие возможности. Условия неизвестного типа отклоняются вместе с определением, не пропускаются.

## 10. Основные потоки

### 10.1. Первоначальная выдача

1. GameDataService загружает Quests, QuestProvider создаёт определения.
2. Main заканчивает стартовое размещение; gate становится доступен.
3. Драйвер проверяет корневые правила, включая пустые Conditions и ранее накопленные факты.
4. AutomationService фиксирует Waiting и отправляет AcceptQuestRequest.
5. Журнал проверяет ограничения, создаёт AttemptId/QuestState, фиксирует базовые значения целей, выполняет проверенные стартовые действия.
6. После успеха ожидания гасятся; QuestStatusChangedEvent обновляет журнал и HUD, обычный broadcaster показывает получение.
7. Если цели уже выполнены, следующий проход продвигает этапы и при Automatic завершает квест; историческая ретроактивность не подавляется искусственным требованием подождать кадр.

### 10.2. А завершён → Б ожидает → Б принят

1. Автоцели или явная сдача вызывают общий TryComplete(A).
2. Награда А выдана, Completed и ResolutionId зафиксированы; уведомление о завершении А публикуется первым.
3. По записи разрешения создаётся экземпляр группы продолжений, выбирается маршрут Б.
4. Если идёт диалог/бой, ожидание сохраняется. Если не выполнены acceptConditions Б, остаётся Waiting с причиной.
5. Возврат в мир или изменение условий будит очередь; повторная команда Б проходит актуальные проверки.
6. Принятие Б не повторяет сдачу и награду А. Его уведомление идёт после завершения А.

### 10.3. Разветвление, параллельность и объединение

1. А фиксирует исход Helped или Refused; запись разрешения сохраняет исход.
2. Подходящая группа FirstMatch выбирает одну ветвь и записывает её ID до принятия цели. Изменение мировых фактов позднее не выбирает другую ветвь этой группы.
3. Независимая группа All может одновременно открыть два побочных задания; отказ одного не отменяет другое.
4. Финальный квест имеет activationRule с двумя QuestHistory(Completed). После обоих завершений он становится кандидатом даже при завершении в обратном порядке или до загрузки сохранения.

### 10.4. Отказ и провал

1. Игрок отклоняет предложение либо отказывается от Active; журнал проверяет попытку/OfferId и политику.
2. Готовит один результат с первичной причиной Declined/Abandoned и целевым статусом внутри защищённой операции.
3. Выполняет соответствующие проверенные действия; при успехе фиксирует статус, запись истории и отмену актуальных ожиданий на этот квест. Сбой после эффектов даёт Faulted и блокирует продолжения.
4. После успешной фиксации запись открывает подходящие альтернативы; принятие ждёт безопасного мира.
5. Дедлайн/потеря адресата/неуспешный исход создают Failed только если canFail разрешает. Запрещённый провал не открывает ложную ветвь Failed.

### 10.5. Событие в бою / загрузка

1. Успешное применение предмета или результат боя записывает факты независимо от наличия квеста.
2. Закрытый gate не позволяет стартовым действиям менять мир; dirty сохраняется.
3. После cleanup боя и возвращения живого игрока проходит обычная переоценка.
4. При загрузке вместо повторения событий восстанавливаются факты, журнал и ожидания. После полной готовности мира выполняется такой же проход.
5. Если пользователь успел получить и потратить предмет до появления продолжения, Item_Acquired всё равно удовлетворяет историческое условие.

```json
  "routes": [
    {
      "id": "Alternative",

```

```json
{

    { "type": "QuestHistory", "questId": "Quest_Right", "resolution": "Completed" }
  ]
}
```

Ключ conditions в AllOf соответствует существующему CompositeConditionFactory. Новым здесь является только QuestHistory, которое добавляется в общий словарь и инструментальную схему.

## 12. Сохранения, время и новая сессия

Секцию quests поднять до v4: AttemptId, счётчик ResolutionId, история разрешений, сведения о Faulted-операциях и уже применённых AutomationKey. Секцию questAutomation v1 хранить отдельно: состояния корневых правил, выбранные маршруты, Waiting/Fulfilled/Cancelled/Faulted, курсор обработанной истории. Курсор и созданные из записи ожидания меняются одной синхронной операцией, сохранение между ними запрещено guard-ом.

Восстановление: факты/инвентарь/квесты → questAutomation после RestoreOrder.Quests (предложение: отдельная константа QuestAutomation=26) → оставшиеся секции, NPC, локация и игрок → открытие gate. Порядок секций сам по себе не разрешает исполнение. Restore только восстанавливает данные. Автоматика сверяет необработанные QuestResolutionRecord, так что потерянное уведомление не теряет продолжение.

Если цель уже принята, а ожидание ещё Waiting, сверка по журналу превращает его в Fulfilled без повторного OnAccept. Если исходное определение/маршрут удалено, ожидание не переназначается по индексу: пометить Faulted/MissingDefinition, сохранить исходные ID и вывести диагностику. Переименование ID требует явной миграции; порядок массива может меняться без изменения идентичности ожидания. При живом hot reload не сбрасывать выбранную ветвь.

Предлагаемая совместимость со старыми сейвами: не придумывать утраченную историю. Для v3 сохранять прежние состояния и назначить служебные номера текущим попыткам; не восстанавливать Declined как Abandoned и не считать Failed доказательством самостоятельного провала. Исторические продолжения по отсутствующим ResolutionRecord не запускать автоматически. Историю для старых сейвов не синтезируем даже для доказуемого Completed: продолжения работают только в прохождениях, начатых с новой версией (решение Q03). Новые события и факты работают с момента обновления. Полная гарантия ретроактивности относится к прохождениям, где свидетельства уже записывались.

Время остаётся временем мира: AcceptedAtMinutes, NextOfferAtMinutes, AtGameMinutes — целые игровые минуты; timeLimitHours/declineCooldownHours переводятся существующим общим способом. Ожидание продолжения не имеет нового таймаута. Не переносить сюда реальные минуты перезарядок предметов или ходы боевых бафов.

Новая игра: закрыть gate, увеличить временное поколение запуска, очистить журнал/историю/факты/автоматику через ISessionResettable, загрузить начальный мир и открыть gate. Обратные вызовы от старого хоста/предыдущей загрузки проверяют поколение и игнорируются. Загрузка не считается новой игрой и не обнуляет погашенные правила.

## 13. Редактор, проверки данных и UI

QuestProvider продолжает строго разбирать запись. После загрузки всего каталога выполнить перекрёстную проверку целевых квестов и графа — в шаге слоя данных после чтения всех каталогов (решение T03): порядок чтения файлов не должен решать, существует ли ссылка. Некорректные автоматические связи блокировать с диагностикой до исполнения; не молча превращать их в пустые условия.

В NarrativeChecks и общие схемы включить:

- Уникальные QuestId, RuleId, GroupId/RouteId в соответствующих областях; непустые и известные ссылки/enum/OutcomeId.
- Pure/world-compatible условия, корректные писатели фактов и перечень недоступных интеграций.
- Automatic без адресатов сдачи; корректные этапы и награды; проверяемые действия автоматически исполняемых списков.
- Прямые циклы графа continuations, включая self-edge: отклонять. Для косвенных циклов через QuestHistory/QuestStatus и AcceptQuest в actions — перекрёстная диагностика; runtime дедупликация и бюджет прохода обязательны независимо от статической проверки.
- Безусловный маршрут не на последнем месте FirstMatch, одинаковые цели, недостижимые ветви, отсутствие явной сдачи, конфликтующие корневые правила и исключающие ветви — предупреждения с адресом JSON.
- Будущий автоматически запускаемый квест с контекстными acceptConditions либо стартовым SpawnNpc без доступной мировой точки — объяснимое ограничение, а не бесконечное молчаливое ожидание.

NarrativeEditor: в outline добавить completionMode, activationRules и группы/маршруты continuations; редактирование через общие DTO/схемы, ссылки и Undo/Redo. Граф отдельных квестов строится поверх ссылок, без второй копии данных: различать All, FirstMatch и причины; слияние по условиям показать отдельной пометкой зависимости. Наличие такого графа не должно блокировать базовый авторинг в инспекторе.

Dry run использует настоящие провайдеры/журнал/автоматику с управляемым gate и подставными источниками: дать факт, получить предмет, завершить бой, завершить/провалить/отклонить квест, выйти в мир, сохранить/восстановить состояние. Показать Waiting и причину, выбранный маршрут, Applied и Faulted; неподдержанные эффекты песочницы обозначать явно.

Игровой журнал показывает только принятые задания; PendingQuestActivation — техническое состояние, не фальшивый Active. Квест Automatic с ожидающей наградой получает понятную подпись «Освободите место для награды», а не «Вернитесь к NPC». Уведомления обычного получения/завершения переиспользуются, локализация через существующие ключи/сервис. Диагностический список ожиданий доступен через debug-консоль; служебные ключи и классы в игровой интерфейс не выводятся.

Последовательность работ:

1. Контракты JSON/enum/DTO, правила чистоты, проверка ссылок и определений. Старые данные с отсутствующими полями сохраняют ручное поведение.
2. История причин и попыток, защита повторных команд, общий путь Complete, проверяемые действия и guard операций. Сначала обеспечить единственную точку изменения состояния.
3. Очередь переоценки и gate готовности мира; убрать исполнение новых квестов из вложенных событий инвентаря/фактов.
4. Правила получения и продолжения, состояния ожидания/выбора, автозавершение и возобновление после освобождения места.
5. Сохранение, восстановление и новая игра; проверка до подключения рабочего контента.
6. Источники фактов: существующие посещения/факты, приобретение, бой, взаимодействие. Использование — после реализации согласованного результата из [[UsableItemsArchitecture]]; до этого диагностика зависимости обязательна.
7. Редактор, dry run, UI причин ожидания наград и диагностическая консоль.
8. Авторинг начальной истории и осознанный перевод нужных существующих заданий. Исправить пустые стадии/битые счётчики отдельными явными изменениями данных; не менять все испытания на автоматические по умолчанию.

Задачи и их зависимости ведутся карточками на доске #3; сводная карточка со списком всех задач указана в разделе 17. Этап 0 — исправление счётчика `Quest_Field_Of_Bones`; шаг слоя данных после загрузки, общие запреты сохранения и часы сессии заведены в списке временных эффектов и используются здесь.

**Минимальный путь для начального квеста (решение Q01).** До контента этапа 4 usable items (#715–#717) готовы: поля и строгий разбор определений, история и результаты операций, общий путь завершения с планом размещения наград, проверяемые действия, очередь переоценки, gate и готовность хоста с драйвером, корневые правила, автозавершение и секции сейва. Продолжения, источники фактов, редактор и dry run могут идти после.

## 15. Критерии проверки будущей реализации

| Сценарий | Проверяемый результат |
| --- | --- |
| Два этапа одного квеста | Продвигаются по существующим правилам; отдельный квест и награда не возникают. |
| Старые определения | Отсутствие новых полей даёт ExplicitTurnIn и отсутствие автополучения. |
| Старт новой игры / повторная загрузка | Корневое правило выдаёт квест один раз; загрузка не повторяет OnAccept и награды. |
| Ретроактивность | Посещение, приобретение с последующей тратой, использование и завершённый бой до появления Б позволяют запуск без повторения события. |
| А Completed, Б пока закрыт | Награда А выдана один раз; Б ждёт, сохраняется и запускается после открытия условий. |
| Полная сумка на автонаграде | А остаётся ReadyToTurnIn, нет частичной награды/опыта/продолжения; после освобождения места награда и цепочка выполняются один раз. |
| All / FirstMatch | All допускает несколько целей и позднее открытие отдельных маршрутов; FirstMatch сохраняет один выбор даже при недоступной цели. |
| Слияние | Две QuestHistory-ветви учитываются в любом порядке, в том числе после повторной попытки предшественника. |
| Declined / Abandoned / Failed | Разные альтернативы, один ResolutionId на операцию; Fail-политика не дублирует причину. canFail=false не порождает Failed. |
| Две причины выдачи одной цели | Одна попытка, один OnAccept, остальные ожидания Fulfilled. |
| Бой, диалог, переход, загрузка | Никаких автоматических Accept/Complete/SpawnNpc до готовности мира; поражение ждёт оживления. Явная сдача в диалоге остаётся рабочей. |
| Согласованность наград и уведомлений | Completed А виден до принятия Б; события источников не исполняют квесты посреди выдачи. |
| Отказ игрока | Старое корневое правило и ожидание не навязывают квест снова; альтернативный маршрут разрешён. |
| Исключение / скрытый отказ действия | Проверяемый адаптер возвращает ошибку; частично исполненная операция Faulted и не повторяется после загрузки. |
| Источники фактов | Частичный перенос считает фактическое количество; экипировка, Restore, отмена взаимодействия, NPC-бой и повтор визуального события не начисляют факты. |
| Старый хост / смена сессии | Отложенный callback не меняет новое прохождение. |
| Плохие данные | Цикл, битый ID, небезопасное условие, неподдержанное действие и отсутствующий писатель имеют адресную диагностику. |
| Редактор | Сохранение/Undo/Redo не теряет ID правил; runtime и dry run дают одинаковые решения на одинаковом состоянии. |

Чистую логику проверять управляемыми тестами без создания нативных Godot-объектов. Жизненный цикл мира, реальный бой, возврат/оживление, диалоги, взаимодействия, локации, сохранение и UI — интеграционными сценами Godot. Это план проверок реализации; текущая задача проверяет сам документ и примеры, а не работу ещё не написанных сервисов.
