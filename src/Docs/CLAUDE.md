# LastBreath — правила работы (всегда в контексте)

Godot 4.7, C# (.NET 9, LangVersion preview: primary constructors, `field`). Пошаговая 2D RPG, соло-разработчик Todd, общение на русском. Подробный контекст архитектуры/способностей — `HANDOFF.md`.

## Поведение
1. НЕ предлагать что то сделать после выполнения задачи
2. НЕ повторять запрещенные/отклоненные действия. Пример: Я ставлю задачу сделать Х, но не делать Y. В отчете ты не говоришь что Y не сделан потому что я запретил.

## Общая информация о проекте
1. Проект на стадии прототипа/ранней альфы, за рамки дев билда не выходит. Это значит сейвы и системы можно менять и переписывать.

## Код
1. Один метод = одна функция.
2. Как можно меньше хардкод чисел/строк.
3. Системы расширяемы, но без оверинженеринга.
4. Несвязные между собой системы комуницируют через GameMessageBus посредством Request>Responce. Оповещение всех заинтересованных систем посредством IMessage (async void)
5. Компоненты предпочтительнее наследования, если наследование уходит глубже чем на 3 уровня.
6. Сначала поля, затем свойства, конструкторы и методы. Порядок ключевых слов private, protected, public
7. Решение не симптомов, а задач. Пример: Необходимо заблокировать UI в определенном сценарии. Вместо написания гуарда сначала стоит собрать информацию, возможно это не единичное место и лучше ввести механизм блокирующий UI для нескольких сценарие.
8. Документация в коде описывает функционал. Подписи типа "Вариант Б" или "Решение: Todd" излишни.
9. Повторяющиеся куски кода выносим в extension методы, хелперы либо обобщаем.
10. Вместо магических строк и хардкор чисел создаем константы/enums, выносим в конфигурации.
11. Для событий и сигналов используем null propagation. Пример: `_close?.Pressed += Close;` вместо `if (_close != null) _close.Pressed += Close;`
12. Предпочитаем keyword field вместо создания приватного поля (там где это необходимо и есть публичное свойство).
13. Предпочитаем Lock вместо object в асинхронном контексте.
14. Для избежания nesting инвертим условия (где возможно).


## Документация
1. Описываем конректно и по делу что делает метод/код. 
2. В документацию обсуждение из чата не попадает "Решение Todd" или "Выбранный вариант А/Б".
3. Коротко и по существу: одна-две строки. Целые параграфы-эссе над одной строчкой кода не пишем. Развёрнутое обоснование — в план/дизайн-док, не в xml-док.


## Дизайн
1. Работаем в контексте игры. Предложенные решения рассматриваем в рамках не только конкретной задачи, но и общей картины.
2. Нарратив в приоритете
3. Игровой мир работает по правилу: Игрок не центр вселенной,а всего лишь один из жителей. 

## Существующие системы и их назначение
- ParameterModifiersComponent содержит список модификаторов сущности. В большинстве случаев сущность получает модификаторы от экипировки (больше всего относится к Игроку), Аттрибутов (Dex, Int, Str), пассивок, реже от эффектов.
Задача данного компонента: Хранение списка модификаторов цели и уведомление об изменениях списка модификаторов для параметра.
Для нпс имеется дополнительный источник модификаторов: INpcModifier.
- EntityParametersComponent содержит значения параметров сущности. Работает в связке c ParameterModifierComponent (неявно посредством подписки на EventHandler<IModifiersChangedEventArgs>? ModifiersChanged). При получении уведомления об изменении модификаторов параметра пересчитывает значение и сохраняет в Current. Все значения расчитываются по схожей формуле: (сумма flat * (1 + сумма insreased)) * (1+ сумма мультиплаеров). Параметры сущности затем могут быть изменены посредством декораторов. 
Задача компонента: Хранение, расчет и уведомление об изменении значения параметра. 
- EffectsComponent хранит и обрабатывает эффекты владельца. Уведомляет о добавлении и удалении эффекта. 
- NpcModifier хранит список модификаторов наложенных на нпс. Один из источников модификаторов значений параметров для нпс. 
- PassiveSkillComponent обрабатывает пассивные способности сущности. Уведомляет о добавлении/удалении. 
- ModifierHandlerComponent хранит пайплайны обработки контекстов. IContextModifier<T> используется для модификации цифровых значений атаки, лечения, урона и активации способностей. Порядок применения — семантическая шкала `ContextModifierPriority` (Early −100 / Normal 0 / Late 100 / Absolute 1000); конверсии урона при появлении берут Absolute (применяются последними).
- **Урон атаки — словарь компонентов (2026-07-26)**: `AttackContext.DamageComponents` (тип → значение). При создании сеются Physical = базовый урон и флэт `Fire/Cold/LightningDamage` атакующего (префиксы оружия); бонус способности = `AddDamage(Physical, x)`, «+X% этой атаке» = `ScaleDamage` (Право первого, Primal Fury — умножают ВСЁ, включая стихию). Крит умножает все компоненты (`CalculateInitialAttackDamage`); в `DamageContext` компоненты переезжают через `Calculations.ComposeAttackDamage` — единственная точка для всех 4 копий ReceiveAttack. `AdditionalDamage` удалён. `FinalDamage` = фактически нанесённый урон ПОСЛЕ хита (лич/сплеш/DoT-та читают его).
- **Митигация** (`Calculations.MitigateComponent` — единственное место правил по типам): Fire/Cold/Lightning → резист × (1 − пенетрация источника: `*ResistancePenetration`, агрегат `AllResistancePenetration`, кап 0..1); Physical и **Bleed** → броня с `ArmorPenetration`; **Burning** → огненный резист, **Poison** → ядовитый резист, оба с пенетрацией и оба МИМО флага `IgnoreResistances` (это атакующая метка, а тик ДоТа — не атака: пара яда лежит вне `s_resistanceByType` именно поэтому); **Sacred** и **Blight** не митигируются. Агрегаты `AllResistance`/`AllResistancePenetration` включают яд. Пер-статусные ручки предметов: `Burning/Poison/BleedDamageTakenReduction` (маска в общем `DotDamageTakenReductionContextModifier`).
- CombatEventBus внутрення шина сущности. Необходима для работы внутренних систем сущности. Создается и умирает вместе с сущностью
- BattleEventBus внешняя боевая шина. Служит для комуникации между системами в рамках боя. Создается в начале боя, удаляется в конце.
- IAbilityBookComponent место обработки конкретных активных способностей сущности.
- Система улучшений активных способностей: Комбинированный подход из нескольких паттернов. Численные значения меняются при помощи декораторов. Логические выносятся в стратегии/отдельные небольшие модули. 
- Активные способности: Комплексная система. Жизненный цикл Данные(json. Сейчас локально, потенциально получаемый от сервера) => Провайдер (Создание через фабрики) => Инстанция => Владалец. Каст AbilityExecute - Единая точка для всех путей активации. 
AbilityActivationContext меняется активационными мутаторами: Ability-scoped => Entity-scoped.
- ExecuteInternal - Delivery. 
- Delivery: 1. Attacks - настоящие атаки. Для каждой создаается AttackContext через scheduler и проходит полный пайплайн обработки атак. 2. HitSequence - прямые хиты. Стратегия IHitSequenceStrategy отдает последовательность фактических касаний. 3. MulticastAbility<TPlan>: база способностей стойки интеллекта. Гарантирует бросок стадии и кумулятивный цикл. План - Generic-параметр живущий ровно один каст. Формы планов: CastPlanVolley - общий залп/крит в MulticastAbilityVoley, ChainPlan, AegisPlan, OverloadPlan.
- Riders - единый контракт вторичных эффектов: 1. IActivationRider - единожды на каст. 2. IImpactRider - на каждый импакт доставки. **Импакт несёт `required Source` (инстанция породившей способности — канал к её декорированным числам) и `required ImpactKind` — пять родов: `Attack` (пайплайн атак), `Hit` (прямое касание, включая отскоки IHitSequenceStrategy и доставку без урона), `Projectile` (снаряд залпа), `ChainJump` (прыжок цепи со своим falloff/счётом), `Splash` (вторичный урон, разлитый другим импактом). Род ставится в точке доставки и ниже не исправляется; забытая точка — ошибка компиляции, а не молчание.**
- Апгрейды (три рычага, комбинируемые): 1. Числа - декораторы: SimpleAbilityParameterDecorator поверх единого AbilityParameterSet (Core/Battle/Abilities; строковые ключи-константы: общие в AbilityParameter, свои — nested static class Parameters способности; регистрация значений в RegisterBaseParameters, каждый ключ автоматически = плейсхолдер описания). 2. Логика - подмена стратегий/фабрики. 3. Riders. Добавление: generic обертки AbilityUpgradeImpactRider, AbilityUpgradeCastEffect. 4. Апгрейд может ОДОЛЖИТЬ способности базовое значение параметра (`AbilityParameterSet.TryRegister` при установке, возврат при снятии; база уходит с последним одолжившим) — так податель делает транзитивность возможной на способности, не знавшей понятия.
- Воспроизведение боя (replay-модель): логика резолвит ход МГНОВЕННО, события пишутся в BattleTimeline (catch-all с per-entity CombatEvents). **BattleDirector** — единственное место «как событие выглядит»: проигрывает записи «битами» с реальным темпом и в момент показа РЕПУБЛИКУЕТ событие в BattleEventBus — весь UI (бары, цифры, лог) реагирует на показ, не на резолв. Событие без хендлера скипается молча; новый визуал = один хендлер в CreateBeatHandlers. Аккорды: события одного каста группируются по `CastId` (штампуется на DamageContext'ы) и играют единой фразой; смерть режет биты мертвеца; турн-луп ждёт `WaitUntilIdleAsync` (гейт хода). UI НИКОГДА не читает живое состояние — только снапшоты из событий (VitalsSnapshot).
- Анимации бойцов: AnimationsComponent поверх AnimatedSprite2D сущности. Клипы по конвенции имён: `Fight_Attack`/`Fight_Hurt`/`Dead`/`Stunned`/`Idle_*` + каст-позы `Ability_<Id>` (PlaceholderFrames.tres). `PlayAnimationAsync`: нет клипа → пауза 0.5с; зацикленный клип → ждём расчётную длительность (кадры/FPS), НЕ animation_finished (иначе подвес).
- VFX способностей: цепочка каста = поза кастера ∥ CastClip (эффект активации на споте кастера, параллельно позе) → полёт/аура → импакт → hurt. VFX-стадии — данные: `AbilityVisualConfig` (Delivery: None/Projectile/Chain/InstantOnTarget/SelfAura; CastClip/TravelClip/ImpactClip — пустой клип = стадия пропускается) в `AbilityVisualLibrary` (.tres, назначен арене), исполняет `AbilityVfxPresenter` (спавн AnimatedSprite2D, полёт твином между спотами). Chain играет хиты последовательно в порядке записи; касты без прямого урона берут цели VFX из EffectAppliedEvent аккорда. Серии атак: атаки штампуют `SourceAbilityId` на AttackContext→DamageContext — бит урона играет ImpactClip способности (полёт к атакам не применяется). Новая способность = клип в VfxFrames + конфиг в библиотеке, код не трогается.

## AI NPC (Core/Ai — чистый C#, Godot только адаптеры)
- Боевой AI: `UtilityTurnPlanner` играет ход NPC (скоринг способностей → касты → базовая атака) через `ICombatEnvironment` (реализует BattleArena). Поведение = `BehaviorProfile` из `NpcBehavior.json` (архетип жёстко от стойки: Dex=агрессия, Str=защита, Int=смешанный), интеллект — явное поле `AiIntellect`.
- Мировой AI: `WorldBrain` (Stateless FSM Calm/Suspicious/Alert/Search) + активности Idle/Wander/Patrol; тело за `IWorldAgent` (BaseNpc: движение прямой, зрение поллингом игрока). Стимулы (`WorldStimulusEvent`) через GameEventBus. Бой стартует физическим контактом.
- Данные NPC: `Npc.json` → `NpcProvider` → `NpcDefinition` → `BaseNpc.ApplyDefinition` (статы/стойка/способности/мозг/lifecycle). EntityType задаёт макс. уровень и число способностей (Regular=Обычный 15 … Archon 150; Boss/Archon вручную).
- Цикл нежити: `NpcLifecycle` — тело после смерти лежит в мире; не-нежить восстаёт нежитью по таймеру (сильнее ∝ времени), нежить в анабиозе; сжигание кликом = финальная смерть (`NpcFinalDeathEvent`).
- Спавн: `NpcSpawnPoint` (лимиты точки, респавн замены по событиям) + `NpcPopulationService` (глобальный лимит живых NPC).
- **Мирные жители (2026-08-08)**: у циклов жизни общий контракт `INpcLifecycle` + два суб-интерфейса исходов подъёма — `IUndeadRiseLifecycle` (`ResurrectionReady(float)`, нежить, сила ∝ пролёжанному) и `IAliveRiseLifecycle` (`ReviveReady`, встал живым). Подписка на исход, которого у цикла нет, НЕ КОМПИЛИРУЕТСЯ — это несущее различие, не менять на флаги. `VillagerLifecycle`: сбит → лежит → по таймеру встаёт ЖИВЫМ (та же фракция, без бонусов/тинта, БЕЗ событий — слот спавн-точки занят, личная репутация игрока переживает нокдаун); не горит, финальной смерти нет; любая лежачая стадия из сейва = «лежит и восстановится» (вечный труп запрещён). Цикл строится ТОЛЬКО `NpcLifecycleFactory.Create(definition, rnd)` — switch в одном тестируемом месте, обе копии `BaseNpc` зовут фабрику. Выбор — данными: `lifecycle.kind: "Villager"` (+`recoverMin/MaxSeconds`; отсутствие kind = цикл нежити, опечатка = отказ записи). Сейв: `RestoreAsRisen` только для `IUndeadRiseLifecycle` — старый сейв не поднимет жителя нежитью.
- **Авторский именованный спавн**: секция `authored` в записи Npc.json (`stance`/`level`/`rarity`/`modifierCount` — все опциональны, названное заменяет свой ролл; `modifierCount: 0` = модификаторы не роллятся, отрицательное = 0). Приоритет: рантайм-overrides > authored > старые поля (`rarity`, одна стойка, `levelMin==levelMax`) > ролл; архетип следует за авторской стойкой. Состав модификаторов и пик способностей НЕ фиксируются (сейв перекатывает). Фиксированная позиция = спавн-точка radius 0 / max 1.
- **Сейв дикого живого NPC (`npcWorld` v2, 2026-08-09)**: NPC, поставленный в мир квестом (`SpawnNpcAction`), не принадлежит НИ ОДНОЙ точке — точка одолжила координаты и его не перекатывает, поэтому секция пишет его как запись `kind: "alive"`. Дикость — факт носителя (`IFightableNpc.IsWild` + `MarkAsWild()`, обе копии `BaseNpc`) И факт записи (поле `wild`): восстановление зовёт `MarkAsWild()` только по полю, иначе тело точки вернулось бы «ничьим» и загрузочный дубль (тело из файла + резидент точки) закрепился бы навсегда вместо самолечения. У `alive`-записи набор модификаторов ПЕРЕЖИВАЕТ сейв — свой список id в записи, восстановление собирает `CreateDefinition(id, overrides) with { Modifiers = ... }`; тела (`defeated`/`dormant`/`risen`) перекатывают как раньше. Витал, пик способностей и InstanceId НЕ идентичность: раненая цель встаёт целой, способности перекатываются, личная репутация к телу забывается. Слот популяции — `ReserveOutsideLimit()` (как первый спавн: полный мир ставит точки на паузу, но цель испытания не теряется). Файл v1 читается: записей `alive` в нём нет, `wild` = false.
- **Активность Work**: `{activity: "Work", point: "Forge"|"TradeStall"}` в расписании — клейм smart-точки по тегу + рабочая поза (третья конфигурация `PointPoseActivity`, чувства не глушит, фактов не тикает); без точки — мягкая деградация «стоять дома». Образец полного дня — `Npc_Ronald` (кузня → прилавок → костёр → сон; торговец `Trader_Ronald` через диалоговое `StartTrade`).
- ВАЖНО: `BattleEndEvent` публикуется в ОБЕ шины (game — лут, battle — выход Player/NPC из Fight-состояний; публикует BattleContext).

## Система лута (LootGeneration)
- Пайплайн: `EntityDiedEvent` → `LootGenerationService.GenerateItemsAsync` (только `IFightableNpc`) → таблица через `GetLootTableRequest` → `SpendBudget` → `IItemCreationService` → `List<ItemStack>` → `LootOrchestrator` (презентация). Кэши (`_tableCache`/`_diedEntities`) чистятся по `BattleEndEvent`.
- **Бюджет** = `baseBudget(EntityType) × (1 + lvlCoef × f(Level)) × rarityMult(Rarity) × (1 + Σ difficulty модификаторов)`; f = √Level (Regular…Unique) или ln(Level+1) (Boss/Archon). Больше difficulty у NPC = больше и лучше лут — ядро мотивации игрока «кормить» NPC модификаторами.
- **Тиры** 0..3: 0 — лучший и самый дорогой. **Rarity**: меньше = лучше (Legendary=0 … Common=4); Unique=10/Mythic=11 — фиксированные шаблонные редкости, генерация их НЕ перекатывает (эксклюзивы, лежат в тире 0 по 420–650).
- `SpendBudget`: ролл тира по шансам (модификаторы двигают шансы через `Calculations.CalculateChances` с нормализацией и перетоком из низших тиров) → доступность тира по **минимальной фактической цене предмета** (не по конфигному прайсу) → недоступный тир падает в ближайший худший → предмет равномерно из доступных по цене. **Тир-апгрейд = бесплатный свап ПОСЛЕ покупки** (ролл платит цену исходного тира, difficulty модификатора уже оплатила разницу). Кап `maxItemsPerKill`; излишек бюджета конвертируется в качество (свап самого дешёвого выбранного на предмет лучшего тира) → потолок ценности ≈ кап × средняя цена t0. Guaranteed-предметы бесплатны и идут ПОВЕРХ капа. Холостые роллы ограничены (100) — пустые таблицы не вешают цикл. **Золото (2026-07-24)**: ФИНАЛЬНЫЙ остаток (после качества-свапа) чеканится в кучку `GoldItem` (`ICurrencyItem`, Core/Items): `goldPerBudgetUnit` (4) × остаток, кламп `maxGoldPerKill` (300, анти-джекпот: без него перекормленный архонт чеканил 46к при закупе торговца ~500). Кучка едет обычным дроп-каналом (`ItemOnGround`), подбор кладёт в КОШЕЛЁК мимо сумки; сим-метрика Gold/kill в отчёте, инвариант `GoldDrop_RespectsCapAndPaysWeakKills` (кап держится + слабые киллы платят). Лут-у.е. ≠ золото — курс только в этой точке.
- **Статы предметов**: множитель `1 + itemModifierMultiplier × Σ difficulty`; масштаб ЛИНЕЙНЫЙ для всех типов модификаторов (flat/inc/multi в данных — дельты, суммируются на базу 1). Пул-шаблоны предметов никогда не мутируются — только свежие инстанции (`ModifiersCreator`), композиты разворачиваются со скейлом каждой части.

Таблицы: `SharedData/LootTables` — секции general(basic)/fractions/types/individual, объединяются юнионом по номеру тира (поиск по полю `tier`, не по индексу).
- NPC-модификаторы: `SharedData/NpcModifiers/NpcModifiers.json` → DTO `Core/Data/NpcModifiersData` (маппинг `JsonProperty` ↔ json уже один раз молча умирал — `tierUpgradeChance`; сим-тест держит пол доли тира 0). `ScaleModifier` усиливает остальные модификаторы NPC.

Effect-грант ре-аплаится на каждый `BattleInitializedEvent` (эффекты чистятся в конце боя).
- Лут-канал грантов (2026-07-19): экип-дроп роллит бонус-грант из каталога `SharedData/ItemEffects/ItemEffects.json`. NPC с `ItemEffectsModifier` (секция itemEffects в NpcModifiers.json) даёт ГАРАНТИРОВАННЫЙ грант на каждый экип-предмет килла (пул = сигнатурные id NPC, вес из каталога); обычный килл роллит `equipItemEffectChance` (конфиг, 0.15) по всему каталогу. Unique/Mythic не трогаются; ролл ПОСЛЕ аффикс-строк. Каталог — общий `CraftingEffectProvider` (Core/Crafting) с крафт-каналом 4; id без записи в каталоге = Tracker + отказ (payload обязателен). Хардкодный `IItemEffectProvider` удалён.

## Система крафта (Crafting/Source; домен и UI переписаны 2026-07-11, фаза 3 закрыта 2026-07-16)
- **Четыре команды через шину** (Request>Response), всё остальное — прямые сервисы: `CreateEquipItemRequest` (создание по рецепту), `UpgradeEquipItemRequest` (заточка), `RecraftEquipItemModifierRequest` (реролл модификатора), `AscendEquipItemRequest` (возвышение). Хендлеры — единственные ворота операций: UI-кнопки лишь зеркалят доступность.
- **`CraftingResources`** — check-then-spend (всё-или-ничего) для любых списаний. Порядок в хендлерах: валидация (мастерство/кап/наличие) → списание → операция → опыт. Провал заточки платит и учит (осознанно); кап/нехватка/невозможный реролл не стоят ничего (`ItemUpgradeResult.NotEnoughResources`).
- **Создание**: рецепт (строгие ресурсы и/или категорийные-по-тегу) + до 3 опциональных добавок; пул роллов = family∪item∪дескрипторы ВСЕХ использованных ресурсов, значения × качество мастерства (пишется в `PowerMultiplier`), редкость роллится каналом 3 (руны создания дают пол). Предмет запоминает `UsedRequiredResources`/`UsedOptionalResources`.
- **Пул реролла — живой (2026-07-16)**: вычисляется В МОМЕНТ перековки = family-пул категории ∪ собственный пул базы ∪ дескрипторы `UsedResources` (у лута пусто) ∪ пулы добавок операции; весь union скейлится `PowerMultiplier` предмета (лут пишет difficulty-множитель при дропе, крафт — качество мастерства при создании; поле сейвится, легаси → 1). Лут перековывается наравне с крафтом; правка пула в json видна на уже существующих предметах. Реролл слот-сохраняющий (кандидаты фильтруются по аффиксу целевой строки), группа композита снимается целиком → взамен один атом ИЛИ целый композит (2026-07-26: композиты — полноценные кандидаты с весом корня, ложатся группой со свежим GroupId; дедуп — по LineIdentity, см. «Без дублей строк»), пустые кандидаты → отказ без списания. Сборка union'ов — только `EquipItemPoolExtensions` (Core).
- **Без дублей строк (2026-07-20; реворк на LineIdentity 2026-07-26)**: идентичность player-facing строки — `LineIdentity` (Core/Modifiers): атом = синглтон-`ModifierKey` (канал + параметр + тип значения, НИКОГДА значение: «+35% урона» и «+33% урона» — одна строка), композит = отсортированное МУЛЬТИМНОЖЕСТВО ключей частей (тот же набор = та же строка, диапазоны/веса не в идентичности — тир-записи из разных источников конкурируют как атомы; композит-одиночка из одной части ≡ атому — решение Todd), грант/операция идентичности не имеют (не строки, в роллы замен не входят — в т.ч. композит с грант-частью). Один инвариант в трёх точках: `AffixRoller` (рождение — слот за слотом, занятые идентичности выбывают, веса пересчитываются), `ItemUpgrader.TryRecraftModifier` (кандидаты с занятой идентичностью выбрасываются) и зеркало приглушения в CraftingWindow. Занятые идентичности считает `IEquipItem.OccupiedLineIdentities` ДО снятия строки (атомы + свёртка групп по GroupId; исключённый instanceId снимает ВСЮ свою группу) — отказ ничего не мутирует и не стоит. Вне подсчёта осознанно: имплициты (авторская строка базы не ест пул) и сама перекатываемая строка/группа (тот же стат/композит с новыми значениями легален). Части многочастного композита не блокируют атомы и не блокируются ими — дубль только при полном совпадении набора. Будущие условные модификаторы встраиваются идентичностью «ключ + условие» без правки роллов.
- **Слот строки держится (2026-07-20)**: реролл вставляет свежую строку на индекс снятой (`IEquipItem.InsertAdditionalModifier/InsertAdditionalContextModifier`; `Add*` = вставка в конец, весь путь один). Индексы читаются ДО удаления группы (по первому члену в СВОЁМ канале; строка, родившаяся в другом канале, приписывается в конец). Строка не падает вниз списка после переката.
- **Блоки строк в UI (2026-07-20)**: `EquipItemLines.ComposeRolled` отдаёт строки уже в порядке показа — префиксы → суффиксы → безаффиксный хвост (легаси-сейвы) → мифик-подарок; сортировка стабильна, внутри блока порядок предмета. `EquipItemLine.Affix` — семья строки (у композита — штамп корня на частях). Заголовки блоков — единая точка `Core/Views/UI/ItemLineRows.AffixHeader` (у безаффиксного хвоста заголовка нет); тултип рисует подарок карточкой в рамке цвета Mythic вместо заголовка, окно крафта — обычной строкой под заголовком. **`AffixKind.Mythic` — СОБСТВЕННАЯ семья слота**: мифический модификатор обособлен и не входит в счёт префиксов/суффиксов предмета, поэтому записи мифик-пулов помечены `"affix": "Mythic"` прямо в данных. `ItemAscender` тянет из пула ЦЕЛИКОМ (никакого броска префикс/суффикс — тянуть не из чего) и штампует Mythic на выданное как страховку от забытого маркера; `AffixRoller` мифик-записи в обычный ролл не пускает (инфо, не ошибка). Едет в сейве по обычному полю `Affix`. Легаси-мифики из старых сейвов штампа не получат — их подарок останется в общем блоке.
- **`ItemUpgrader`**: шанс заточки = кривая P0=0.95…P12=0.01 (константы в коде) × (1 + бонус мастерства 0–200%) + Σ флюсов, кламп 0..1 — ОДНА формула (приватный `ComputeUpgradeChance`), её же отдаёт `GetUpgradeChance(item, resources)` для UI-полосы. Стоимости — `SharedData/UpgradeCosts/UpgradeCosts.json`: схема с редкостью (`byRarity` на записи требования = оверрайды id/amount per-rarity, дефолты — поля записи; битая запись = Tracker + скип всей строки). Руны заточки 1/1/2/3/4 из данных; перековка = пыль категории + основной ресурс по категории×редкости (руды для Weapon/Armor, самоцветы для Jewellery), цена ×(1+0.1×RecraftCount) с ceil — считает `GetRecraftResourceCost(item)`, растёт только с СОСТОЯВШИМСЯ рероллом. **`ItemAscender` (эталон, 2026-07-16)**: гейт мастерства 35 (`ascensionLevelGate` в CraftingMastery.json, бонус-уровни считаются) + Legendary + полная заточка; порядок ДО печати: +15% ко всему (`ascensionStatBonus` → `AscensionMultiplier` на предмете: Value = Base × UpdateMultiplier × AscensionMultiplier, оба канала; properties/значения грантов ×1.15 ОДНОРАЗОВО) → мифик-гифт (шанс `mythicGiftBaseChance` 0.15 × (1 + канал мастерства), пул по КАТЕГОРИИ: `Mythic_Weapon`/`Mythic_Jewellery`/`Mythic_Armor`) → Mythic + печать. «+1..69 уровней заточки» НЕ гарантирован — это одна из записей гифт-пула (`extraUpgradeLevels` в записи, есть у всех трёх клейм; `UpgradeLevelsDescriptor` — операция, не строка: кап += ролл + штатный Upgrade, материализатор такую запись громко отвергает — в обычные пулы ей нельзя). Цена = 1 клеймо категории (`Upgrade_Resource_*_Mark`, Mythic, лут general т0 по 630–650). `AscensionMultiplier` сейвится (легаси → 1). Всережущий (Weapon_All_Cutting): «1–69 заточки» — ВРОЖДЁННЫЙ эффект (data-born мифик, `updateLevel: {min,max}` → Minter фиксирует UpdateLevel==Max==ролл), строк нет, точить/рероллить нечего (тултип-кнопки прячутся по капу/пустоте).
- **Мастерство (реворк 2026-07-16)**: `SharedData/CraftingMastery/CraftingMastery.json` — уровни 0–50, шесть бонус-каналов эталона (шанс заточки 0–200%, значения 0–150% БЕЗ штрафа внизу, редкость 0–150%, доп. эффект 0–150%, мифик-модификатор 0–100% — потребляется возвышением через `GetMythicGiftChance()`, возврат ресурсов), кривая и награды опыта. Прогресс = (уровень+бонус)/50, линейный лерп каналов. Каждый уровень заточки предмета = +5% к значениям строк (эталон; константа в EquipItem).
- **Доп. эффект при создании (канал 4, подключён 2026-07-16)**: скрафченный предмет с шансом `extraEffectBaseChance` (0.1) × (1 + бонус канала) роллит ОДИН бонус-грант из каталога `SharedData/ItemEffects/ItemEffects.json` (`ICraftingEffectProvider`; записи id+kind+weight+properties — payload едет с записью, строгие скилл-фабрики без properties грант не соберут; кривой kind/пустой id = Tracker + скип). Только крафт; лутовые эффекты (IItemEffectProvider) — отдельный недоведённый пайплайн.
- **Добавки** (`ICraftingAdditiveProvider`, каталог `SharedData/CraftingAdditives`): опциональные ресурсы — флюсы `upgradeChanceBonus` (+3/6/9/15% к шансу заточки), руны создания `minRarity` (пол редкости Uncommon…Legendary, из слотов берётся ЛУЧШИЙ), `extraUpgradeLevelChance` (второй уровень при успехе), `recraftPoolId` (временный пул НА ОДНУ операцию). Хендлеры передают ВСЕ ресурсы запроса в апгрейдер — не-добавки просто не дают эффектов. Новая эссенция = запись в json, код не трогается.
- **Разбор** (`DestroyItemMessage`): запечатанное не разбирается (хендлер — гейт); возврат `UsedResources` × канал 6 мастерства + пыль категории floor(1×(1+сырой бонус канала)) — маппинг категория→пыль зашит в хендлере осознанно; опыт Shatter.
- **Опыт**: `GainCraftingExpirienceMessage(mode, rarity)` → хендлер → `ICraftingMastery.GetExperienceReward(mode, rarity)`; все цифры (по редкости × фактор режима) — в CraftingMastery.json.
- **UI**: одно окно `CraftingWindow` (все 4 режима; `SetItem(item, mode)` или выбор рецепта в дереве) — дерево категорий с поиском и счётчиком «(N)», строки требований кодом, категорийное требование = тег ресурса (выбор через встроенный пикер), 3 слота добавок (блок скрыт, пока каталог пуст), полоса шанса заточки в action-баре (Upgrade-режим, live: пересчёт при выборе/снятии флюсов и после каждой попытки; кап-предмет — полоса скрыта; ключ `UI_Craft_Success_Chance`, формула — `GetUpgradeChance`). Вход: `OpenCraftingWindowMessage(id, isItem, mode)`; тултип-кнопки предмета (`InventorySlotTooltipButtons`): Update/Recraft/Ascend шлют соответствующий режим — видимость по `EquipItemCraftActions` (Core: Recraft у любого незапечатанного, Ascend только Legendary; глубокий `CanAscend` — за окном/хендлером). Кнопки живут в PINNED-состоянии `ItemTooltipPopup` (2026-07-16): пин (Alt) добавляет ряд действий для предметов ИЗ СУМКИ (надетые резолвятся null → без кнопок, сначала снять); попап при пине открывает mouse-фильтры (в ховере — Ignore).

## Система торговли (Core/Trade + Main/Trade; 2026-07-24, окно ждёт сцену)
- **Деньги**: `IWalletService` — кошелёк-счётчик (НЕ предмет; сейв-секция `wallet` v1, session reset к `startingGold`). Золото входит в мир кучкой `GoldItem` (`ICurrencyItem`) из остатка лут-бюджета (см. «Система лута»); подбор кладёт в кошелёк мимо сумки.
- **Цена = оценщик инстанции** `ItemValuation` (единственная точка золотых цен): `basePrice(блюпринт/предмет) × редкость × (1 + 0.1×заточка) × возвышение`; без basePrice предмет неторгуем (0). Множители — `SharedData/Trade/TradeConfiguration.json`. `TradePricing` поверх: покупка ×(1+`Perk_Price_Change` фракции торговца), продажа ×buyback(0.4)×(1−перк). ЛУТ-у.е. ≠ золото.
- **Торговцы**: `SharedData/Traders/Traders.json` → `TraderProvider` → `TraderService` — гибрид-полка (авторский каталог id+count+chance с шансом появления на рестоке + случайные экип-слоты через настоящий минтер; уники/мифики не роллятся), ленивый рестока по игровым минутам, `TakeMany` all-or-nothing. **Buyback**: проданное ждёт на полке торговца по ЗАРАБОТАННОЙ цене (кап 12, FIFO; переживает рестока, умирает с сессией). Полка НЕ сейвится (осознанный пробел до анти-сейвскам-прохода).
- **Операции через шину** (ворота — хендлеры, UI зеркалит): `BuyItemRequest(trader, offer, amount)` — кошелёк check-then-spend, полная сумка откатывает; `SellItemRequest(trader, instance, amount)` — стак продаётся до фактического наличия, экип уходит целиком в buyback. Вход: `OpenTradeWindowMessage(traderId)` ← диалог-действие `StartTrade` (json: `{type: "StartTrade", traderId}`; вешать на узел, ЗАВЕРШАЮЩИЙ диалог) и консоль `trade [traderId]`.
- **Все регистрации — Main** (модульная дисциплина): `RegisterTradeServices` в GameServiceProvider. `TradeWindow` разрешён в World|Dialogue (исключение из карты — окно должно пережить флип контекста закрывающегося диалога). Сцена TradeWindow.tscn — за Todd (uid вписать в константу окна).

## Система репутации (Core/Reputation + Core/Ai/World/Raids; сделано, awaiting Godot-теста)
- **Очки, не уровни**: int per-фракция −6000..6000, `RelationLevel` — производный от порогов из `SharedData/Factions/FactionRelations.json` (Hatred −6000 / Hostility −2000 / Dislike −800 / Neutral −200 / Friendly 1000 / Respect 3000 / Alliance 5000; смена уровня с гистерезисом 50 — уровень хранится как состояние). Дефолты: Undead −1000 (Hostility — атака on sight сохранена), Human 500, остальные 0. Флаги фракций: `hasReputation` (Animal/MysticalCreature false — реп заморожена, свидетелями не являются), `canRaid`. Матрица фракция-vs-фракция СТАТИЧНА — динамичен только слой игрока.
- **`IFactionRelationService`** (единственная реализация в `Core/Reputation`): `AddReputation(faction, delta, reason)` — единственный игровой путь; `SetPlayerRelation(level)` = прыжок в середину диапазона уровня (квесты/миграция); события `PlayerReputationChanged`/`PlayerRelationChanged` (только пересечения порогов). ВАЖНО: пустой ctor нужен DI (данные приходят через Apply), ctor с данными — тестовый.
- **Деяния**: `ReputationDeedProcessor` — единственное место превращения поступков в репутацию; каталог `SharedData/ReputationDeeds/ReputationDeeds.json` (дельта; `noPenaltyAtOrBelow` — анти-death-spiral пол: убийство уже-враждебных бесплатно; `hostileToTargetBonus` — плюс врагам жертвы по матрице; `personal`; `requiresWitness`; `repeatDecay` — сессионное затухание против фермы). Убийства выводятся из `EntityDiedEvent.Killer` (= последний источник урона из TakeDamage; `DefeatInWorld`/`Kill()` обнуляют — скирмиши не винят игрока); остальные системы публикуют `PlayerDeedEvent(deedId, faction, instanceId?, position)`. Всё глушится при `ILoadScope.IsLoading`.
- **Свидетели (уровень 0)**: `IWitnessQuery`/`WorldWitnessQuery` — живой не-сражающийся NPC реп-фракции в `witnessRadius` ИЛИ сбежавший из текущего боя (гарантированный свидетель до BattleEndEvent; `EntityFledBattleEvent` теперь публикуется и в game bus). Якорь радиуса — мировая точка боя из `BattleInitializedEvent` (в бою Position бойцов = спот арены!). Нет свидетелей → деяние с `requiresWitness` не произошло вовсе (ни штрафа, ни бонусов, decay не сжигается).
- **Личный слой**: `IPersonalReputationService` — очки per-NPC (InstanceId), секция `personalReputation` в FactionRelations.json (±1000, 300 очков = 1 ступень лестницы, кап ±2). ## Аугменты и сокеты (Core/Battle/Abilities; 2026-08-04…08, заменили бесплатный выбор апгрейда)
- **Улучшение способности — ПРЕДМЕТ.** Запись каталога (`AbilityUpgradeData`) + роллённая копия (`AugmentInstance`: id записи и словарь чисел, ±25% вокруг базы, спред в `CombatRules.json`) + предмет сумки (`AugmentItem : IAugmentItem`, `MaxStackSize = 1`). Копия минтится `AugmentMinter`/`AugmentItemMinter`; выпадает через обычные столы лута, покупается, конвертируется 3→1 в рамках тира и редкости (`ConvertAugmentsRequest`, роллится заново).
- **Подгонка — ОДНО МЕСТО**, `AugmentFit.Check`: тир (сокет тира N берёт запись тира ≤ N) → привязка (`abilityId` решает один, иначе пересечение тегов `SharesAny`, `OrdinalIgnoreCase`; `fitsAnyAbility` — универсальный) → группа исключения. Интерфейс НЕ ИМЕЕТ ПРАВА мерить тиры и теги сам: два прочтения одного правила — два ответа. Тег обещает подгонку, а не работу (аугмент может подойти и ничего не делать).
- **Доска сокетов** `IAbilitySocketBoard` — слот адресуется строкой `socketId|abilityId|tier`, а не id узла. Набор слотов даёт аллокация дерева (`Sync`), содержимое — её собственность (сейвится). **Слот с аугментом переживает потерю своего узла**: закрывается и пускает только наружу («только вынуть»), пустой исчезает. Респек не уничтожает имущество игрока.
- **Ворота — хендлеры, интерфейс зеркалит**: `InstallAugmentRequest`/`ExtractAugmentRequest` через шину, `IAugmentInstallGate` — единственная точка посадки (сумка → есть ли слот → закрыт → занят → правило). Извлечение кладёт в сумку ДО того, как слот отпустит копию: числа роллятся один раз и восстановлению не подлежат.
- **Способность носит ровно то, что стоит в её сокетах** — `IAbilityAugmentBinder.Bind()`, тотальная пересборка (снос и сборка целиком), не инкрементальная. Зовут её ПЯТЬ дорог: посадка, извлечение, `Reconcile` (Sync/аллокация/смена игрока), загрузка сейва, сессионный сброс. Числа берутся у КОПИИ (`AbilityProvider.CreateUpgrade(AugmentInstance)` → `instance.Applied(record)`), не у записи.
- **Соперничество (2026-08-07)**: два аугмента с ОДНИМ ЭФФЕКТОМ не складываются — работает сильнейший, проигравший остаётся в слоте спящим и оживает при извлечении победителя. Идентичность эффекта — `AbilityEffectIdentity` (параметр + направление, НИКОГДА величина; родня `LineIdentity` из крафта). Сравнение настоящее: оба применяются к недекорированной базе, дальше от базы = сильнее. Решается НА ЧТЕНИИ (`AbilityParameterSet.GetValue`), поэтому от порядка посадки не зависит. **Цена — исключение**: у ухудшающих движений (`AbilityParameter.CastPrices` = Cooldown, CostValue) в идентичность входит id записи, иначе игрок получал бы скидку за то, что надел больше платных аугментов. **Пол перезарядки**: долевые срезы кулдауна не опускают его ниже 1 (`AbilityParameter.MinimumCooldown`) — аугмент продаёт короткую перезарядку, а не её отсутствие; нулевой базы пол не касается (мгновенный каст остаётся мгновенным), плоские срезы авторских апгрейдов проходят мимо пола осознанно.
- **Орнаменты — четвёртый сокет (2026-08-17)**: предмет (`OrnamentItem`, каталог `SharedData/Ornaments`, по одному на тир, источник — только квесты линейки испытаний), надетый на способность, даёт ей **+1 сокет своего тира**; **один орнамент на способность** → максимум 4 аугмента (2 одного тира + по 1 остальных). Владелец состояния — доска (`AbilityOrnament` = ornamentId|abilityId|tier; socketId сокета = id орнамента, адрес обычный): `Sync` объединяет сокеты аллокации с орнаментными, поэтому **респек орнамент не трогает**, а инвариант «один на способность» стоит на доске и обязателен для всех дорог, включая загрузку. Снятие — **только при пустом сокете** (`remove-only`, как у слота без узла: иначе аугмент переехал бы на способность с другими тегами); отсюда следствие — посадка/снятие орнамента НЕ меняет носимое, и `Bind()` на этих дорогах не зовётся. Ворота — `IOrnamentAttachGate` + `AttachOrnamentRequest`/`DetachOrnamentRequest`; единственный гейт по дизайну — способность открыта (открытый сокет того же тира НЕ требуется). Числа орнамент не роллит, поэтому сумочная копия при снятии **чеканится заново**.
- Сейв: секция `abilityBook` **v7**, `sockets` — список записей с адресом, роллёнными числами и подписью слота; `ornaments` — пары «орнамент↔способность» (тир НЕ пишется, берётся из каталога), едут ОДНИМ вызовом `Restore` вместе с посадками (половина восстановленной раскладки = потерянный четвёртый сокет; сам порядок внутри вызова не несущий — закрытый слот, поднятый записью, переоткрывается посадкой орнамента). **Отвергнутая запись НЕ теряется** (надетый орнамент не лежит в сумке, а выдаётся одним неповторяемым квестом ⇒ потеря перманентна): доска ВОЗВРАЩАЕТ вытесненные орнаменты вызывающему, участник чеканит их в сумку; если чеканить нечем (запись id пропала) или в сумке нет места — запись переносится в СЛЕДУЮЩИЙ сейв как есть (`_unplaceable`, чистится каждым ресторе и `RestoreWithoutSection`, чтобы не течь в новую игру). Исключение — файл, назвавший ОДИН орнамент дважды: он уже на способности, возврат сделал бы второй экземпляр уникума ⇒ дубль громко отбрасывается. **секции `upgrades` больше нет** (описывала бесплатный выбор). Старые версии читаются от 4-й (файл до 7-й = орнаментов нет), отброшенные выборы называются в Tracker.

## Пассивное дерево в игре (Core/PassiveTree + Battle/Source/UIElements/PassiveWheel; 2026-08-08)
- **Аллокация** `IPassiveTreeService` поверх `AllocationState` (чистый C#): `CheckTake` отвечает с причиной без покупки, `Take`/`Refund`/`TakePath`/`Respec`/`RestoreState`, `CheckRefundSet`/`RefundSet`. Очко стоит узел, у которого `NodeKindRules.CostsPoint` — единственное место этого правила. Очки приходят снаружи из мастерства (`MartialArtMastery` → `SetTotalPoints`), бюджет из разметки в проверках НЕ участвует.
- **План покупки — ПРОЕКЦИЯ, а не список намерений.** `PassiveTreeDraft` держит `AllocationState`, равный тому, чем аллокация СТАНЕТ: взятое ∪ отмеченное (режим Take) либо взятое \ отмеченное (Refund). Отсюда даром: сироты всплывают сами, узел за отмеченным просто достижим, цена пути не считает оплаченные ступеньки дважды. Драфт создаёт ОКНО, в DI не идёт, источников модификаторов и участников сейва не имеет — отмеченный узел физически нельзя спутать с купленным. Возврат берёт узел вместе с ветвью за ним, цена названа ДО клика.
- **Респек стоит золота** (`IPassiveRespecPricing` + `SharedData/PassiveTreeRules`, цена за узел растёт с уровнем мастерства), списание всё-или-ничего через `RespecPassiveNodesRequest`. Показанная цена и списанная считаются одним прайсингом.
- **Отрисовка режется по частоте изменения, а не по типу узла**: подложка и тусклые рёбра (перерисовка на зум), взятые рёбра (на аллокацию), масса рядовых узлов слоем, «важные» и отмеченные — сценами `PassiveNodeView` из пула, курсорный слой (ховер, фронтир, метки плана, пунктир), кольца сокетов, слой эффектов. Всё лежит в документных координатах внутри рамы `Node2D`: панорама — одна запись поля, ноль перерисовок. Экранные полы (ширина ребра, радиус узла) выражены в документных единицах, делённых на зум.
- **Попадание считается ОДНО, на родителе**, по ближайшему центру (`NodeGeometry`); узлы-виды — чистая презентация с `MouseFilter.Ignore`. Движковый пикинг по Control не используется: в авторской разметке полторы сотни пар фигур перекрываются, а Godot решает такие случаи порядком в дереве сцены, то есть порядком строк в json.
- **`spread`** — авторское решение о раскладке, живёт в документе рядом с `budget`, пишется инструментом разметки, читается игрой. Разброс входит и в раму, и в попадание одновременно; на значении по умолчанию (1) поле в файл не пишется.
- Подписей на колесе нет вовсе — ни имён узлов, ни названий секторов; имя живёт в попапе. Выделения узла нет: клик отмечает. Ховер красит кромку узла, а не рисует кольцо вокруг.
- **Общее с инструментом разметки** (`src/PassiveTreeEditor`, ВНЕ решения игры, заморожен): `CanvasTransform`, `NodeGeometry`, `NodeSpatialIndex`, `AllocationState`, `PassiveTreeSummary` — в `Core`, инструмент ссылается файлами-алиасами. Внешний вид у игры СВОЙ: `CanvasStyle` инструмента не переезжает.
- **Окно мастерства** (`MartialArtMasteryWindow`) показывает только ИМЕЮЩИЕСЯ способности сплошным списком по стойкам, вместе со слотами; `AbilitySocketPanel` — самостоятельный элемент, встраиваемый и им, и будущими окнами.

## Данные
- Исходные игровые данные расписаны в json (предметы, активные способности, пулы модификаторов для предметов и т.д). Загрузка — единый слой `Core/Data/GameData` (зеркало системы сейвов): провайдер = `IGameDataParticipant` (декларирует каталоги-подпапки Data и парсит файлы в `Apply`), `GameDataService.LoadAll()` вызывается ОДИН раз в бутстрапе проекта (`AddGameData(root)` + участники через `AddGameDataParticipant<TService, TImpl>`); источник (res:// / файловая система / потенциально сервер) — за `IGameDataSource`. Конструкторы провайдеров НЕ читают файлы.
- Enum'ы из json парсятся строго через `DataParse.ParseEnum` (опечатка = ошибка в Tracker, не молчаливый дефолт). Битый файл/каталог скипается с репортом, битый модификатор скипается на уровне записи.
- **Ручки мифических клейм (2026-07-20)**: 17 новых членов `ContextParameter` с биндингами — конверсия физического в стихию (`PhysicalToFire/Cold/Lightning`, по элементу на запись), `AttacksIgnoreResistances` (flag), добавленный стихийный от атак (`AddedFire/Cold/LightningDamage`), `AttackSacredConversion`, `CooldownResetChance`/`FreeCastChance` (роллят на `IAbilityActivationContext.Rnd`), `DotDamageBonus` (маска Bleed|Poison|Burning — «удвоение урона эффектов» и «Яд/Кровь/Горение +X%» это ОДНА ручка, две записи пула), `EffectDurationScale` (умножение длительности всех эффектов), четыре `DamageTakenReductionFrom*` по `DamageCause` и `DotDamageTakenReduction` (по компонентам урона). Урон-мутаторы гейтятся по владельцу, поэтому строятся в `Attach` (`DamageBinding`). Инвариант «у каждого члена есть биндинг» держит `ContextModifierBindingTests`.
- **Разрез пулов по категории экипировки (2026-07-24)**: у категорий материалов и ресурсов (`CraftingResources.json`) рядом с плоским `modifiers` («для всех») живёт опциональный `"byCategory": {"Weapon"/"Armor"/"Jewellery": [...]}` — записи секции штампуются `IModifierDescriptor.OnlyFor` и отсеиваются на СБОРКЕ пула (`EquipItemPoolExtensions.ForCategory`; создание — в хендлере, реролл — в `GetLiveRerollPool`), парс не фильтрует. `MaterialType.Modifiers` = база категории ∪ собственные (единственная точка объединения). Кривой ключ секции = Tracker + скип секции. Веса миграции 2026-07-24 — плейсхолдер 100, баланс-пасс позже.
- **Виды записей пула (2026-07-20)**: обычная строка (`parameter` + `modifierType` flat/inc/multi + `value`), композит (`parts`), операция `extraUpgradeLevels`, **флаг** (`"modifierType": "flag"` — переключатель без числа: значение приколочено к 1, не роллится и НЕ скейлится заточкой/возвышением; разрешён только для `ContextParameter`, на `EntityParameter` — Tracker + скип) и **грант** (`"grant": {kind, id, properties}` — поведение, которое строкой не выразить: чеканится через `IGrantFactory` в `sink.Grants` и ложится в раздел «Эффект» предмета, а не в строки). Реролл берёт кандидатами ТОЛЬКО строки (у них есть `ModifierKey`) — грант/операция в пуле реролла не съедят строку.
- Общие данные всех проектов лежат в `src/SharedData/<Каталог>` (единственная физическая копия) и подключены в каждый проект симлинком `Data/Shared` (Crafting: `Internal/Data/Shared`). Бутстрап передаёт два корня: `AddGameData("res://Data/", "res://Data/Shared/")`. Каталог целиком берётся из ПЕРВОГО корня, где найден: локальная папка-каталог с тем же именем полностью перекрывает общую (механизм оверрайда для экспериментов).
- Провайдеры являются источниками оригиналов; по необходимости создают новые инстанции (фабрики либо через вызов Copy сущности).

Battle log: тексты `Log_*`/`DamageType_*` в .po, цвета — только из `TextPalette`.
- Модификаторы: шаблоны `Modifier_Flat/Increase/Multiplicative` в .po; единицы параметров — `SharedData/Formatting/ParameterFormats.json` (источник правды; в данных доли: 0.5 = 50%). Числа всегда с точкой (InvariantCulture).
- Новый форматируемый тип = класс `ITextFormatter` + DI-регистрация (реестр вместо switch).

## Интерфейс (UI)
- По возможности интерфейсы не должны знать о доменных объектах/знать как можно меньше. Исключение: обеспечение "глупого" интерфейса повлечет за собой создание огромного абстрактного слоя.
- UI создается через Godot эдитор и сохраняется в виде сцены. Создание ui элементов через код только в редких узконаправленых случаях.
- **Три слоя**: Hud (постоянный, один активный) / Window (временные комплексные окна, `IWindow`) / **Overlay** (тултипы, попапы, нотификации — `IPopup` с `PopupLifetime` Timed/WhileHovered/Pinned и `OverlayRegion` Cursor/TopCenter/TopRight/BottomRight; системный фид едет в BottomRight). Расположение: элемент декларирует ТОЛЬКО регион; слой владеет геометрией — регионы это ноды-контейнеры в сцене (VBox стекует соседей, наложение исключено). Нотификации: категория в `SendNotificationMessageMessage` → регион (маппинг в NotificationService). Всё открывается через `IUiElementsManager`: `ToggleWindow` (хоткеи: повтор = закрыть) / `OpenWindow` (открыть или вернуть открытое) / `ShowPopup` (всегда новая инстанция; предыдущий попап ТОГО ЖЕ типа закрывается, разные типы сосуществуют).
- **Fresh-instance политика**: каждый показ = новая инстанция, закрытие = `QueueFree` (`Close()` умирает сам, менеджер подстраховывает FreeIfValid). Окно с подписками на шины ОБЯЗАНО отписываться при смерти (`_ExitTree`).
- **Esc по слоям** (`HandleEscape` в ноде слоёв): первое нажатие чистит Overlay, следующее закрывает все окна с `IsDismissable` (у GameOver — false). Pinned-попапы также закрываются кликом мимо.
- Границы видимости плавающих элементов — только через `UiPlacement.PlaceClamped` (Core).

## Сервисы
- GameServiceProvider своеобразный DI контейнер. Регистрируем и храним необходимые игровые сервисы там. У каждого проекта есть свое расширение позволяющее зарегистрировать необходимые зависимости.
- GameEventBus глобальная игровая шина событый. Служит для уведомления систем на глобальном уровне (к примеру начало и конец боя).
- GameMessageBus глобальная шина обмена информацией между системами. Два режима: Глобальное уведомление fire and forget и Request>Responce.  
- UiElementsManager единая точка создания UI элементов и их отображение на необходимом слое (всего 3 слоя: HUD layer, Window layer, Notifications layer).
