# LastBreath — правила работы (всегда в контексте)

Godot 4.7, C# (.NET 9, LangVersion preview: primary constructors, `field`). Пошаговая RPG, соло-разработчик Todd, общение на русском. Подробный контекст архитектуры/способностей — `HANDOFF.md`.

## Поведение
1. НЕ предлагать что то сделать после выполнения задачи
2. НЕ повторять запрещенные/отклоненные действия. Пример: Я ставлю задачу сделать Х, но не делать Y. В отчете ты не говоришь что Y не сделан потому что я запретил.


## Код
1. Один метод = одна функция.
2. Как можно меньше хардкод чисел/строк.
3. Системы расширяемы, но без оверинженеринга.
4. Несвязные между собой системы комуницируют через GameMessageBus посредством Request>Responce. Оповещение всех заинтересованных систем посредством IMessage (async void)
5. Компоненты предпочтительнее наследования, если наследование уходит глубже чем на 3 уровня.
6. Сначала поля, затем свойства, конструкторы и методы. Порядок ключевых слов private, protected, public
7. Решение не симптомов, а задач. Пример: Необходимо заблокировать UI в определенном сценарии. Вместо написания гуарда сначала стоит собрать информацию, возможно это не единичное место и лучше ввести механизм блокирующий UI для нескольких сценарие.


## Дизайн
1. Работаем в контексте игры. Предложенные решения рассматриваем в рамках не только конкретной задачи, но и общей картины.
2. Нарратив в приоритете
3. Игровой мир работает по правилу: Игрок не центр вселенной,а всего лишь один из жителей. 

## Существующие системы и их назначение
- ParameterModifiersComponent содержит список модификаторов сущности. В большинстве случаев сущность получает модификаторы от экипировки (больше всего относится к Игроку), Аттрибутов (Dex, Int, Str), пассивок, реже от эффектов.
Задача данного компонента: Хранение списка модификаторов цели и уведомление об изменениях списка модификаторов для параметра.
Для нпс имеется дополнительный источник модификаторов: INpcModifier.
- EntityParametersComponent содержит значения параметров сущности. Работает в связке c ParameterModifierComponent (неявно посредством подписки на EventHandler<IModifiersChangedEventArgs>? ModifiersChanged). При получении уведомления об изменении модификаторов параметра пересчитывает значение и сохраняет в Current. Все значения расчитываются по схожей формуле: (сумма flat * (1 + сумма insreased)) * (1+ сумма мультиплаеров). Параметры сущности затем могут быть изменены посредством декораторов. 
Задача компонента: Хранение, расчет и уведомление об изменении значения параметра. 
- EffectsComponent хранит и обрабатывает эффекты владельца. Уведомляет о добавлении и удалении эффекта. 
- NpcModifier хранит список модификаторов наложенных на нпс. Один из источников модификаторов значений параметров для нпс. 
- PassiveSkillComponent обрабатывает пассивные способности сущности. Уведомляет о добавлении/удалении. 
- ModifierHandlerComponent хранит пайплайны обработки контекстов. IContextModifier<T> используется для модификации цифровых значений атаки, лечения, урона и активации способностей. Порядок применения — семантическая шкала `ContextModifierPriority` (Early −100 / Normal 0 / Late 100 / Absolute 1000); конверсии урона при появлении берут Absolute (применяются последними).
- CombatEventBus внутрення шина сущности. Необходима для работы внутренних систем сущности. Создается и умирает вместе с сущностью
- BattleEventBus внешняя боевая шина. Служит для комуникации между системами в рамках боя. Создается в начале боя, удаляется в конце.
- IAbilityBookComponent место обработки конкретных активных способностей сущности.
- Система улучшений активных способностей: Комбинированный подход из нескольких паттернов. Численные значения меняются при помощи декораторов. Логические выносятся в стратегии/отдельные небольшие модули. 
- Активные способности: Комплексная система. Жизненный цикл Данные(json. Сейчас локально, потенциально получаемый от сервера) => Провайдер (Создание через фабрики) => Инстанция => Владалец. Каст AbilityExecute - Единая точка для всех путей активации. 
AbilityActivationContext меняется активационными мутаторами: Ability-scoped => Entity-scoped.
- ExecuteInternal - Delivery. 
- Delivery: 1. Attacks - настоящие атаки. Для каждой создаается AttackContext через scheduler и проходит полный пайплайн обработки атак. 2. HitSequence - прямые хиты. Стратегия IHitSequenceStrategy отдает последовательность фактических касаний. 3. MulticastAbility<TPlan>: база способностей стойки интеллекта. Гарантирует бросок стадии и кумулятивный цикл. План - Generic-параметр живущий ровно один каст. Формы планов: CastPlanVolley - общий залп/крит в MulticastAbilityVoley, ChainPlan, AegisPlan, OverloadPlan.
- Riders - единый контракт вторичных эффектов: 1. IActivationRider - единожды на каст. 2. IImpactRider - на каждый ипакт доставки (хит/прыжок/атака).
- Апгрейды (три рычага, комбинируемые): 1. Числа - декораторы: SimpleAbilityParameterDecorator поверх единого AbilityParameterSet (Core/Battle/Abilities; строковые ключи-константы: общие в AbilityParameter, свои — nested static class Parameters способности; регистрация значений в RegisterBaseParameters, каждый ключ автоматически = плейсхолдер описания). 2. Логика - подмена стратегий/фабрики. 3. Riders. Добавление: generic обертки AbilityUpgradeImpactRider, AbilityUpgradeCastEffect.
- Воспроизведение боя (replay-модель): логика резолвит ход МГНОВЕННО, события пишутся в BattleTimeline (catch-all с per-entity CombatEvents). **BattleDirector** — единственное место «как событие выглядит»: проигрывает записи «битами» с реальным темпом и в момент показа РЕПУБЛИКУЕТ событие в BattleEventBus — весь UI (бары, цифры, лог) реагирует на показ, не на резолв. Событие без хендлера скипается молча; новый визуал = один хендлер в CreateBeatHandlers. Аккорды: события одного каста группируются по `CastId` (штампуется на DamageContext'ы) и играют единой фразой; смерть режет биты мертвеца; турн-луп ждёт `WaitUntilIdleAsync` (гейт хода). UI НИКОГДА не читает живое состояние — только снапшоты из событий (VitalsSnapshot).
- Анимации бойцов: AnimationsComponent поверх AnimatedSprite2D сущности. Клипы по конвенции имён: `Fight_Attack`/`Fight_Hurt`/`Dead`/`Stunned`/`Idle_*` + каст-позы `Ability_<Id>` (PlaceholderFrames.tres). `PlayAnimationAsync`: нет клипа → пауза 0.5с; зацикленный клип → ждём расчётную длительность (кадры/FPS), НЕ animation_finished (иначе подвес).
- VFX способностей: цепочка каста = поза кастера ∥ CastClip (эффект активации на споте кастера, параллельно позе) → полёт/аура → импакт → hurt. VFX-стадии — данные: `AbilityVisualConfig` (Delivery: None/Projectile/Chain/InstantOnTarget/SelfAura; CastClip/TravelClip/ImpactClip — пустой клип = стадия пропускается) в `AbilityVisualLibrary` (.tres, назначен арене), исполняет `AbilityVfxPresenter` (спавн AnimatedSprite2D, полёт твином между спотами). Chain играет хиты последовательно в порядке записи; касты без прямого урона берут цели VFX из EffectAppliedEvent аккорда. Серии атак: атаки штампуют `SourceAbilityId` на AttackContext→DamageContext — бит урона играет ImpactClip способности (полёт к атакам не применяется). Новая способность = клип в VfxFrames + конфиг в библиотеке, код не трогается.

## AI NPC (Core/Ai — чистый C#, Godot только адаптеры)
- Боевой AI: `UtilityTurnPlanner` играет ход NPC (скоринг способностей → касты → базовая атака) через `ICombatEnvironment` (реализует BattleArena). Поведение = `BehaviorProfile` из `NpcBehavior.json` (архетип жёстко от стойки: Dex=агрессия, Str=защита, Int=смешанный), интеллект — явное поле `AiIntellect`.
- Мировой AI: `WorldBrain` (Stateless FSM Calm/Suspicious/Alert/Search) + активности Idle/Wander/Patrol; тело за `IWorldAgent` (BaseNpc: движение прямой, зрение поллингом игрока). Стимулы (`WorldStimulusEvent`) через GameEventBus. Бой стартует физическим контактом.
- Данные NPC: `Npc.json` → `NpcProvider` → `NpcDefinition` → `BaseNpc.ApplyDefinition` (статы/стойка/способности/мозг/lifecycle). EntityType задаёт макс. уровень и число способностей (Regular=Обычный 15 … Archon 150; Boss/Archon вручную).
- Цикл нежити: `NpcLifecycle` — тело после смерти лежит в мире; не-нежить восстаёт нежитью по таймеру (сильнее ∝ времени), нежить в анабиозе; сжигание кликом = финальная смерть (`NpcFinalDeathEvent`).
- Спавн: `NpcSpawnPoint` (лимиты точки, респавн замены по событиям) + `NpcPopulationService` (глобальный лимит живых NPC).
- ВАЖНО: `BattleEndEvent` публикуется в ОБЕ шины (game — лут, battle — выход Player/NPC из Fight-состояний; публикует BattleContext).

## Система лута (LootGeneration)
- Пайплайн: `EntityDiedEvent` → `LootGenerationService.GenerateItemsAsync` (только `IFightableNpc`) → таблица через `GetLootTableRequest` → `SpendBudget` → `IItemCreationService` → `List<ItemStack>` → `LootOrchestrator` (презентация). Кэши (`_tableCache`/`_diedEntities`) чистятся по `BattleEndEvent`.
- **Бюджет** = `baseBudget(EntityType) × (1 + lvlCoef × f(Level)) × rarityMult(Rarity) × (1 + Σ difficulty модификаторов)`; f = √Level (Regular…Unique) или ln(Level+1) (Boss/Archon). Больше difficulty у NPC = больше и лучше лут — ядро мотивации игрока «кормить» NPC модификаторами.
- **Тиры** 0..3: 0 — лучший и самый дорогой. **Rarity**: меньше = лучше (Legendary=0 … Common=4); Unique=10/Mythic=11 — фиксированные шаблонные редкости, генерация их НЕ перекатывает (эксклюзивы, лежат в тире 0 по 420–650).
- `SpendBudget`: ролл тира по шансам (модификаторы двигают шансы через `Calculations.CalculateChances` с нормализацией и перетоком из низших тиров) → доступность тира по **минимальной фактической цене предмета** (не по конфигному прайсу) → недоступный тир падает в ближайший худший → предмет равномерно из доступных по цене. **Тир-апгрейд = бесплатный свап ПОСЛЕ покупки** (ролл платит цену исходного тира, difficulty модификатора уже оплатила разницу). Кап `maxItemsPerKill`; излишек бюджета конвертируется в качество (свап самого дешёвого выбранного на предмет лучшего тира) → потолок ценности ≈ кап × средняя цена t0. Guaranteed-предметы бесплатны и идут ПОВЕРХ капа. Холостые роллы ограничены (100) — пустые таблицы не вешают цикл.
- **Статы предметов**: множитель `1 + itemModifierMultiplier × Σ difficulty`; масштаб ЛИНЕЙНЫЙ для всех типов модификаторов (flat/inc/multi в данных — дельты, суммируются на базу 1). Пул-шаблоны предметов никогда не мутируются — только свежие инстанции (`ModifiersCreator`), композиты разворачиваются со скейлом каждой части.
- Конфиг: `SharedData/LootConfiguration/LootConfiguration.json` (каталог `LootConfiguration` → `LootConfigurationProvider` = `ILootConfiguration`). Таблицы: `SharedData/LootTables` — секции general(basic)/fractions/types/individual, объединяются юнионом по номеру тира (поиск по полю `tier`, не по индексу).
- NPC-модификаторы: `SharedData/NpcModifiers/NpcModifiers.json` → DTO `Core/Data/NpcModifiersData` (маппинг `JsonProperty` ↔ json уже один раз молча умирал — `tierUpgradeChance`; сим-тест держит пол доли тира 0). `ScaleModifier` усиливает остальные модификаторы NPC.
- НЕ доведено (сознательно отложено): Grants из `ItemEffectsModifier` (контекст `AdditionalItemEffects` не заполняется, `equipEffectChance` не используется); `AdditionalItemsModifier` не зарегистрирован в `NpcModifiersFactory`.
- **Симуляция** (`src/Testing/LootSimulation`): настоящий пайплайн без Godot — `FileSystemDataSource` + `DefaultRandomNumberGenerator(seed)`, NPC — Moq-стаб. Быстрые инварианты в обычном прогоне тестов; полный Monte-Carlo отчёт (~10 мин): `dotnet test --filter "TestCategory=Simulation"` → `LootSimulation/Reports/LootSimulationReport.md`. Баланс лута меняем ТОЛЬКО с перегоном отчёта.
- Вне Godot-рантайма нативные вызовы (`ProjectSettings`, `ResourceLoader`, `GD.*`) = фатальный 0xC0000005, try/catch НЕ спасает: Tracker обезврежен через `TrackerBootstrap.LogPathOverride` ([ModuleInitializer] в тестах), `EquipItem.Icon` лениво грузит текстуру — не трогать в копированиях/логике.

## Система крафта (Crafting/Source; домен и UI переписаны 2026-07-11, фаза 3 закрыта 2026-07-16)
- **Четыре команды через шину** (Request>Response), всё остальное — прямые сервисы: `CreateEquipItemRequest` (создание по рецепту), `UpgradeEquipItemRequest` (заточка), `RecraftEquipItemModifierRequest` (реролл модификатора), `AscendEquipItemRequest` (возвышение). Хендлеры — единственные ворота операций: UI-кнопки лишь зеркалят доступность.
- **`CraftingResources`** — check-then-spend (всё-или-ничего) для любых списаний. Порядок в хендлерах: валидация (мастерство/кап/наличие) → списание → операция → опыт. Провал заточки платит и учит (осознанно); кап/нехватка/невозможный реролл не стоят ничего (`ItemUpgradeResult.NotEnoughResources`).
- **Создание**: рецепт (строгие ресурсы и/или категорийные-по-тегу) + до 3 опциональных добавок; пул роллов = family∪item∪дескрипторы ВСЕХ использованных ресурсов, значения × качество мастерства (пишется в `PowerMultiplier`), редкость роллится каналом 3 (руны создания дают пол). Предмет запоминает `UsedRequiredResources`/`UsedOptionalResources`.
- **Пул реролла — живой (2026-07-16)**: вычисляется В МОМЕНТ перековки = family-пул категории ∪ собственный пул базы ∪ дескрипторы `UsedResources` (у лута пусто) ∪ пулы добавок операции; весь union скейлится `PowerMultiplier` предмета (лут пишет difficulty-множитель при дропе, крафт — качество мастерства при создании; поле сейвится, легаси → 1). Лут перековывается наравне с крафтом; правка пула в json видна на уже существующих предметах. Реролл слот-сохраняющий (кандидаты фильтруются по аффиксу целевой строки), группа композита снимается целиком → один атом взамен, дубли (param,type) легальны, пустые кандидаты → отказ без списания. Сборка union'ов — только `EquipItemPoolExtensions` (Core).
- **`ItemUpgrader`**: шанс заточки = кривая P0=0.95…P12=0.01 (константы в коде) × (1 + бонус мастерства 0–200%) + Σ флюсов, кламп 0..1 — ОДНА формула (приватный `ComputeUpgradeChance`), её же отдаёт `GetUpgradeChance(item, resources)` для UI-полосы. Стоимости — `SharedData/UpgradeCosts/UpgradeCosts.json`: схема с редкостью (`byRarity` на записи требования = оверрайды id/amount per-rarity, дефолты — поля записи; битая запись = Tracker + скип всей строки). Руны заточки 1/1/2/3/4 из данных; перековка = пыль категории + основной ресурс по категории×редкости (руды для Weapon/Armor, самоцветы для Jewellery), цена ×(1+0.1×RecraftCount) с ceil — считает `GetRecraftResourceCost(item)`, растёт только с СОСТОЯВШИМСЯ рероллом. **`ItemAscender` (эталон, 2026-07-16)**: гейт мастерства 35 (`ascensionLevelGate` в CraftingMastery.json, бонус-уровни считаются) + Legendary + полная заточка; порядок ДО печати: +15% ко всему (`ascensionStatBonus` → `AscensionMultiplier` на предмете: Value = Base × UpdateMultiplier × AscensionMultiplier, оба канала; properties/значения грантов ×1.15 ОДНОРАЗОВО) → мифик-гифт (шанс `mythicGiftBaseChance` 0.15 × (1 + канал мастерства), пул по КАТЕГОРИИ: `Mythic_Weapon`/`Mythic_Jewellery`/`Mythic_Armor`) → Mythic + печать. «+1..69 уровней заточки» НЕ гарантирован — это одна из записей гифт-пула (`extraUpgradeLevels` в записи, есть у всех трёх клейм; `UpgradeLevelsDescriptor` — операция, не строка: кап += ролл + штатный Upgrade, материализатор такую запись громко отвергает — в обычные пулы ей нельзя). Цена = 1 клеймо категории (`Upgrade_Resource_*_Mark`, Mythic, лут general т0 по 630–650). `AscensionMultiplier` сейвится (легаси → 1). Всережущий (Weapon_All_Cutting): «1–69 заточки» — ВРОЖДЁННЫЙ эффект (data-born мифик, `updateLevel: {min,max}` → Minter фиксирует UpdateLevel==Max==ролл), строк нет, точить/рероллить нечего (тултип-кнопки прячутся по капу/пустоте).
- **Мастерство (реворк 2026-07-16)**: `SharedData/CraftingMastery/CraftingMastery.json` — уровни 0–50, шесть бонус-каналов эталона (шанс заточки 0–200%, значения 0–150% БЕЗ штрафа внизу, редкость 0–150%, доп. эффект 0–150%, мифик-модификатор 0–100% — потребляется возвышением через `GetMythicGiftChance()`, возврат ресурсов), кривая и награды опыта. Прогресс = (уровень+бонус)/50, линейный лерп каналов. Каждый уровень заточки предмета = +5% к значениям строк (эталон; константа в EquipItem).
- **Доп. эффект при создании (канал 4, подключён 2026-07-16)**: скрафченный предмет с шансом `extraEffectBaseChance` (0.1) × (1 + бонус канала) роллит ОДИН бонус-грант из каталога `SharedData/ItemEffects/ItemEffects.json` (`ICraftingEffectProvider`; записи id+kind+weight+properties — payload едет с записью, строгие скилл-фабрики без properties грант не соберут; кривой kind/пустой id = Tracker + скип). Только крафт; лутовые эффекты (IItemEffectProvider) — отдельный недоведённый пайплайн.
- **Добавки** (`ICraftingAdditiveProvider`, каталог `SharedData/CraftingAdditives`): опциональные ресурсы — флюсы `upgradeChanceBonus` (+3/6/9/15% к шансу заточки), руны создания `minRarity` (пол редкости Uncommon…Legendary, из слотов берётся ЛУЧШИЙ), `extraUpgradeLevelChance` (второй уровень при успехе), `recraftPoolId` (временный пул НА ОДНУ операцию). Хендлеры передают ВСЕ ресурсы запроса в апгрейдер — не-добавки просто не дают эффектов. Новая эссенция = запись в json, код не трогается.
- **Разбор** (`DestroyItemMessage`): запечатанное не разбирается (хендлер — гейт); возврат `UsedResources` × канал 6 мастерства + пыль категории floor(1×(1+сырой бонус канала)) — маппинг категория→пыль зашит в хендлере осознанно; опыт Shatter.
- **Опыт**: `GainCraftingExpirienceMessage(mode, rarity)` → хендлер → `ICraftingMastery.GetExperienceReward(mode, rarity)`; все цифры (по редкости × фактор режима) — в CraftingMastery.json.
- **UI**: одно окно `CraftingWindow` (все 4 режима; `SetItem(item, mode)` или выбор рецепта в дереве) — дерево категорий с поиском и счётчиком «(N)», строки требований кодом, категорийное требование = тег ресурса (выбор через встроенный пикер), 3 слота добавок (блок скрыт, пока каталог пуст), полоса шанса заточки в action-баре (Upgrade-режим, live: пересчёт при выборе/снятии флюсов и после каждой попытки; кап-предмет — полоса скрыта; ключ `UI_Craft_Success_Chance`, формула — `GetUpgradeChance`). Вход: `OpenCraftingWindowMessage(id, isItem, mode)`; тултип-кнопки предмета (`InventorySlotTooltipButtons`): Update/Recraft/Ascend шлют соответствующий режим — видимость по `EquipItemCraftActions` (Core: Recraft у любого незапечатанного, Ascend только Legendary; глубокий `CanAscend` — за окном/хендлером). Кнопки живут в PINNED-состоянии `ItemTooltipPopup` (2026-07-16): пин (Alt) добавляет ряд действий для предметов ИЗ СУМКИ (надетые резолвятся null → без кнопок, сначала снять); попап при пине открывает mouse-фильтры (в ховере — Ignore).

## Система репутации (Core/Reputation + Core/Ai/World/Raids; сделано, awaiting Godot-теста)
- **Очки, не уровни**: int per-фракция −6000..6000, `RelationLevel` — производный от порогов из `SharedData/Factions/FactionRelations.json` (Hatred −6000 / Hostility −2000 / Dislike −800 / Neutral −200 / Friendly 1000 / Respect 3000 / Alliance 5000; смена уровня с гистерезисом 50 — уровень хранится как состояние). Дефолты: Undead −1000 (Hostility — атака on sight сохранена), Human 500, остальные 0. Флаги фракций: `hasReputation` (Animal/MysticalCreature false — реп заморожена, свидетелями не являются), `canRaid`. Матрица фракция-vs-фракция СТАТИЧНА — динамичен только слой игрока.
- **`IFactionRelationService`** (единственная реализация в `Core/Reputation`): `AddReputation(faction, delta, reason)` — единственный игровой путь; `SetPlayerRelation(level)` = прыжок в середину диапазона уровня (квесты/миграция); события `PlayerReputationChanged`/`PlayerRelationChanged` (только пересечения порогов). ВАЖНО: пустой ctor нужен DI (данные приходят через Apply), ctor с данными — тестовый.
- **Деяния**: `ReputationDeedProcessor` — единственное место превращения поступков в репутацию; каталог `SharedData/ReputationDeeds/ReputationDeeds.json` (дельта; `noPenaltyAtOrBelow` — анти-death-spiral пол: убийство уже-враждебных бесплатно; `hostileToTargetBonus` — плюс врагам жертвы по матрице; `personal`; `requiresWitness`; `repeatDecay` — сессионное затухание против фермы). Убийства выводятся из `EntityDiedEvent.Killer` (= последний источник урона из TakeDamage; `DefeatInWorld`/`Kill()` обнуляют — скирмиши не винят игрока); остальные системы публикуют `PlayerDeedEvent(deedId, faction, instanceId?, position)`. Всё глушится при `ILoadScope.IsLoading`.
- **Свидетели (уровень 0)**: `IWitnessQuery`/`WorldWitnessQuery` — живой не-сражающийся NPC реп-фракции в `witnessRadius` ИЛИ сбежавший из текущего боя (гарантированный свидетель до BattleEndEvent; `EntityFledBattleEvent` теперь публикуется и в game bus). Якорь радиуса — мировая точка боя из `BattleInitializedEvent` (в бою Position бойцов = спот арены!). Нет свидетелей → деяние с `requiresWitness` не произошло вовсе (ни штрафа, ни бонусов, decay не сжигается).
- **Личный слой**: `IPersonalReputationService` — очки per-NPC (InstanceId), секция `personalReputation` в FactionRelations.json (±1000, 300 очков = 1 ступень лестницы, кап ±2). Эффективное отношение = фракционный уровень + сдвиг; его читает `BaseNpc.ConsidersPlayerAnEnemy` (спасённый гном не атакует; флаг `hostileToPlayer` бандитов — абсолютный оверрайд). Память умирает с носителем: FinalDeath/FactionChanged → Forget.
- **Транслятор**: `ReputationBroadcaster` зеркалит события сервиса в GameEventBus (`ReputationChangedEvent`/`PlayerStandingChangedEvent` — заинтересованные подписываются на шину вместо инжекта сервиса) + шлёт тосты. Пайплайн нотификаций умеет шаблоны: `SendNotificationMessageMessage.Values` → попап рендерит `Localization.Render`. Ключи: `Fraction_*`, `RelationLevel_*`, `UI_Reputation_Changed`, `UI_Standing_Changed`, `UI_Raid_Started`.
- **Рейды**: `RaidService` (каталог `SharedData/Raids`, тикается `NpcWorldDirector`): Hatred + `canRaid` → кулдаун/шанс → отряд 2–4 у БЛИЖАЙШЕЙ к игроку спавн-точки фракции (`NpcSpawnPoint : IRaidSpawnSite`, фракция лениво из первого npcId; реестр `IRaidSpawnRegistry`). Рейдеры БЕЗ мирового мозга (`definition with { World = null }`) — сервис сам ведёт их `IWorldAgent.MoveTo` на игрока, бой по контакту; `INpcPopulationService.ReserveOutsideLimit()` — вне капа, но занимают счётчик (спавн-поинты ждут). Таймаут → выжившие уходят ЧЕРЕЗ `NpcFinalDeathEvent` + `INpcWorldSpawner.Despawn` (штатная очистка популяции/личной памяти); активный бой доигрывается. Активный рейд блокирует `CanSave`. Убийство рейдеров бесплатно автоматически (пол Hostility).
- **Перки (фундамент, потребителей нет)**: `IReputationPerkProvider` + `SharedData/ReputationPerks/ReputationPerks.json` — уровень → ПОЛНЫЙ набор перков (`Perk_Price_Change`, `Perk_Reward_Change`, `Perk_Mythic_Gear_Access`, `Perk_Settlements_Closed`, `Perk_Entrance_Fee`). Подключать к торговле/поселениям по мере появления.
- **Сейвы**: `factionRelations` v2 (очки+уровень; миграция v1: level → середина диапазона), `personalReputation` v1, `raids` v1 (кулдаун) — последние два регистрируются опционально (проект без сервиса не пишет секцию).
- **ЛЕГАСИ снесено** (подтверждено 2026-07-11): `Main/Reputation` + `Main/UI/View/FractionReputation` удалены ещё нарратив-реворком; остался только мёртвый путь в `Main/export_presets.cfg` (см. Доработать №25). Окно фракций — в бэклоге улучшений репутации.

## Данные
- Исходные игровые данные расписаны в json (предметы, активные способности, пулы модификаторов для предметов и т.д). Загрузка — единый слой `Core/Data/GameData` (зеркало системы сейвов): провайдер = `IGameDataParticipant` (декларирует каталоги-подпапки Data и парсит файлы в `Apply`), `GameDataService.LoadAll()` вызывается ОДИН раз в бутстрапе проекта (`AddGameData(root)` + участники через `AddGameDataParticipant<TService, TImpl>`); источник (res:// / файловая система / потенциально сервер) — за `IGameDataSource`. Конструкторы провайдеров НЕ читают файлы.
- Enum'ы из json парсятся строго через `DataParse.ParseEnum` (опечатка = ошибка в Tracker, не молчаливый дефолт). Битый файл/каталог скипается с репортом, битый модификатор скипается на уровне записи.
- Общие данные всех проектов лежат в `src/SharedData/<Каталог>` (единственная физическая копия) и подключены в каждый проект симлинком `Data/Shared` (Crafting: `Internal/Data/Shared`). Бутстрап передаёт два корня: `AddGameData("res://Data/", "res://Data/Shared/")`. Каталог целиком берётся из ПЕРВОГО корня, где найден: локальная папка-каталог с тем же именем полностью перекрывает общую (механизм оверрайда для экспериментов).
- Провайдеры являются источниками оригиналов; по необходимости создают новые инстанции (фабрики либо через вызов Copy сущности).

## Локализация и текст
- .po файлы (en+ru) — ЕДИНСТВЕННАЯ копия в `SharedData/Localization`, подключены во все 4 project.godot через симлинк Data/Shared. Приоритет en; ru пополняется только ключами (msgstr "" → показывается ключ). Конвенция ключей: имя = `<Id>`, описание = `<Id>_Description`, интерфейс = `UI_*`.
- Архитектура: чистое ядро `Core/Localization` + DI (регистрируется в shared-сервисах): `ILocalizationProvider` (Godot-адаптер над TranslationServer, событие LocaleChanged, плюрализация), `ILocalizationService`, статик-фасад `Localization` — тонкая обёртка для UI.
- Описания — шаблоны с именованными плейсхолдерами: `{Damage}`, доля-в-процент `{chance:%}` (×100+знак), плюрализация `{Duration|turn|turns}`, ключевые слова `{@Effect_X}` (клик → карточка `<Key>_Tooltip`, подключение UI — `KeywordLinks.Attach`), экранирование `{{}}`; движок `TextTemplateEngine`. Значения отдаёт домен (`DescriptionValues` у Ability/Effect/Skill; у апгрейдов — автоматом из json `upgradeProperties`). Неизвестный плейсхолдер остаётся видимым в тексте. `TextFormat.Plain` для Label / `TextFormat.Rich` (BBCode, числа красятся `TextPalette.Number`). Гайд: `Docs/AbilityDescriptions.md`. Battle log: тексты `Log_*`/`DamageType_*` в .po, цвета — только из `TextPalette`.
- Модификаторы: шаблоны `Modifier_Flat/Increase/Multiplicative` в .po; единицы параметров — `SharedData/Formatting/ParameterFormats.json` (источник правды; в данных доли: 0.5 = 50%). Числа всегда с точкой (InvariantCulture).
- Новый форматируемый тип = класс `ITextFormatter` + DI-регистрация (реестр вместо switch).

## Интерфейс (UI)
- По возможности интерфейсы не должны знать о доменных объектах/знать как можно меньше. Исключение: обеспечение "глупого" интерфейса повлечет за собой создание огромного абстрактного слоя.
- UI создается через Godot эдитор и сохраняется в виде сцены. Создание ui элементов через код только в редких узконаправленых случаях.
- **Три слоя**: Hud (постоянный, один активный) / Window (временные комплексные окна, `IWindow`) / **Overlay** (тултипы, попапы, нотификации — `IPopup` с `PopupLifetime` Timed/WhileHovered/Pinned и `OverlayRegion` Cursor/TopCenter/TopRight/BottomCenter). Расположение: элемент декларирует ТОЛЬКО регион; слой владеет геометрией — регионы это ноды-контейнеры в сцене (VBox стекует соседей, наложение исключено). Нотификации: категория в `SendNotificationMessageMessage` → регион (маппинг в NotificationService). Всё открывается через `IUiElementsManager`: `ToggleWindow` (хоткеи: повтор = закрыть) / `OpenWindow` (открыть или вернуть открытое) / `ShowPopup` (всегда новая инстанция; предыдущий попап ТОГО ЖЕ типа закрывается, разные типы сосуществуют).
- **Fresh-instance политика**: каждый показ = новая инстанция, закрытие = `QueueFree` (`Close()` умирает сам, менеджер подстраховывает FreeIfValid). Окно с подписками на шины ОБЯЗАНО отписываться при смерти (`_ExitTree`).
- **Esc по слоям** (`HandleEscape` в ноде слоёв): первое нажатие чистит Overlay, следующее закрывает все окна с `IsDismissable` (у GameOver — false). Pinned-попапы также закрываются кликом мимо.
- Границы видимости плавающих элементов — только через `UiPlacement.PlaceClamped` (Core).

## Сервисы
- GameServiceProvider своеобразный DI контейнер. Регистрируем и храним необходимые игровые сервисы там. У каждого проекта есть свое расширение позволяющее зарегистрировать необходимые зависимости.
- GameEventBus глобальная игровая шина событый. Служит для уведомления систем на глобальном уровне (к примеру начало и конец боя).
- GameMessageBus глобальная шина обмена информацией между системами. Два режима: Глобальное уведомление fire and forget и Request>Responce.  
- UiElementsManager единая точка создания UI элементов и их отображение на необходимом слое (всего 3 слоя: HUD layer, Window layer, Notifications layer).
