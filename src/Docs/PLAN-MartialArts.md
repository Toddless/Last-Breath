## 1. Резюме

| Метрика | Значение |
|---|---|
| Находок в реестре | **90** (F-01 … F-90) |
| Опровергнуто аудитом (делать не надо) | **20 позиций** — раздел 3 |
| Находок в объёме прогона | 23 |
| Находок в бэклоге с обоснованием | 63 |
| Находок закрыто до плана (✅/⛔) | 4 |
| Задач | **18** (T-02 … T-19; T-01 отменена владельцем) |
| Волн | **5** + волна F (хвосты по решению владельца, подтверждена) |
| Критический путь | 5 задач, T-06 → T-07 → T-11 → T-15 → T-16 |

**Что делает прогон.** Закрывает шаги 3–6 «Предлагаемого порядка» техбазы: теги (уже закрыты, задач нет), развязку блокеров дерева, урезку атрибутов и домен дерева пассивок без UI. На выходе игра читает `PassiveTree.json`, узлы берутся и снимаются через отладочную консоль, вклад узлов виден в параметрах игрока и переживает сейв.

**Что вне прогона.** Сокеты и аугменты, разбор 189 записей реестра апгрейдов, аугменты-предметы, UI колеса и UI сокетов, данные дерева (~90 узлов, 3 старта, 36 сокетов), испытания сильных, конверсия N→1 в крафте, балансный пасс. `AbilityUnlockService` на узлы дерева — **следующая волна по решению владельца**, см. риск R-1.

> [!IMPORTANT] Условия адресуются по явному `id` — решение владельца 2026-07-31
> Условия нужны **не только дереву**: модификаторы экипировки берут те же предикаты. Отсюда требование явного идентификатора, и отсюда же — каталог как способ адресации.
>
> **Формат:** отдельный каталог `SharedData\Conditions` (`id` → тип, ресурс, порог, инверсия), потребитель несёт **только** `id`. Одно определение — одна правка; «здоровье ниже 30%» существует в игре ровно один раз. Цена принята: на каждый порог заводится своя запись (`Health_Below_30`, `Health_Below_40`).
>
> **Два следствия, снимающие уже записанные долги.** Во-первых, шов **W-52** закрывается сам: поле `Condition` на обеих строках узла — **строка**, и она же и есть `id`; изобретать второй формат не нужно, а `ConditionParser` из T-10b2 переезжает внутрь провайдера каталога и парсит его записи. Во-вторых, `LineIdentity` предмета получает то стабильное сравнимое представление условия, без которого «ключ + условие» из `CLAUDE.md` не реализуется — сравнение идёт по `id`, а не по структуре записи.
>
> **Ловушка, которую задача обязана закрыть:** ссылка на несуществующий `id` — репорт и отказ строки, не молчаливое «условие всегда истинно». Это тот же класс, что закрытый блокер про нечитаемый ресурс.

**Мина, зафиксированная в постановке T-10b1:** узлы дерева **нельзя** вешать per-node через `ContextModifierEntry`, хотя это скомпилируется. `ModifierHandlerComponent.Apply` применяет последовательно, а не суммирует: 20 узлов «+10%» дадут ×6.73 вместо ×3 — ровно дефект, который лечит T-12. Строка узла обязана остаться **данными**, а модификатор на пайплайн вешает агрегатор, один.

**Шов между T-10b1 и T-10b2 закрыт постановкой:** формат записи условия целиком принадлежит T-10b2; T-10b1 поле `Condition` не трогает и парсер не изобретает. Сводит их T-10b4. Это тот же класс шва, что открывался между T-11 и T-14 — там его пришлось закрывать задачей T-22 задним числом.
