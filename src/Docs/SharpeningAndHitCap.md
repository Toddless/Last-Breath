# Заточка и кап доп-атак

Разбор по заказу владельца от 2026-08-26. Две независимые темы: правила заточки (карточка #200, V1-В2)
и кап `AdditionalHitChance` (V2-В8). Всё ниже — факты из кода и данных с путями; расчётные таблицы
считаны на средних роллах и `PowerMultiplier = 1`, если не сказано иное.

> [!IMPORTANT] РЕШЕНО 2026-09-01 — вариант «б», но с оговоркой, меняющей часть таблиц
> Владелец принял вариант **(б)**: заточка достаёт только базовый канал (`_baseStats`, оружейная
> тройка, плоские **имплиситы**). Оговорка: **возвышение свой охват НЕ сузило** — ×1.15 по-прежнему
> поднимает все цифровые значения, включая плоские **роллённые** строки и значения грантов.
>
> Отсюда: **колонки «(б) +возв» в §1 и §2 НЕВЕРНЫ** — они считались в предположении, что возвышение
> тоже перестанет доставать роллённые строки. Колонки «(б) +12» верны и остаются в силе. Правильные
> числа на +12 с возвышением: меч — физ **577.3**, добавленный огонь **258.75**, крит-урон **3.43275**;
> `Body_Stoneheart` — здоровье **717.6**, огнерезист **0.1725**. Пять суффиксов огнерезиста на мифике
> дают **0.69**, а не 0.60 (§2).
>
> Реализация — карточка #240 (`EquipItem.BaseChannelMultiplier` / `RolledChannelMultiplier`; имя
> `LineMultiplier`, которым оперирует §0, в коде больше не существует). Оговорки §3 остаются в силе
> и разведены по карточкам: вес базы бижутерии — #241, бюджет доп-атаки в `baseStats` — #235.

## §0. Границы, которые задаёт код

### Шкалы

| Величина | Значение | Где |
|---|---|---|
| Бонус за уровень заточки | `+0.05` линейно | `src/Core/Items/EquipItem.cs:16` (`UpgradeBonusPerLevel`) |
| Множитель на +12 | `1 + 12×0.05 = 1.60` | `EquipItem.cs:255` (`UpdateMultiplier += appliedLevels * UpgradeBonusPerLevel`) |
| Множитель возвышения | `1.15` | `src/SharedData/CraftingMastery/CraftingMastery.json` → `ascensionStatBonus: 0.15`; применяется в `src/Crafting/Source/ItemAscender.cs:44` |
| Мифик = легендарка +12 + возвышение | `1.60 × 1.15 = 1.84` | `EquipItem.cs:40` — `LineMultiplier => UpdateMultiplier * AscensionMultiplier` |

### Где проходит граница «база / строка» — по коду

Обе стороны множатся на один и тот же `LineMultiplier`, но **разными вызовами**:

* **База (BASE-канал)**
  * `EquipItem.cs:175` — `float scaledBase = _baseStats.GetValueOrDefault(parameter) * LineMultiplier;`
    Это типизированный базовый канал предмета (`_baseStats`, `EquipItem.cs:22`): броня — Armor/Evade/
    Barrier/Health, бижутерия — атрибут + Health/Mana/Accuracy/шанс. Роллится минтером один раз
    (`src/Core/Items/EquipItemMinter.cs:83-89`) и хранится **нескалированным**.
  * `src/Core/Items/WeaponItem.cs:50` и `:57` — та же формула для оружейной тройки
    `BaseDamage` / `CriticalChance` / `CriticalDamage`.
* **Строка (LINE-канал)**
  * `EquipItem.cs:368-369` — `private float Scaled(float baseValue, ModifierValueType type) =>
    type == ModifierValueType.Flat ? baseValue * LineMultiplier : baseValue;`
    Через него проходят **имплиситы, роллённые аффиксы и контекст-строки** (`SetModifiers`,
    `InsertAdditionalModifier`, `SetContextModifiers`, `UpdateModifiersValue`).

**Ключевой факт:** `Scaled` множит только `Flat`. Строки типа `Increase` и `Multiplicative`
не скалируются заточкой уже сегодня, ни в одном варианте. Значит вся разница (а)/(б) — это разница
**по плоским строкам аффиксов и имплиситов**, и только по ним.

Определение вариантов для этого документа:

* **(а)** — текущее поведение: `LineMultiplier` применяется к `_baseStats`, оружейной тройке
  **и** ко всем плоским строкам (имплиситы + аффиксы).
* **(б)** — предложение: `LineMultiplier` применяется к `_baseStats`, оружейной тройке
  и **имплиситам**; плоские **роллённые аффиксы** остаются как их записал ролл.

### Асимметрия, которую стоит держать в голове

Роллённые аффиксы **уже** имеют собственный множитель — `PowerMultiplier` (калибр: сложность убийства
или качество крафта), который масштабирует весь пул перед роллом:
`src/LootGeneration/Internal/ItemCreationService.cs:46-47` (`DescriptorOperations.Scale(descriptor, modifierMultiplier)`),
`src/Crafting/Source/ItemUpgrader.cs:124`.
**Базы `PowerMultiplier` не получают** — минтер роллит их до применения калибра
(`EquipItemMinter.cs:41` идёт до `HandleEquipItemGeneration`).

То есть сегодня по варианту (а) аффикс кормится **двумя** множителями (калибр × заточка),
а база — **одним** (заточка). Вариант (б) разводит их 1:1: база ← заточка, аффикс ← калибр.

### Состав легендарки

`src/Core/Modifiers/AffixRules.cs:16` — `Rarity.Legendary => (2, 2)`: два префикса + два суффикса.
Пул = пул предмета ∪ пул семейства (`src/Core/Data/EquipItemPoolExtensions.cs:18`;
семейство берётся по `id.Split('_')[0]`, `src/LootGeneration/Services/ItemDataProvider.cs:67`).
Дубликаты одной «линии» на предмете запрещены — `src/Core/Modifiers/AffixRoller.cs` + `LineIdentity`
(идентичность = канал + параметр + тип значения + условие), и корзины префиксов/суффиксов делят
**один** набор занятых идентичностей. Поэтому на одном кольце не может быть двух `AHC/Flat`,
но `AHC/Flat` и `AHC/Increase` — могут.

Легендарки родом из Common-блюпринтов: у них есть `baseStats` и **нет имплиситов**. Имплиситы есть
только у Unique/Mythic, а у тех, наоборот, нет `baseStats` (проверено по всем девяти файлам
`src/SharedData/EquipItems/*.json`). Для легендарки «база» = `baseStats` / оружейная тройка.

## §2. Резисты: где вариант (а) сжигает роллы

Огнерезист лежит **только в суффиксах брони** и ни у одного блюпринта не является `baseStats`
(проверено по всем `EquipItems/*.json` — в базах нет ни одного параметра `*Resistance`).
Значит по варианту (б) резисты заточкой не кормятся вообще.

Диапазоны суффикса `FireResistance Flat` по слотам (`EquipItemModifierPools.json`):

| Слот | Диапазон | Средний ролл |
|---|---|---:|
| Body (:869) | 0.10–0.20 | 0.150 |
| Cloak | 0.10–0.20 | 0.150 |
| Helmet | 0.05–0.15 | 0.100 |
| Gloves | 0.05–0.15 | 0.100 |
| Boots | 0.05–0.15 | 0.100 |
| **Сумма пяти слотов** | | **0.600** |

| Сборка | (а) | (б) |
|---|---:|---:|
| 5 суффиксов огнерезиста, +0 | +60.0% | +60.0% |
| 5 суффиксов, +12 (×1.60) | **+96.0%** | +60.0% |
| 5 суффиксов, мифик (×1.84) | **+110.4%** | +60.0% |
| То же для `AllResistance` (0.125×2 + 0.075×3 = 0.475), мифик | **+87.4%** к четырём резистам сразу | +47.5% |

Кап резиста: `src/Core/Entity/Components/ResistanceParameters.cs:14` — `DefaultMaximum = 0.75`,
потолок самого кап-параметра `0.9` (`EntityParametersComponent.cs:16`). Сам резист сверху не ограничен
намеренно (комментарий `EntityParametersComponent.cs:24-26`) — оверкап съедается только шредом.

**Итог по резистам.** Цифра владельца +110% подтверждается ровно: `0.600 × 1.84 = 1.104`.
При капе 0.75 это значит, что **на мифике 47% вложенного резиста мертвы** — пять слотов дают то,
что при 0.75 упирается в потолок примерно на третьем. При (б) те же пять суффиксов дают +60%,
до кэпа не хватает 15 п.п. — их надо добирать `AllResistance`-суффиксами, уникалками или деревом.
Это ровно то поведение, ради которого кап и существует.

## §3. Вывод и рекомендация

### Что делает вариант (а) сегодня

1. **Заточка — не выбор, а налог.** Она множит весь предмет, поэтому «не точить» никогда не выгодно
   ни на одном слоте и ни в одном билде. Решения игрока в заточке нет.
2. **Двойное кормление аффиксов.** Аффикс уже промасштабирован калибром (`PowerMultiplier`),
   и заточка накладывается сверху: `итог = ролл × калибр × 1.84`. База получает только заточку.
3. **Систематический перелив через капы.** Заточка бьёт по `Flat`, а почти все жёстко закапанные
   параметры набираются именно плоскими строками: резисты (кап 0.75), `AdditionalHitChance` (0.75,
   `EntityParametersComponent.cs:31`), `Suppress` (0.75), `BlockChance` (0.9), `CriticalChance` (1.0),
   `ArmorPenetration` (1.0). До капа заточка даёт +60/+84%, после — ровно ноль. Дизайн-диапазоны в пулах
   рассчитаны на нескалированное значение, поэтому «+12» их просто выносит.
4. **Мифик усиливает эффект, а не отменяет его**: пулы возвышения (`MythicModifiers.json`) резистов и
   доп. атаки не содержат, так что +15% возвышения бьёт по тем же переполненным строкам.

### Что делает вариант (б)

1. **Убирает двойное кормление**: база ← заточка, аффикс ← калибр. Одна причина роста на канал.
2. **Снимает проблему капов почти целиком.** В `baseStats` из закапанных параметров встречаются только
   `BlockChance` (`Belt_of_Knight`, `Ring_of_Knight`), `CriticalChance` (`Ring_of_Assassin`),
   `MulticastChance` (`Ring_Archmage_Signet`), `AdditionalHitChance` (`Ring_of_Trickster`) — все
   в диапазоне 0.01–0.05, на +12 это 0.016–0.08. Резистов в базах нет вообще.
3. **Возвращает заточке решение.** Она становится «докачать базу предмета», а не «умножить предмет».
   Меч 220 → 405 базы на мифике, тело 525 армора → 966 — это существенно и понятно читается в тултипе.
4. **Не убивает бижутерию.** Проверено фактом: у всех Common-блюпринтов `Ring`/`Amulet`/`Belt` базы
   есть (см. §1.3, §1.4 и дамп всех блюпринтов). Кольцо — атрибут + типовая строка (Health 100–190,
   Armor 150–280, Mana 100–200, Accuracy 250–380 или шанс 0.01–0.05); амулет — атрибут 11–17 либо
   пара 5–10; пояс — атрибут 5–15 или Health 150–270. Но база бижутерии **заметно скромнее** базы
   оружия и брони, поэтому +60% на ней ощущается слабее.

### Рекомендация ведущего

**Брать (б)** — заточка множит только базовый канал (`_baseStats` + оружейная тройка) и имплиситы.

Причина в одну строку: при (а) заточка — это скрытый общий множитель на весь предмет, который
одновременно (1) дублирует калибр, (2) систематически выкидывает вложенные роллы за жёсткие капы
и (3) не оставляет игроку выбора. При (б) каждый канал растёт от одной причины, капы перестают
съедать вложенное, и заточка становится осмысленной операцией «докачать сам предмет».

**Две оговорки, без которых (б) не поедет:**

1. **Бижутерии нужно вернуть вес базы.** Сегодня ролл базы кольца — это 7.5 ловкости и 0.03 шанса;
   +60% от этого = +4.5 и +0.018. Это меньше, чем игрок ждёт от четырёх рун. Варианты:
   (а) расширить базовые диапазоны бижутерии примерно ×1.5 (`Ring` атрибут 5–10 → 8–15,
   типовая строка Health 100–190 → 150–280, шанс 0.01–0.05 → 0.02–0.06);
   (б) перенести по одной «фирменной» строке из пула предмета в `baseStats` каждого блюпринта
   (у `Ring_of_Trickster` это уже сделано — `AdditionalHitChance` стоит в базе).
   Механику менять не нужно, только данные.
2. **(б) конфликтует с правилом из части 2 — см. §4.4.** Правило «кап доп-атак берётся только
   заточенной экипировкой» держится на том, что `AdditionalHitChance` на шмоте — плоский **аффикс**,
   который заточка множит. При (б) он множиться перестанет. Значит бюджет доп-атаки на шмоте
   надо переносить в базовый канал.

## §4. Кап доп-атак (`AdditionalHitChance`)

### 4.0 Механика и потребитель

Единственный потребитель — `src/Battle/Source/PassiveSkills/ChainAttackPassiveSkill.cs:24`:
после каждой успешной атаки катится `Owner.Parameters.AdditionalHit`, породившая атака катится снова.
Матожидание доп. атак на один замах = `p / (1 − p)`:

| p | 0.42 | 0.50 | 0.62 | 0.70 | 0.75 (кап) |
|---|---:|---:|---:|---:|---:|
| Доп. атак на замах | 0.72 | 1.00 | 1.63 | 2.33 | **3.00** |

Кривая взрывная — поэтому кап 0.75 (`EntityParametersComponent.cs:31`) и поэтому важно, где именно
билд по ней стоит. Формула значения — `src/Core/Calculations.cs:295-315`:
`(база + Σflat) × (1 + Σincrease) × (1 + Σmulti)`, кап накладывается в индексере компонента.
База игрока — `0.05` (`src/SharedData/PlayerStats/PlayerStats.json:13`, `src/Battle/Internal/Player/Player.cs:660`).

### 4.1 Арифметика дерева — по факту данных

Все ноды с `AdditionalHitChance` в `src/SharedData/PassiveTree/PassiveTree.json` (все — стойка Dexterity):

**Плоские (Σ = 0.13):**

|---|---|---:|

| `notable_critical_chance_additional_hit_chance_1` | Crit\|Additional Hit Chance | Flat 0.05 |
| `notable_evade_7` | **Evade** | Flat 0.03 |

**Increase (Σ = 1.77):**

| Нода(ы) | Заголовок | Значение | Вклад |
|---|---|---|---:|
| `notable_additional_hit_chance_evade_1` | Additional Hit Chance\|Evade | Inc 0.40 | 0.40 |
| `notable_10` | Additional Hit Chance | Inc 0.25 | 0.25 |
| `notable_evade_7` | **Evade** | Inc 0.25 | 0.25 |
| `small_additional_hit_chance_1..5` (5 шт.) | Additional Attack Chance | Inc 0.05 | 0.25 |
| `small_additional_hit_chance_evade_1..6` (6 шт.) | Additional Hit Chance\|Evade | Inc 0.04 | 0.24 |
| `small_critical_chance_additional_hit_chance_1..6` (6 шт.) | Critical\|Additional Hit Chance | Inc 0.03 | 0.18 |
| `small_evade_1..4` (4 шт.) | **Evade** | Inc 0.05 | 0.20 |

Итого 24 ноды при бюджете 65 очков (`PassiveTree.json:3`) — луч выбирается целиком с большим запасом.

**Расхождение с заказом.** Владелец пишет, что чистый луч даёт `0.29 × 2.77 = 0.80` **без экипировки**.
По факту `0.29` — это уже **с** экипировкой: `src/Docs/TreeV2-Clusters.md:263` раскладывает её как
`0.05 база + 0.13 дерево + 0.11 мифик-шмот`. Множитель `2.77` совпадает с данными точно (`1 + 1.77`).

**Чистое дерево без экипировки:**
`(0.05 + 0.13) × (1 + 1.77) = 0.18 × 2.77 = ` **`0.499`**

То есть **дерево одно кап не перекрывает** — оно попадает ровно в верхнюю границу целевой вилки
владельца 0.4–0.5. Посылка «дерево одно перекрывает кап» не подтверждается.

**Кап перекрывает экипировка.** Одно легендарное `Ring_of_Trickster` на +12 даёт `0.166` (§1.3).
Два таких кольца = `0.333`. Тогда `(0.05 + 0.13 + 0.333) × 2.77 = 1.42` — почти двукратный перелив,
и это без учёта `Increase`-строк на шмоте, которые задирают ещё и множитель.

### 4.3 Предлагаемый нерф — вариант (а) остаётся (заточка множит аффиксы)

**Алгебра целей.** Обозначим `F0 = 0.05 + Tflat` (база игрока + плоское дерево), `M = 1 + Tinc`,
`G` — суммарный плоский `AdditionalHitChance` собранной экипировки без заточки.
Три точки владельца:

```
дерево одно                : F0 · M           ∈ [0.40, 0.50]
дерево + шмот без заточки  : (F0 + G) · M     = 0.625
дерево + шмот +12 (×1.60)  : (F0 + 1.60·G)·M  = 0.750
```

Из двух последних: `(F0 + 1.6G)/(F0 + G) = 1.2` ⟹ **`G = 0.5 · F0`**, и тогда
`F0·M = 0.625/1.5 = 0.4167` — то есть «дерево одно» **однозначно определено** тремя целями владельца
и равно **0.417**, что попадает в его же вилку. Хорошая новость: система целей непротиворечива.
Остаётся выбрать, как поделить `0.4167` между `F0` и `M`. Чем меньше `M`, тем менее чувствительна
настройка шмота — поэтому предлагается опустить `Increase` дерева и слегка поднять плоское.

**Целевые числа: `Tinc = 1.00` (+100% вместо +177%), `Tflat = 0.16` (вместо 0.13).**
Тогда `F0 = 0.21`, `M = 2.00`, бюджет шмота `G = 0.105`.

**Конкретные правки нод (только значения, id не трогаем):**

| Нода | Сейчас | Предложение | Δ |
|---|---|---|---|
| `notable_evade_7` | Evade Inc 0.35 + **AHC Inc 0.25** + **AHC Flat 0.03** | убрать обе строки AHC, оставить Evade | inc −0.25, flat −0.03 |
| `small_evade_1..4` | Evade Inc 0.05 + **AHC Inc 0.05** | убрать строку AHC (как у `small_evade_5`, где её уже нет) | inc −0.20 |
| `notable_additional_hit_chance_evade_1` | AHC Inc 0.40 | AHC Inc **0.20** | inc −0.20 |
| `small_additional_hit_chance_evade_1..6` | AHC Inc 0.04 | AHC Inc **0.02** | inc −0.12 |
| `notable_10` | AHC Flat 0.05 + Inc 0.25 | AHC Flat **0.09** + Inc 0.25 | flat +0.04 |
| `notable_critical_chance_additional_hit_chance_1` | AHC Flat 0.05 | AHC Flat **0.07** | flat +0.02 |
| остальные (`small_additional_hit_chance_1..5`, `small_critical_chance_additional_hit_chance_1..6`) | — | без изменений | — |

Проверка: `Σinc = 0.25 (notable_10) + 0.20 + 0.25 (5×0.05) + 0.12 (6×0.02) + 0.18 (6×0.03) = 1.00` ✔
`Σflat = 0.09 + 0.07 = 0.16` ✔

Первые две строки таблицы — это ещё и чистка данных: три ноды с заголовком «Evade» несут
`AdditionalHitChance`, при том что `small_evade_5` того же семейства его не несёт. Похоже на слип,
а не на дизайн. Дерево правит владелец, поэтому это предложение, а не правка.

**Правки экипировки (бюджет `G = 0.105` на собранный сет, средние роллы):**

Принцип, который я предлагаю зафиксировать: **`Increase`-канал доп-атаки принадлежит дереву,
экипировка несёт только `Flat`.** Иначе множитель гуляет вместе со шмотом и никакая настройка
плоских значений не сходится.

| Что | Сейчас | Предложение |

| `Ring` семейный, Flat Suffix (`:2605`) | 0.01–0.05 | **0.015–0.035** (среднее 0.025) |

Носители: оружие, перчатки, два кольца — четыре слота × 0.025 ≈ **0.10** ≈ бюджет.

**Раскладка по точкам инвеста (после нерфа, средние роллы, `PowerMultiplier = 1`):**

| Сборка | `G` | Итог | Доп. атак на замах |
|---|---:|---:|---:|
| Дерево одно, без шмота | 0 | **0.42** | 0.72 |
| Дерево + Rare/Epic, AHC на 2 слотах, без заточки | 0.050 | **0.52** | 1.08 |
| Дерево + Rare/Epic, AHC на 3 слотах, без заточки | 0.075 | **0.57** | 1.33 |

**Оговорка по вилке владельца.** «Дерево + Rare/Epic без заточки ~0.6–0.65» достигается в этой
раскладке только если под этим понимается сет, у которого AHC выпал **на всех четырёх слотах**.

из четырёх слотов невелик, поэтому реальная Rare/Epic-сборка сядет ближе к 0.52–0.57. Если владелец
хочет именно 0.62–0.65 на Rare/Epic, из алгебры выше следует, что «дерево одно» придётся поднять
до ~0.515 (то есть почти не резать `Increase`, а резать шмот) — это альтернативная развилка,
и решение за владельцем.

### 4.4 Если принимается вариант (б) из §3 — раскладка меняется

При (б) плоские **аффиксы** заточкой не множатся, а значит строка `+12 (×1.60)` из таблицы выше
просто исчезает: `G` остаётся 0.100 и кап не берётся никогда. Правило владельца («кап только
с заточкой») при (б) держится лишь на **базовом канале**. Поэтому бюджет доп-атаки надо перенести
в `baseStats`:

| Слот | Предложение при (б) |
|---|---|
| `Ring_of_Trickster` | baseStat `AdditionalHitChance` 0.01–0.05 → **0.02–0.05** (среднее 0.035) |
| Кинжал / когти (`Weapon_Simple_Dagger`) | **добавить** `baseStats: [{ "parameter": "AdditionalHitChance", "value": { "min": 0.02, "max": 0.05 } }]` |
| `Gloves_Hunter` (и один «ловкий» архетип перчаток) | **добавить** тот же baseStat 0.015–0.035 |
| Семейные суффиксы `Weapon`/`Ring`/`Gloves` | оставить как в §4.3 (0.015–0.035), но они станут «незатачиваемой» частью |

Технически это работает без правок кода: `ParseBaseStats` (`src/Core/Data/DataParser.cs:224`)
применяется ко всем предметам независимо от слота, а `WeaponItem.IsLocalBucketExternal`
(`WeaponItem.cs:64-66`) уже делегирует в базовую реализацию, которая смотрит в `_baseStats`.
Комментарий в `EquipItemBlueprint.cs:16` говорит «non-weapon equip», но код к слоту не привязан —
комментарий стоит поправить.

Раскладка при (б), `Tflat = 0.16`, `Tinc = 1.00`, база-канал 4 слота × 0.035 = 0.14,
аффикс-канал 4 × 0.025 = 0.10 (не растёт от заточки):

| Сборка | Итог |
|---|---:|
| Дерево одно | 0.42 |
| Дерево + Legendary без заточки (базы 0.14 + аффиксы 0.10) | (0.21+0.24)×2.00 = **0.90** — уже за капом |

Не сходится: при (б) незаточенный базовый канал слишком велик. Значит при (б) бюджет надо
перераспределить жёстче — **убрать AHC из семейных суффиксов вовсе** и оставить его только в базах:

| Сборка (вариант «б», AHC только в базах) | `G` | Итог |
|---|---:|---:|
| Дерево одно | 0 | **0.42** |
| Дерево + 2 слота с базой AHC, без заточки | 0.070 | **0.56** |
| Дерево + 4 слота с базой AHC, без заточки | 0.140 | **0.70** |
| Дерево + 4 слота, +12 (×1.60) | 0.224 | 0.87 → **кап** |
| Дерево + 3 слота, +12 | 0.168 | **0.756** ≈ кап ✔ |

То есть при (б) целевая точка — **три слота с базовым AHC, заточенные до +12**, а базовые диапазоны
надо ужать примерно до 0.015–0.035 (среднее 0.025), чтобы четвёртый слот не выносил вилку.
Ровные цифры при (б): базы 4 × 0.025 = 0.10 без заточки → `0.31 × 2.00 = 0.62`;
на +12 → `0.16` → `0.37 × 2.00 = 0.74` ≈ кап. Тот же результат, что и в §4.3, только канал другой.

**Вывод по развилке:** какую бы схему ни выбрал владелец, числа сходятся одинаково —
`Tflat = 0.16`, `Tinc = 1.00`, суммарный «затачиваемый» AHC на сете ≈ 0.10 без заточки.
Разница только в том, в каком канале эти 0.10 лежат: при (а) — в суффиксах, при (б) — в `baseStats`.

## §5. Что осталось за границей заказа (для сведения)

* `src/Docs/TreeV2-Clusters.md:349` и `:407-408` описывают кластеры доп-атаки значениями, которых
  в текущем `PassiveTree.json` нет (например «нотабл `MulticastChance Flat 0.04` + `AdditionalHitChance
  Flat 0.04`»). Похоже, это проектные заготовки V2, а не снимок данных — при сверке цифр опираться
  надо на JSON.
* Ноды `notable_evade_7`, `small_evade_1..4` несут `AdditionalHitChance` под заголовком «Evade»,
  а `small_evade_5` — нет. Кандидат в опечатку данных; дерево правит владелец.
* Локальная строка `Increase` на параметре без базы и без плоского локала даёт ноль
  (`EquipItem.cs:356-360`). В пулах такие сочетания встречаются (например `FireDamage Increase`
  на амулете, у которого нет ни базы огня, ни гарантии плоской строки). Отдельная тема.
