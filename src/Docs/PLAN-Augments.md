Черновик 2026-08-09. Основание: два разведотчёта (карта реализации + сверка с `02_Стойки/Аугменты.md`; транзитивность), решения владельца 2026-08-09 (см. `docs/decisions.md`). Ведёт основной агент; задачи ставятся по одной, ревью на каждую.

**Транзитивность** работает только там, где способность сама рождает эффект, читая свой `AbilityParameterSet` (PoisonCoating, JarOfPoison). Разрывы: `AbilityImpact` не несёт способность; числа райдеров приколочены в конструкторах; эффекты — снапшот при наложении; следа способности на эффекте нет; `nameof`-коллизии (`Duration` ×6, `Attacks` ×2, `PoisonDuration` ×2) заставляют аугменты продлевать чужие бафы и душить друг друга соперничеством.

## 2. Решения владельца (рамки, не пересматриваются здесь)

1. Транзитивность **поэтапно**: канал (райдер видит способность, ленивые фабрики эффектов) → отдельной волной след (AbilityId/CastId на эффекте).
2. **Общие ключи** `AbilityParameter` + регистрация владельцем понятия; приватные остаются именному.
3. **Поведение из данных** для обобщаемых (реестр behaviour + effectId + properties); именные — кодом.
4. Ранее: соперничество/цена — пересматриваются этим проходом (тай-брейк Replace произволен; «проигравший дар платит цену»); значок спящего аугмента ждёт штампа адреса сокета.

- G-3. Пол «не ниже 1» у снижения перезарядки (`AbilityUpgradeReduceCooldown`).
- G-4. `SpawnNpcAction.ResolvePosition` — перечислять зарегистрированные id точек в отказе (из бага Trial_Ground).
- G-5. **Переименования классов и id по необходимости (решение владельца 2026-08-09): имя соответствует реальности.** Общий аугмент не носит префикс способности: `PcUpgradeExtendExistingPoison`/`IpUpgradeExtendPoison` → общий `AugmentExtendPoison` (продление яда — аугмент ЛЮБОЙ атакующей способности, не уникум Poison Coating/IP); по мере генерализации волн A–C правило применяется ко всем «Xx*Upgrade*»-классам, чьё поведение перестало быть именным. id записей каталога — так же (сейвы сокетов ломаем по действующему правилу).

### Волна A — канал «способность ↔ рождение эффекта» (решение 1, шаг 1)

**Несущий инвариант волны (владелец, 2026-08-09): единица работы райдера — ИМПАКТ, а не каст и не только атака.** Импакт = каждое фактическое касание любой доставки: атака серии, прямой хит, снаряд, прыжок цепи, каждая цель мульти-target'а. Отсюда композиция аугментов обязана получаться АРИФМЕТИКОЙ, без специального кода на пару:
- «хиты накладывают яд» + «дополнительные снаряды» (+2) = Ice Shards кладёт на 2 стака яда больше — потому что райдер отработал на каждом снаряде;
- то же + «усиление/длительность яда» = каждый стак усилен — потому что фабрика эффекта ленива и читает декорированный `AbilityParameterSet` (A-3);
- «наложение эффекта при хите» + «усиление накладываемых эффектов» + «хиты по всем противникам» = эффект на каждом противнике, усиленный — те же два механизма, помноженные на число целей.

- A-1. Контракт: импакт-райдер получает способность (расширение `AbilityImpact` или сигнатуры `IImpactRider.Apply`) — единая правка всех реализаций + обёрток. **Импакт несёт РОД касания** (атака / хит / снаряд / прыжок) — райдер и поведение волны C фильтруют по роду: дизайн-список различает «Атаки» и «Удары» как разные теги.
- A-2. `ApplyImpactRiders` уезжает в общий путь доставки ВСЕХ трёх родов (Attacks / HitSequence / Multicast-планы; сегодня 12 способностей не зовут его вовсе — D-2, а у зовущих пер-импактность не доказана). **DoD волны: комбинаторные тесты** — «N снарядов → ровно N применений райдера», «прыжок цепи = импакт», «мульти-цель = импакт на цель», «+2 снаряда через аугмент → +2 наложения яда».
- A-3. Фабрики эффектов райдеров становятся ленивыми: числа читаются из `AbilityParameterSet` в момент наложения (прецедент `AbilityUpgradeCastEffect`); «Ядовитая серия атак» — эталонный переезд + тест «податель + усилитель складываются» и «податель + усилитель + доп. снаряды = N усиленных стаков».

### Волна B — общие ключи (решение 2)
- B-1. Расширение `AbilityParameter`: `AppliedEffectDuration`, `AppliedEffectiveness`, `AppliedEffectStacks`, `AttackCount`, `ProjectileCount`, `Charges`, `ShieldStrength` (список сверить со списком владельца); регистрация — владельцем понятия (способность/семейство).
- B-2. Переезд существующих приватных ключей-дублей на общие (`Duration` ×6, `Attacks` ×2, `PoisonDuration` ×2 …); идентичность соперничества выправляется сама (один честный ключ вместо коллизии).
- B-3. Переезд 47 строк `_parameterAugments` + записи списка владельца, ставшие выразимыми (счёт из таблицы сверки).

### Волна C — поведение из данных (решение 3)

**Даруемые теги (решение владельца 2026-08-09): установленный аугмент добавляет способности теги — но не теги подгонки, а отдельно объявленные ДАРУЕМЫЕ** (обычно род накладываемого эффекта: податель яда дарит `poison`; усилитель не дарит ничего — иначе усилители бутстрапят друг друга без подателя). Эффективные теги способности = базовые ∪ даруемые установленными аугментами; читает их ТОЛЬКО `AugmentFit` (единственная точка подгонки сохраняется). Извлечение подателя НЕ выбрасывает севших по его тегу усилителей — они остаются и молчат (прецеденты: «слот переживает потерю узла», «тег обещает подгонку, не работу»). Это звено, без которого транзитивные комбо не собираются на способности без родного тега.
- C-1. Общий провайдер эффектов с properties (расширение `GrantEffectProvider`-подхода: 6 эффектов → нужный набор; `BleedEffect` завести — его нет вовсе).
- C-2. Реестр behaviour («наложить-на-импакт», «баф-на-каст», «контекст-модификатор атак») → запись данных вместо лямбды; **запись behaviour декларирует РОД импакта** (только атаки / только хиты / любой — по различию «Атаки»/«Удары» в дизайн-списке); перевод 33 обёрточных записей; «Кровавая серия атак» — эталонная новая запись без кода.
- C-3. Хвост данных: `rarity` (авторская, по списку владельца), `exclusionGroup`, лут-группы аугментов в таблицы (баланс — с Monte-Carlo перегоном).

### Волна D — след способности на эффекте (решение 1, шаг 2)
- D-1. `AbilityId`/`CastId` на `IEffect` + контексты применения; «продлить/усилить СВОЙ яд» (сегодня продлевается любой, включая чужой).
- D-2. Пересмотр соперничества: тай-брейк `Replace`-направления, «проигравший дар платит цену», отчёт способности о победителе на сокет → UI-заглушка `ActivityOf` оживает (значок спящего).

### Волна E — сверка каталога со списком владельца
- E-1. Добавление недостающих позиций списка на новых механизмах (щиты, заряды, снаряды/цепи, эффективность бафа/дебафа…); капстоун-орнаменты (P-09 из шага 14) — сюда же или отдельно, по решению владельца.

## 4. Открытые вопросы владельцу (соберутся при декомпозиции волн)

1. Волна G: судьба каждой из 12 мёртвых записей — таблица будет предъявлена при постановке G-1. *(закрыто в G-1)*
2. Точный список общих ключей B-1 — сверю с `Аугменты.md` и предъявлю. *(закрыто в B-1/B-3: 10 ключей)*
3. P-09 (орнаменты) — до прохода или внутри волны E?
4. **Из B-3 (2026-08-10):** «Эффективность дебафа» некуда посадить — тег `debuff` не носит ни одна способность книги и ни одна не читает эффективность своего дебафа; раздать тег + чтение (Глыба, Эгида, Заморозка, Двойной удар) или ось дебафа ждёт волны C?
5. **Из B-3:** пример «Эгида жизни 54% вместо 35%» требует множителя ≈1.543, а дизайн-строка «Эффективность восстановления» объявлена 10–35%; отгружен потолок строки — 0.35×1.35 = 47.25%. Поднимать ли диапазон строки до 54%?
6. **Из B-3:** значения накладываемых дебафов (`Withering_Value`, `ClumsinessValue`, `FrostbiteColdAmp`) — кандидаты в чтение `Effectiveness`, но у каждой способности таких чисел два-три: какое множится — дизайн-вопрос той же природы, что отложенный «Длительность накладываемых эффектов» (волна C).
7. **Из B-3:** `Augment_Buff_Effectiveness` инертна на шести буфф-способностях (Арес, Эгида, Покрытие, Дикобраз, Жертва, Доспех) — законно, но список велик; доводить ли их до владения `Effectiveness` в волне E?
