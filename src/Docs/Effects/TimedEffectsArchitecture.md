# Временные эффекты: расширение системы бафов и дебафов

Статус: архитектурный проект для реализации, 23.09.2026. Игровые правила согласованы; новые контракты ниже — техническое предложение, а не существующие API.

Документ дополняет [архитектуру используемых предметов](../Items/UsableItemsArchitecture.md). Флаконы находятся на стадии дизайна. Здесь проектируется механизм эффектов, а не конкретный баланс или генерация предметов.

## 1. Цель и границы

Добавить эффекты с длительностью в игровых минутах и масштабируемых секундах активной игры, сохранив эффекты на ходы. Все виды остаются в одном EffectsComponent, используют общие правила силы, стаков, снятия и представления.

Первая реализация поддерживает изменение характеристик, скорость перемещения, периодическое восстановление HP/MP/барьера и периодический урон. Получатель новых минутных эффектов — игрок. NPC продолжают пользоваться существующими боевыми эффектами; сохранение минутных эффектов NPC и их симуляция в выгруженных локациях не входят в задачу.

Источники первой интеграции — используемые предметы игрока. Наложенный эффект не требует существования флакона: предмет может закончиться, переместиться или удалиться. Отдельный NPC-кастер, перенос минутного эффекта на другого носителя и автономные ауры не добавляются без отдельного сценария.

## 2. Подтверждённые правила

| Область | Правило |
| --- | --- |
| Время | Есть эффекты на ходы, игровые минуты и секунды активной игры. Ускорение игры ускоряет отсчёт минутных эффектов. |
| Остановка | Пауза, главное меню и закрытая игра не расходуют длительность. Нет offline-прогресса. |
| Бой | Минутные эффекты действуют и отсчитываются во время боя. Правило единое, флага заморозки отдельного эффекта нет. |
| Периодические действия | Интервал измеряется тем же временем, что и длительность. Учитываются все прошедшие срабатывания, включая ускоренное время. |
| Смерть | Минутные эффекты не снимаются. Срок идёт; лечение и урон по мёртвому пропускаются без накопления. После воскрешения неистёкший эффект снова действует. |
| Урон в мире | Может убить игрока вне боя. |
| Сохранение | Минутные эффекты и оставшееся время восстанавливаются из сейва. |
| Бонусы длительности | Существующие прибавки и множители длительности действуют только на эффекты в ходах. |
| Рассеивание | Охватывает также минутные эффекты, сохраняя EffectPower и DispelScope. Absolute не снимается обычным рассеиванием. |
| Повтор | Текущая политика EffectsComponent: сильный одиночный экземпляр заменяет старый; равный/слабый обновляет срок без сокращения. Повтор бафа расходует предмет/заряд. |
| UI | Существующие панели эффектов; явные единицы времени. |
| Акторы | Минутные эффекты первой реализации принадлежат игроку; аналогичные бафы NPC не требуются. |

«Смерть не снимает» не означает заморозку срока: эффект может закончиться до воскрешения, особенно при ускоренном посмертном ожидании.

## 4. Архитектурное решение

Разделить поведение (что делает эффект), время (срок и следующее срабатывание) и жизненный цикл (переходы, снятие, восстановление).

EffectsComponent — единственный владелец живых экземпляров. Планировщик хранит регистрацию владельца и временные курсоры, не второй список эффектов. Каталог и фабрика остаются единственной дорогой создания. Отдельная система «бафов от флаконов» не нужна.

Новые временные классы не наследуются от RegenerationEffect/DamageOverTurnEffect с подменой Duration: у них уже есть побочные действия на TurnEnd. Общие формулы извлекаются в небольшие операции.

### 4.1. Предлагаемые сущности

| Сущность | Ответственность |
| --- | --- |
| `EffectTimeKind` enum | OwnerTurns, GameMinutes, ScaledSeconds, Permanent. Последний представляет существующие бессрочные эффекты, не новые минутные бафы. |
| `EffectLifetimeDefinition` | Kind и Duration: положительное число для конечного срока, целое для OwnerTurns, отсутствует для Permanent. |
| `EffectTimingState` | Остаток ходов либо ExpiresAt в своих часах, NextTickAt, TickIndex, временная ревизия. Меняется только доменными операциями. |
| `EffectLifetimeScope` enum | Battle, Session, SourceOwned. Определяет очистку, а не единицу. Минутные эффекты этой версии — Session. |
| `EffectRemovalReason` enum | Expired, Replaced, Dispelled, BattleEnded, SourceDetached, SessionReset. Отмена тиков больше не зависит от Duration > 0. |
| `EffectTimeSnapshot` | Kind, Remaining, ClockValueAtCapture, Revision для UI, без ссылки на живой эффект. |
| `IEffectTimeSource` / `EffectTimeSource` | Сессионный сервис: GameMinutes из IWorldClock, собственный ScaledSeconds; reset/restore, без UTC. |
| `TimedEffectsDriver` | Единственный адаптер Godot активной сессии. Передаёт продвижение времени; живёт над локациями, по одной регистрации в Main и Battle-песочнице. |
| `TimedEffectScheduler` | Чистый планировщик сроков, периодических действий, обработанного горизонта и поколений сессии. Сам не меняет HP. |
| `IPeriodicEffect` | ExecuteTickAsync(EffectTickContext) и интервал, не привязанные к концу хода. |
| `EffectTickContext` | InstanceId, TickIndex, scheduled time, момент обработки; идентичность срабатывания против дублей. |
| `IEffectApplicationService` | Prepare, Commit/Rollback плана наложения, восстановление без повторного Apply; использует фабрику и EffectsComponent. |
| `EffectApplicationPlan` / `EffectApplyResult` | План со старым/новым состоянием и ревизией; результат Added/Replaced/Refreshed/Rejected. План может содержать несколько стаков. |
| `TimedParameterEffect` | Параметры через существующие декораторы. MoveSpeed — обычный параметр, не новый контроллер движения. |
| `TimedResourceRecoveryEffect` | Периодические HP/MP/барьер через общие доменные операции. |
| `TimedDamageEffect` | Периодический урон с заданным DamageType; Genus=Damaging, IsHarmful=true. |
| `ActiveEffectSaveData`, `ActiveEffectsSaveParticipant` | Секция минутных эффектов игрока, восстановление до Vitals. |
| `EffectClockSaveParticipant` | Сохраняет ScaledSeconds; GameMinutes уже сохраняет WorldClockSaveParticipant. |

Размещение: единицы, контракты и планировщик — Core; конкретные эффекты/фабрики — Battle/Source; Godot-адаптер — композиция Main и Battle. DTO остаются Core/Data/EffectsData, редактор — EffectsCatalogDescriptor.

### 4.2. Переход существующих API

Добавить в IEffect Timing, LifetimeScope, типизированный снимок времени и снятие с причиной. На переходный период Duration и Extend(int) остаются только фасадом OwnerTurns для старых фабрик/способностей. Нельзя выдавать из Duration секунды или фиктивное 999: обращение для минутного экземпляра — ошибка контракта. Для прежних бессрочных экземпляров переходный адаптер сохраняет используемое фабрикой представление Permanent, пока их Copy/TurnEnd не переведены на Timing; это не применяется к новым минутным классам.

Общие потребители (stacking, UI, expiry, remove, сериализация) переводятся на Timing до включения минутных данных. Потребители боя сначала проверяют Kind == OwnerTurns. Двух независимо изменяемых значений срока быть не должно.

TriggerTurnStart/End не вызывает callbacks минутных эффектов. Старые Permanent-эффекты, реагирующие на ход, продолжают получать их. Правило свежести текущего хода относится только к OwnerTurns.

Ограничить DurationScale, DurationBonus, Extend, перенос и продление боевых эффектов. Сопротивление контроля и округление в ходах не обрабатывают минутные классы. Полный запрет наложения остаётся отдельной проверкой; минутные контрольные статусы в эту версию не входят.

## 5. Семантика времени

### 5.1. Единицы и ускорение

| Kind | Срок в данных | Часы | Пример |
| --- | --- | --- | --- |
| OwnerTurns | Целое число ходов | Конец хода владельца | 3 хода |
| GameMinutes | Игровые минуты, допускается дробь | IWorldClock.TotalMinutes | 20 игровых минут |
| ScaledSeconds | Секунды активной игры при ×1 | EffectTimeSource.ScaledSeconds | 120 секунд при ×1; 60 фактических секунд при ×2 |
| Permanent | Без числового срока | Нет отсчёта | До снятия источником |

Термин «реальное время» в требованиях включает ускорение игры. В API поэтому используется ScaledSeconds, в редакторе — «секунды при ×1, зависят от скорости игры». Это не wall clock. Изменение длины игрового дня меняет отношение GameMinutes к ScaledSeconds, а глобальное ускорение меняет скорость обеих шкал.

Часы получают delta, уже масштабированную Engine.TimeScale, ровно один раз. Не умножать её повторно. Если ускорение вынесут в сервис симуляции, оба потребителя получают масштабированную delta из единой точки.

В Main скоординировать TimedEffectsDriver с NpcWorldDirector: WorldClock.Tick вызывается один раз за кадр; затем фиксируется пара времён и запускается обработка эффектов. Планировщик не тикает WorldClock повторно. В бою драйвер остаётся активен в сессии, не переносится на арену с игроком.

Пауза останавливает обе шкалы. В меню драйвер отключён; возврат не восполняет отсутствовавшие кадры. Загрузка и переход между сценами — техническая приостановка, их длительность не списывается. Обычные окна, не приостанавливающие игру, эффект не останавливают.

### 5.2. Отличие от cooldown предметов

В архитектуре предметов IRealtimeSessionClock предложен для немасштабируемой реальной перезарядки. Он не подходит для ScaledSeconds: новое требование ускорения относится к эффектам. Драйвер может обслуживать оба счётчика, но значения, контракты и поля сейва различаются. Перезарядка флаконов в эту задачу не добавляется.

### 5.3. Продвижение и восстановление

Планировщик принимает продвижение от предыдущей пары времён к новой. RestoreTime при загрузке — не продвижение: в LoadScope обработка остановлена, старые регистрации очищены, после загрузки курсор устанавливается на восстановленное время без тиков.

MinutePassed не означает «выполни один тик»: оно может перескочить много минут. Планировщик сравнивает сроки с точным TotalMinutes.

Для будущего явного пропуска времени потребуется отдельная AdvanceSimulation с согласованным продвижением обеих шкал. Использовать RestoreTime для сна/ожидания нельзя. Существующее посмертное ускорение через Engine.TimeScale уже продвигает обе шкалы; отдельная система сна здесь не проектируется.

## 6. Создание и наложение

### 6.1. Данные → экземпляр

1. GameDataService читает EffectsData через существующий источник и EffectCanonCatalog.
2. Валидатор проверяет определение и возможности фабрики: единицы, числа, периодические каналы, сохранение.
3. Источник передаёт EffectId и зафиксированные роллы экземпляра предмета. Эффект не роллит повторно.
4. EffectProvider создаёт отделённый от владельца кандидат с точными значениями и спецификацией времени.
5. ApplicationService проверяет игрока, контекст, время, пайплайны и стаки. Исходящие преобразования и входящий отказ рассчитываются без изменения носителя; бонусы длительности пропускают минутного кандидата.
6. План фиксирует величины, силу, источник, статус, решение стаков и зависимые изменения параметров. Начало срока определяется временем фиксации, не открытия тултипа.
7. После commit экземпляром владеет EffectsComponent, декораторы действуют, планировщик видит срок; только затем отправляются уведомления.

Предлагаемый `EffectOrigin`: ActorId, ItemDefinitionId, ItemInstanceId, UseId для диагностики. Source — доменная идентичность источника, но уникальный UseId не расширяет stack cap. В текущем объёме Caster и Target минутного эффекта — игрок. Эффект не держит ссылку на Node предмета.

### 6.2. Предметы и атомарность

В проектируемых действиях предмета заменить узкий ApplyBattleEffectItemAction общим `ApplyEffectItemAction`. Единица принадлежит определению эффекта, действие не конвертирует минуты в ходы. Если к моменту реализации появятся данные со старым type, читать его как совместимый alias.

Текущий Effect.Apply нельзя вызывать в Prepare: он уже меняет стаки/статусы/подписки, публикует события, отдельно применяет bonus stacks. Требуется разделить расчёт и активацию для поддерживаемых действий.

- Prepare проверяет весь пакет предмета, создаёт кандидатов и undo-состояние: старые экземпляры, сроки, модули, затрагиваемые виталы. Уведомлений нет.
- Общая область использования резервирует заряд/предмет и получает последовательный доступ к игроку. План содержит revision эффектов/параметров; устаревший план перестраивается до списания.
- Commit устанавливает экземпляры, модули и сроки, списывает ресурс и фиксирует остальные действия. При техническом отказе до публикации восстанавливает старое состояние, включая NextTickAt и виталы.
- Планировщик и внешние наблюдатели видят изменения только после общей успешной фиксации. Подписчик первого уведомления видит законченный результат.
- Реакции на опубликованный EffectAppliedEvent исполняются после commit как отдельные действия; их ошибка не отменяет объявленный успех предмета.

Это проектируемый протокол, а не обещание транзакционности любого старого Effect.Apply. Фабрика без поддержки Prepare/Commit/Rollback не допускается в такое item action; валидатор объясняет отказ. «Попробовать Apply и удалить обратно» после событий недопустимо.

Bool AddEffect не становится ответом предмета. Refreshed — успех, даже если срок уже длиннее входящего и численно не увеличился. Rejected не расходует предмет и не увеличивает факты. Тики, истечение и восстановление не являются использованием предмета.

## 7. Стаки, сила и идентичность

Один EffectId имеет один TimeKind, LifetimeScope, схему интервала и правило силы. Источник не переопределяет единицу; роллить можно срок и силу. То же поведение в другой единице получает отдельный id. Поэтому stack cap, группировка UI по Id и сравнение сроков остаются осмысленными без конверсии ходов в секунды.

- Один стак: сильный кандидат заменяет старый и получает собственный полный срок, как сейчас. Продление старого срока при сильной замене не добавляется.
- Равный/слабый: сила сохраняется; ExpiresAt = max(старый ExpiresAt, now + входящий срок). Сроки не складываются.
- Несколько стаков: до cap добавляется экземпляр, на cap обновляется ближайший к истечению. Разные роллы не схлопываются в «количество × сила последнего».
- Refresh сохраняет фазу NextTickAt: повторное питьё не откладывает тик и не создаёт немедленный дополнительный. Замена начинает новую фазу.
- Истёкшие к моменту команды экземпляры обрабатываются раньше сравнения. Refresh не воскрешает истёкший эффект.

У TimedParameterEffect декораторы принадлежат InstanceId; снятие не затрагивает другой стек/экипировку. Формулы OperationType и форматирование переиспользуются. Старые боевые классы не меняют stacking случайной общей правкой.

IsStronger определяет фабрика. Для нескольких параметров нельзя суммировать несопоставимые HP и MoveSpeed: задаётся приоритет силы либо частичный порядок «не слабее по всем, сильнее хотя бы по одному». Несравнимый кандидат по умолчанию обновляет время без замены; фабрика обязана явно объявить это правило. Конкретные балансные векторы флаконов ещё не определены.

## 8. Периодические действия

### 8.1. Расписание

Техническое предложение: первое срабатывание через interval после наложения, немедленного тика нет. Для лечения сразу и затем постепенно у предмета два явных действия. При NextTickAt == ExpiresAt последний тик выполняется, затем эффект снимается. Неполный остаток интервала не создаёт частичного тика.

1. Найти ближайший тик/истечение между обработанным курсором и фиксированным горизонтом времени.
2. Проверить поколение сессии, регистрацию, InstanceId, timing revision и наличие эффекта.
3. Для живого владельца выполнить и дождаться действия. Для мёртвого пропустить полезную нагрузку, но продвинуть TickIndex/NextTickAt.
4. Действия на одном времени упорядочить по сохранённому порядку наложения и номеру стека. Результат каждого виден следующему.
5. На общей границе сначала тики, затем истечения. После каждого тика проверить жизнь и состав эффектов заново: реакция могла убить, рассеять или заменить их.
6. Продвинуть курсор. Завершённое срабатывание не повторяется в следующем кадре.

Для двух шкал порядок внутри продвижения определяется долей отрезка `(due - previous)/(current - previous)`, а не сравнением игровых минут с секундами. Непродвинувшаяся шкала не даёт новых сроков; равные доли разрешаются стабильным порядком. Refresh/удаление/загрузка инвалидируют подготовленное событие ревизией; оно пересчитывается из актуального состояния без потери фазы.

Нельзя заменить десять тиков на `amount × 10`: между ними возможны смерть, изменение максимума, лечение и рассеивание. Можно объединить только визуальные уведомления после расчёта.

Большой шаг обрабатывается частями с техническим лимитом работы на кадр, без отбрасывания долга. До достижения фиксированного горизонта новые команды и сейв ждут. Часы накапливают следующее продвижение, не удлиняя бесконечно текущий пакет. Для мёртвого владельца пустые интервалы можно пересчитать арифметически до ближайшего истечения/воскрешения.

### 8.2. Полезная нагрузка

- **Характеристики:** декораторы подключаются/снимаются один раз. MoveSpeed читает существующее движение. Повышение MaxHealth/MaxMana/MaxBarrier само по себе не заполняет ресурс; снижение ограничивает текущий остаток новым максимумом без лечебного события. Нельзя авторить недопустимый максимум; истечение обычного бафа максимума не должно создавать нулевой MaxHealth.
- **HP:** HealContext / IFightable.Heal, с запретами, конверсиями и реакциями. Доля считается от актуального максимума на каждом тике. Текущий Heal может отправить конвертированный урон fire-and-forget: выделить общую awaitable-операцию и дождаться результата, чтобы смерть завершилась до следующего тика.
- **MP:** ManaRecoveryContext / IFightable.RestoreMana; фактическое восстановление определяется после клампа.
- **Барьер:** общего RestoreBarrier в IFightable сейчас нет. Добавить узкую общую операцию восстановления с клампом к MaxBarrier и снимком изменения; использовать её в периодических эффектах. Не объявлять несуществующий контекст уже готовым.
- **Урон:** DamageContext с DamageCause.Effect → TakeDamage; сохранить митигацию, поглощение, реакции и порядок «урон → смерть». Величина/тип задаются данными, не рассчитываются от вымышленной атаки. Процентный урон, если поддержан фабрикой, явно указывает базу; начальный пример использует фиксированный урон.

Для вредного эффекта собственного предмета источник — сам игрок. В текущих damage-модификаторах есть фильтры Source == owner против двойного исходящего/входящего применения. Не обходить их подставным NPC. Сохранить существующую семантику самоурона и проверить тестом; общее изменение правил самоурона — отдельное балансное решение.

Лагерь остаётся зоной RestRecoveryService, не скрытой второй копией бафа. В мировом кадре сначала обрабатывается долг эффектов, затем восстановление зоны; мёртвый игрок зоной не воскрешается. Исторический поминутный пересчёт всех мировых систем не входит в эту задачу.

## 9. Работа в бою и согласованность

Предлагаемый `EffectExecutionGate` — один последовательный исполнитель для игрока/его активного боя. Пакеты времени и команды не меняют одного носителя одновременно. Он работает на основном потоке и не удерживает блокировку потока на время анимации. Если к реализации уже появится общий исполнитель BattleActionService из смежной архитектуры, gate встраивается в него: две независимые очереди команд и эффектов недопустимы.

### 9.1. Ожидание ввода

1. Драйвер фиксирует время, планировщик обнаруживает due-действия.
2. Если нет исполняющегося игрового действия, пакет получает gate и изменяет состояние, не ожидая конца хода.
3. CombatEvents пишет в BattleTimeline, BattleDirector показывает события обычным путём.
4. Смерть отменяет ожидание выбора/прицеливания, боевой цикл видит исход. После await нельзя продолжать атаку или OnTurnEnd уже недопустимого участника.
5. Даже если запрос UI уже отправлен, под gate сначала обрабатываются сроки на момент запроса, затем повторно проверяются актор, цель и доступность.

### 9.2. Resolve и replay

Предлагаемая граница: уже начатый логический пакет (в текущей реализации — вплоть до всего разрешаемого хода) завершается без вмешательства таймера. Часы идут. Наступившие за resolve/replay тики и снятия исполняются следующим пакетом после уже записанного показа и до следующей команды/начала хода. Рассчитанный урон задним числом не меняется.

Обработки только на старте/конце хода недостаточно: игрок может не выбирать цель минутами. Нужен самостоятельный wake-up очереди при ожидании ввода и при освобождении gate.

Пакет имеет фиксированный watermark времени. Новые накопления не продлевают текущий пакет; команды и следующие пакеты получают очередь в определённом порядке. На границе команды сначала обработать временные события, уже наступившие к её приёму. Периодический визуал должен быть коротким/объединяемым, без обязательного Hurt-клипа на каждый исторический тик, иначе частый DoT создаст бесконечный хвост анимаций. Доменный урон и реакции не объединяются.

Перед завершением боя обработать зафиксированный долг, проверить исход заново, показать смертельные события, затем очистить Battle-эффекты. Следующие сроки принадлежат мировому контексту. Перед BattleInitialized тоже сверить сроки: просроченный баф не входит в начальный снимок.

## 10. Смерть, выход из боя, переходы

### 10.1. Смерть вне боя

Смертельный тик → TakeDamage → уведомление смерти → единый обработчик жизненного цикла игрока.

Выделить предлагаемый идемпотентный вход `EnterDefeatedState` из BeginDeathRest:

- В бою он вызывается после корректного завершения и показа, как сейчас; до этого смерть сообщает исход арене.
- В мире — после завершённого смертельного урона. Idle/Walk должны разрешать переход в Dead.
- Повторные PlayerDiedEvent/EntityDiedEvent и BattleEndEvent не создают второй PlayerLifecycle или второй обработчик воскрешения.
- Смерть отменяет взаимодействия и незавершённые запросы использования. Завершённое действие не откатывается.
- Session-эффекты не удаляются. По мёртвому пропускаются периодические действия; срок ускоряется вместе с посмертной симуляцией.
- Перед установкой ресурсов воскрешения обработать истечения до текущего времени, пересчитать максимумы, затем применить ReviveHealthPercent/ReviveManaPercent. Пропущенные тики не восполняются.

Декораторы неистёкшего бафа остаются на мёртвом носителе и сами не оживляют его. Окончательная смерть сохраняет состояние до выхода/загрузки; завершение сессии снимает его как SessionReset без наград.

Во время догоняющего пакета смерть учитывается сразу для последующих тиков. Воскрешение не может вмешаться посередине пакета: уведомление готовности жизненного цикла ставится в тот же последовательный исполнитель. К его обработке пропущенные по мёртвому интервалы уже отмечены, поэтому их нельзя исполнить задним числом по воскресшему.

### 10.2. Очистка

Заменить RemoveAllEffects в конце боя на явное завершение боевого lifetime. Для старых эффектов сохранить текущую очистку; минутные Session не затрагиваются. SourceOwned-грант принадлежит экипировке и не входит в сейв минутных эффектов. Его существующая схема повторного применения допустима для прежних боевых грантов; она не должна удваивать пережившие бой экземпляры.

RemoveAllEffects остаётся для уничтожения владельца/сброса сессии и явно тотальных служебных команд. Трансформация босса не становится «концом боя» механически: это другая причина очистки, а новых минутных эффектов NPC здесь нет.

Переход локации сохраняет компонент игрока. Если необходима новая нода, передать capture/restore состояния один раз с unregister старого владельца; вход в дерево не означает Apply. Регистрация хранит generation сессии, не только InstanceId ноды.

## 11. Сохранение и новая игра

Сохраняются Session-эффекты минутных видов. Экипировочные гранты восстанавливаются своим механизмом. Боевые эффекты не добавляются в сейв; текущий запрет сохранения в бою/при смерти остаётся.

| Поле ActiveEffectSaveData | Содержание |
| --- | --- |
| version, effectId, instanceId, applicationOrder | Версия, определение, стабильная идентичность и порядок стека. |
| kind, remaining | Единица и точный остаток double, не UTC. |
| nextTickIn, tickIndex | Остаток до следующего тика и выполненный номер; null для непериодического. |
| resolvedPayload | Конкретные числа характеристик/урона/восстановления, interval и сравнимая сила после роллов/пайплайнов. |
| origin, status, power, maxStacks | Источник и правила активного экземпляра. |
| payloadVersion | Версия схемы поведения для валидации/миграции. |

Snapshot собирается после DrainTo(capturedTime) под тем же gate. Во время Capture часы, эффекты и виталы не меняются. Срок на точной границе сохранения сначала исполняет тик/истечение, затем проверяется CanSave: смертельный тик отменяет сохранение. Незавершённые Task не сериализуются.

### Порядок восстановления

1. LoadScope останавливает часы, команды и игровые уведомления. Очистить прежние экземпляры, регистрации, пакеты.
2. Восстановить WorldClock и ScaledSeconds. Нет новой clock-секции — начальное значение; остатки всё равно ребазируются от восстановленного now.
3. Восстановить мастерство, дерево, предметы, способности и стойку штатным порядком.
4. Добавить RestoreOrder.ActiveEffects между Stance=40 и Vitals=50, предлагается 45. Фабрика восстанавливает точные данные без RNG, Apply-пайплайнов, bonus stacks и списания предмета. ExpiresAt = now + remaining; NextTickAt = now + nextTickIn.
5. Восстановить декораторы, пересчитать максимумы; затем штатный Vitals.
6. По завершении всех участников опубликовать согласованный снимок параметров/эффектов, установить горизонт планировщика, разрешить обычное время.

Restore не порождает новое EffectApplied, лечение, факты использования, опыт или квестовые действия. Это восстановление состояния, не повтор истории.

Проверять NaN/Infinity, отрицательные остатки, interval <= 0, duplicate instanceId, несовместимую единицу, пропавшую фабрику и payloadVersion. Истёкшая запись не активируется. Неизвестное определение/схема — диагностируемый пропуск конкретного эффекта, допустимый для прототипа; не молчаливое создание с новыми числами. Старый сейв без секции даёт пустой список.

Новая игра очищает эффекты, счётчики, ревизии и очередь. Generation меняется: поздняя асинхронная операция старой сессии не может наложить эффект в новой.

## 12. Авторинг и валидация

Остаётся каталог Effects; добавить типизированные lifetime и необязательный periodic. Enum не кодируется числом в properties. Численные параметры фабрики остаются в properties.

Пример предлагаемой формы. Числа и id демонстрационные, не утверждённый баланс и не рабочие данные:

```json
{
  "effects": [
    {
      "id": "Effect_Timed_Fleetness",
      "power": "Weak",
      "lifetime": { "kind": "ScaledSeconds", "duration": 120 },
      "properties": { "maxStacks": 1, "moveSpeedMultiplier": 1.2 }
    },
    {
      "id": "Effect_Timed_Recovery",
      "power": "Weak",
      "lifetime": { "kind": "GameMinutes", "duration": 10 },
      "periodic": { "interval": 1 },
      "properties": {
        "maxStacks": 1,
        "healthPercent": 0.02,
        "manaPercent": 0.02,
        "barrierPercent": 0.01
      }
    },
    {
      "id": "Effect_Timed_Toxicity",
      "power": "Weak",
      "lifetime": { "kind": "ScaledSeconds", "duration": 30 },
      "periodic": { "interval": 5 },
      "properties": { "maxStacks": 1, "damage": 8 }
    }
  ]
}
```

Фабрики примера: Fleetness → TimedParameterEffect с EntityParameter.MoveSpeed/Multiply; Recovery → TimedResourceRecoveryEffect с тремя каналами; Toxicity → TimedDamageEffect с DamageType.Poison. Связь id с классом/параметрами остаётся в EffectProvider. Свободные наборы характеристик без отдельной фабрики — возможное последующее расширение схемы, не обязательный универсальный движок действий внутри эффекта.

Запись с lifetime не задаёт одновременно properties.duration. Старые записи без lifetime читаются как OwnerTurns с текущим duration. Бессрочные записи мигрируются явно, не правилом «999 означает бесконечно»; существующее отрицательное значение бессрочности адаптер переводит в Permanent после проверки соответствующих фабрик. Старые фабрики получают int только через адаптер своего вида времени.

Для роллов предмета добавить типизированный override Duration в запрос создания, вне properties. Он меняет только положительное число, не Kind/Scope/interval. Канон и ролл проходят одну проверку. Повторное применение и загрузка не обращаются к RNG.

Валидация: возможности фабрики; единицы и диапазоны; отсутствие periodic у непериодического; interval > 0 и interval <= duration; целый положительный maxStacks; поддержка сериализации; явное правило силы для композита; Player-only область новых минутных действий. Один id не может иметь разные единицы в разных источниках. Числа состояния из сейва не подменяются новым балансом каталога: проверяется совместимость схемы и kind, а активный экземпляр сохраняет зафиксированные значения.

DataEditor показывает Kind, подписанные единицы Duration/Interval, условную видимость и ограничения фабрики. Предлагаемые общие метаданные возможностей фабрик размещаются в Core для runtime и инструмента; Battle-сцены не подключаются к редактору. Preview, индекс ссылок EffectId, валидация и сохранение понимают новую форму. Неизвестный enum/поле не должен исчезать при пересохранении.

## 13. Уведомления и UI

EffectsComponent публикует структурные изменения после фиксации: добавление/замена/refresh/снятие с актуальными снимками. Предлагаемые новые сообщения: EffectTimingChangedEvent при изменении срока и PlayerEffectsSnapshotMessage для мировой панели. Боевой EffectsChangedEvent расширяется EffectTimeSnapshot.

В бою остаётся маршрут CombatEvents → BattleTimeline → BattleDirector → BattleEventBus → UI. В мире адаптер компонента передаёт снимок через GameMessageBus независимо от BattleEventBus. Начальный снимок запрашивается при создании HUD, не ждёт тика. Смерть, фактическое лечение/урон и изменения параметров используют существующие доменные события; не дублировать их через обе презентационные дороги.

Для отсчёта панель получает снимки часов презентации, Kind и остаток. Можно визуально уменьшать число между уведомлениями, но нельзя самостоятельно удалять иконку при нуле или считать декоратор снятым. Во время replay снятие может ждать границы пакета: показывать ноль до подтверждённого события, не отрицательное число. UI не читает живой EffectsComponent.

Единицы: «3 хода», «12 игр. мин.», «1:30 (при ×1)» для масштабируемых секунд с пояснением в тултипе. При ускорении отсчёт ускоряется. Округление только в UI, дробь в сейве сохраняется. Несколько стаков показывают количество и максимальный остаток, как сейчас.

Минутные описания не используют `{Duration|turn|turns}`. Добавить форматтер времени и ключи локализации единиц; Godot UI остаётся сценами, общие компоненты — в SharedUi по правилам проекта.

## 14. Порядок реализации и зависимости

1. **Типизированное время без новых данных:** контракты, адаптер Duration, классификация урона, перенос общих потребителей на Timing; регрессия turn-эффектов.
2. **Часы и gate:** один тик, pause/ускорение/reset/load; самостоятельная обработка при ожидании боевого ввода.
3. **Три новых поведения:** параметры, восстановление, урон; общие формулы и awaitable-действия, точное расписание.
4. **Жизненный цикл:** выборочная очистка боя, смерть в мире, сохранение после смерти, reconcile перед воскрешением/переходом.
5. **Сейв:** clock, activeEffects, restore до Vitals, чтение старого файла без секции.
6. **Предметы:** Prepare/Commit для ApplyEffectItemAction и результат применения; связь с будущей транзакцией предмета. Флаконы и баланс не нужны для тестирования ядра.
7. **UI и инструменты:** снимки/единицы/форматирование, редактор, валидаторы; авторинг конкретных эффектов после утверждения баланса.
8. **Интеграция:** Main и Battle-песочница, прежние гранты, turn-эффекты и копии Player. Обновление документации реализации и зеркала по результатам работ.

Первый этап завершается до минутных записей в реальных данных: нельзя выпускать частичный переход, где UI или stacking ещё читает Duration:int. Перед изменением кода проверить актуальное состояние ветки: предметы и другие связанные системы могут быть реализованы после подготовки этого проекта.

## 15. Решения для проверки при реализации

Блокирующих вопросов по ядру не осталось. Следующее — технические предложения документа, а не дополнительные утверждённые игровые требования:

- Первый тик через interval; на точном сроке тик перед снятием.
- Refresh сохраняет фазу, сильная замена начинает новую.
- Во время уже разрешаемого/показываемого действия изменения ждут ближайшей границы; часы и накопление долга не останавливаются.
- Увеличение максимума не заполняет ресурс; уменьшение ограничивает текущий остаток.
- Сохраняется существующая семантика самоурона. Иное действие защитных модификаторов на вредные флаконы потребует отдельного балансного решения.

Открыты конкретные определения/баланс: список эффектов флаконов, числа/роллы, Power, maxStacks, сравнение силы многопараметрических бафов. Их можно заполнить позднее; примеры не переносить в рабочий каталог автоматически.

## 16. Критерии готовности реализации

### Чистые тесты без Godot

- OwnerTurns сохраняет прежние число действий, свежесть, продление и cap. Минутные эффекты не получают turn callbacks или бонусы длительности.
- Скорость ×1/×2 даёт правильный срок обеих шкал; pause/меню/offline ничего не расходуют; cooldown предмета не ускоряется вместе с эффектом.
- Разный размер шага при одинаковом горизонте даёт одинаковое число и порядок действий, включая две шкалы и равные границы.
- Первый/последний тик, дробный остаток, сохранение фазы при refresh и новая фаза при замене.
- Cap обновляет ближайший срок; разные роллы не получают силу последнего стека; снятие одного декоратора не удаляет другие.
- Смерть на догоняемом тике запрещает следующие действия по трупу, но не останавливает срок. Воскрешение не исполняет пропущенные тики.
- Dispel учитывает категорию и Power, сохраняет Absolute; удаление отменяет будущие действия без двойного снятия модулей.
- Snapshot/restore сохраняет числа/фазу без RNG и Apply. Максимумы восстанавливаются до виталов.
- Старый сейв, неизвестный id, версия, дубли, NaN, истёкшая запись, новая игра имеют определённый результат и диагностику.
- Отказ последнего действия предмета возвращает эффекты/сроки/модули/виталы/заряды; observer не видит частичного commit. Повтор CommandId не удваивает применение.
- Сейв на смертельной временной границе отклоняется после урона.

### Интеграционные сцены Godot

- MoveSpeed меняет перемещение; истечение, рассеивание и загрузка снимают/восстанавливают его ровно один раз.
- Вход/выход из боя, переход локации не сбрасывают срок; гранты экипировки не дублируются.
- DoT убивает в мире и запускает посмертное ожидание; ускорение сокращает срок; лечение не оживляет тело.
- Смерть при ожидании цели в бою отменяет ввод. После смертельного тика нельзя исполнить уже недопустимую команду.
- Истечение при replay не меняет вычисленный удар; UI отражает тот же порядок. Частые тики не создают бесконечную очередь анимаций.
- Загрузка не производит факты использования/повторные реакции; HUD сразу показывает правильные единицы/остатки.
- DataEditor открывает, валидирует, сохраняет и повторно читает формат без потери полей; preview использует нужные единицы.

Эти проверки относятся к будущей реализации. Подготовка документа проверяет покрытие решений, единицы, жизненный цикл, потоки, JSON-пример и соответствие существующим API; она не является выполнением игровых тестов.
