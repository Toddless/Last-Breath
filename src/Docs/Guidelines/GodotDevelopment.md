# Разработка Godot/C#: игровые границы и жизненный цикл

Обязательные правила — в [CLAUDE.md](../CLAUDE.md). Здесь приведены проверки для затрагиваемых областей; неприменимые разделы не создают дополнительную работу. Текущее устройство конкретной системы ищется по [карте документации](../README.md), а не выводится из этого руководства.

## Владение и жизненный цикл

- Назвать владельца изменяемого состояния и его срок жизни. Не создавать вторую независимую копию состояния в UI или адаптере.
- Для подписки или регистрации определить момент создания и снятия. Повторный Setup, вход в дерево, открытие окна и смена игрока не должны дублировать обработчики.
- Удаление из дерева, освобождение узла и завершение игровой сессии — разные события. Выбирать очистку по фактическому сроку жизни; не освобождать чужой общий ресурс.
- `_Ready` обычно вызывается один раз. Если регистрация снята в `_ExitTree`, повторное добавление того же узла должно её восстановить; не рассчитывать на повторный `_Ready` без явного механизма.
- Для подписок на долгоживущие C#-сервисы хранить обработчик и снимать подписку. У C#-сигналов Godot есть исключения из автоматической отписки, в частности захватывающие лямбды и пользовательские сигналы.
- Сессионные кэши, статические ссылки и реестры должны корректно переживать «меню → новая игра» в одном процессе.

Основание: [жизненный цикл Node](https://docs.godotengine.org/en/stable/classes/class_node.html), [C# signals](https://docs.godotengine.org/en/stable/tutorials/scripting/c_sharp/c_sharp_signals.html).

## Асинхронность и отложенные действия

- Определить владельца операции, условие отмены, результат повторного запуска и адресата ошибки. Не оставлять Task без наблюдения.
- После await проверять не только наличие объекта, но и актуальность операции: та же сессия, бой, локация, цель или поколение привязки. Если устарел контекст, не применять результат к новому владельцу.
- Отмена не равна ошибке конфигурации и не должна оставлять занятый флаг, блокировку ввода или частично списанный ресурс. Освобождение выполняется на всех путях выхода.
- Не удерживать синхронный lock через асинхронное ожидание. Если нужна очередь или SemaphoreSlim, определить правила отмены ожидающего и уже выполняющегося действия.
- Task.Run не разрешает работу с активным деревом сцены. Передача результата в движок выполняется через допустимый механизм основного потока; безопасность иных API проверяется по документации.

Основание: [C# lock](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/statements/lock), [Godot thread-safe APIs](https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html).

## Состояние, команды и ошибки

1. Отделить чистую проверку/предпросмотр от выполнения. Предпросмотр не меняет факты, инвентарь и игровой поток случайности.
2. Проверить вход, актуальность цели и доступность непосредственно перед изменением состояния.
3. Для составного действия определить подготовку, списание, фиксацию и восстановление при отказе. Не обещать «всё или ничего», если наблюдатель может увидеть частичный результат.
4. Публиковать уведомления результата после согласованной фиксации. Учесть повторный вход из обработчика события и повторную команду.
5. Вернуть различимый результат ожидаемого отказа. Ошибка данных или обязательной зависимости диагностируется с ID/путём и причиной; не подменяется молчаливым успехом или случайным значением по умолчанию.

## Сцены, ресурсы и файлы

- Определение из каталога или общий Resource рассматривается как шаблон. Индивидуальные роллы, здоровье, заряды и остатки принадлежат экземпляру; перед изменением ресурса определить, действительно ли он индивидуальный.
- Проверить обязательные Export-ссылки и настройки сцены при инициализации. Не использовать null propagation для сокрытия нарушенного контракта сцены.
- Различать ID определения, устойчивый ID экземпляра и временную ссылку/привязку к живому объекту. NodePath не становится игровым ID без соответствующего контракта.
- При переименовании/перемещении сохранять UID, связанные .uid и обновлять .tscn/.tres, JSON, локализацию и экспортные ссылки. Не пересоздавать идентичность существующего ассета ради устранения ошибки загрузки.
- Перед правкой пути через симлинк определить физический файл и проекты-потребители. Не копировать общий код в песочницу как исправление отсутствующей ссылки.
- Изменения Tool-скриптов проверять также в редакторском контексте: редакторская инициализация не должна запускать игровую сессию, менять сохранения или авторские данные без команды автора.

Godot повторно использует загруженные ресурсы: [Resources](https://docs.godotengine.org/en/stable/tutorials/scripting/resources.html).

## Анимации и иконки

### Библиотеки анимаций

- Авторские клипы, кадры и настройки визуала хранить в библиотеке ресурсов соответствующей системы, по образцу `AbilityVisualLibrary` и `NpcVisualLibrary`. Здесь library означает каталог визуальных ресурсов проекта; это не требование переводить всё на встроенный тип Godot AnimationLibrary.
- Запись связывается с ID сущности и содержит ссылки на кадры/клипы и параметры представления. Не разносить таблицу «ID → анимация» по switch в игровых сущностях и отдельных окнах.
- Существующий способ воспроизведения расширять новой записью/ресурсом. Код меняется при новом поведении представления, а не для подключения очередного арта.
- Общую библиотеку хранить в одном физическом экземпляре и подключать к проектам существующим способом. Не менять общие кадры и конфигурацию ради состояния одного проигрывателя.
- Процедурные твины и механизмы проигрывания остаются в компонентах представления. Библиотека описывает визуал; расчёт попадания, урона и эффектов принадлежит игровой логике.

Проверенные образцы, пути относительно `src`: `Battle/Source/Presentation/AbilityVisualLibrary.cs` содержит общие `SpriteFrames` и массив `AbilityVisualConfig`; `NpcVisualLibrary.cs` в той же папке — массив `NpcVisualConfig`, где каждой записи NPC назначаются свои `SpriteFrames` и масштаб. Подробности проигрывания — в [описании представления боя](../Combat/Presentation.md).

### Иконки по пути и ленивая загрузка

- Путь к иконке определяется по принятой конвенции категории и ID. Использовать существующий построитель пути, если он есть; не искать файл обходом каталогов при каждом отображении и не дублировать разрешение пути в разных UI.
- Загружать текстуру при первом запросе иконки для представления, сохранять успешно полученную ссылку и повторно использовать её. Ленивая загрузка описывает момент обращения, а не обязательно асинхронный способ загрузки.
- Конструктор, Copy, генерация лута, расчёт характеристик и сохранение не читают Icon. Копирование сущности переносит её данные, не вызывает загрузку текстуры у исходного экземпляра.
- Обращение, вызывающее ResourceLoader, выполняется внутри Godot. Управляемые тесты и симуляции могут создавать и копировать сущности без чтения визуальных свойств; фактическую загрузку проверять внутри движка.

Проверенные образцы: `Core/Items/EquipItem.cs` — `Icon` через `AssetPaths.ItemIcon(Id)` и копирование без чтения `source.Icon`; `Battle/Source/Effects/Effect.cs` — `Icon` по пути `res://Data/Shared/Assets/Effects/{Id}.png`. `Core/Constants/AssetPaths.cs` задаёт пути по категориям; предметы используют `res://Data/Shared/Assets/Items/{Id}.png`. При переносе подхода учитывать корень ресурсов конкретного проекта, не копировать путь вслепую.

Эти примеры подтверждают ленивую загрузку и сохранение успешного результата. Они не задают готовую общую политику отсутствующего ассета, повторной попытки или диагностических сообщений.

## Пространство, время и случайность

- У координат известна система отсчёта: локальная, мировая, экранная. Переходы между ними выполняются явно. Близость координат не означает принадлежность одному World2D или локации.
- Различать положение физического тела, визуального спрайта, точки взаимодействия и источника VFX. Визуальная анимация не перемещает игровое тело без явного контракта.
- Длительность и отметка времени имеют единицу и источник: ходы, игровые минуты, масштабируемые или реальные секунды. Не смешивать абсолютный срок и оставшуюся длительность.
- Для часов определить поведение при паузе, ускорении, бое, выгрузке локации, сохранении и загрузке. Не восстанавливать ход симуляции из длительности визуальной анимации.
- RNG поступает через существующий контракт. Предпросмотр, тултипы и VFX не потребляют игровые броски. Проверки случайного поведения используют воспроизводимый источник; смена порядка бросков считается изменением поведения.
- Боевой визуал воспроизводит результат логики. Пока логика опережает показ, интерфейс читает снимки показываемого события, а не более позднее живое состояние.

## Сохранение и новая игра

- Для добавленного состояния указать способ восстановления: сохранённое значение, вычисление или сброс. Определить порядок зависимых участников.
- Восстановление не повторяет награды, плату, опыт и факты первоначального действия. Подписчики не должны принимать восстановление за новое игровое событие.
- При изменении формата назвать версию, политику отсутствующих/неизвестных данных и миграцию либо согласованный разрыв совместимости.
- Проверить сохранение после изменения и загрузку после пересоздания объектов, а не только восстановление поверх того же экземпляра.
- Проверить новую игру после сыгранной сессии; старые реестры, цели, кошелёк и накопленные события не переносятся случайно.

## Ввод, UI и 2D-представление

- Использовать InputMap и существующего владельца контекста. Проверить фокус текстового поля, модальное окно, Esc и переход в бой/другую локацию. Одно нажатие не выполняет одновременно действие окна и мира.
- Подсказка соответствует привязке действия. UI показывает результат общей проверки доступности, а не реализует вторую версию игрового правила.
- Пользовательские строки и форматирование чисел идут через локализацию. Для изменённого UI проверить длинные строки, другое разрешение/масштаб и доступность элементов управления.
- Для спрайтов и VFX проверить точку опоры, порядок отрисовки, масштаб, кадры и ссылки ресурсов по правилам [стиля ассетов](AssetStyleGuide.md). Представление не владеет результатом операции.
- Профилировать затронутый горячий участок на представительном количестве NPC/объектов. Измерять аллокации, частоту пересчёта и время кадра; не вводить пул, кэш или сложную оптимизацию без конкретной причины. У кэша определить инвалидирование.
