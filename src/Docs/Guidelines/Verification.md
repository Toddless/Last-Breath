# Проверка изменений

Единая политика для лида, исполнителя и ревьюера. Общие правила — в [CLAUDE.md](../CLAUDE.md), игровые границы — в [руководстве Godot/C#](GodotDevelopment.md). Проверки выбираются по риску и типу изменения; неприменимость объясняется кратко, отсутствие проверки не выдаётся за успех.

## Выбор проверок

| Изменение | Проверка |
| --- | --- |
| Чистая логика C# | Тест правила, существенных границ и отказов; сборка затронутых потребителей. |
| Баг | Регрессионный тест или воспроизводимый интеграционный сценарий, показывающий сбой до исправления и успех после. |
| Сцена, сигнал, физика, движковый ресурс | Проверка внутри Godot, в том числе headless; сборка C# одна не подтверждает проводку сцены. |
| JSON/каталог | Разбор, схема, ID, ссылки, диапазоны, локализация и применимые аудиты данных. |
| Сохранение | Изменение → сохранение → пересоздание состояния → загрузка; новая игра после старой сессии; совместимость по принятой политике. |
| UI/VFX | Применимые интеграционные проверки и отдельная визуальная проверка: сцена, действия, ожидаемый результат, разрешение/локаль. |
| Библиотека анимаций или иконки | Привязка ID к записи и клипам, правильность пути; фактическая загрузка в Godot. Для изменения логики загрузки — создание/копирование сущности без чтения Icon и переиспользование успешно загруженной текстуры. |
| Горячий участок | Измерение на представительном сценарии с условиями и результатом. |
| Документация/промпт без кода и данных | Ссылки, полнота, согласованность правил и diff; игровые сборки и тесты не требуются. |

Headless-проверки доступны исполнителю. Нативные объекты и API Godot не создаются вне движка: access violation не перехватывается обычным try/catch. Визуальное качество в редакторе проверяет владелец; headless не заменяет этот этап. Если движок или нужный ресурс недоступен, передать точный незавершённый сценарий и его влияние на приёмку.

## Качество тестов

- Проверять наблюдаемое правило, а не повторять реализацию. Перед новым тестом/фейком/хелпером искать существующий, расширять подходящий параметризованный набор.
- Тест логики не должен зависеть от числа записей контента, конкретного балансного числа, английской формулировки или хэша файла. Аудит реального контента может проверять авторские ID и значения, если это прямо его назначение; не смешивать эти два вида проверки.
- Не читать исходники как текст и не обращаться к private через рефлексию ради проверки поведения; использовать публичный контракт или подходящий интеграционный сценарий.
- Не ослаблять, не игнорировать и не удалять падающий тест ради зелёного. Изменённое ожидание или удаление связывается с конкретным изменением требований. Тест, написанный при рефакторинге, остаётся, пока защищает актуальное правило.
- Устаревшую проверку заменить или удалить вместе с намеренно изменённым поведением, перечислив причину в сдаче. Регрессионные тесты входят в задачу реализации; отдельная задача допустима для независимой инфраструктуры тестирования.
- Для исправления бага подтвердить исходное падение на соответствующей версии/сценарии без отката чужих правок. Если воспроизвести исходную ошибку не удалось, назвать ограничение; не заявлять доказанную регрессию.
- Случайность и время в тесте контролируются. Проверять отказ, повторный вызов, отмену и завершение владельца там, где они затронуты.
- Документация теста описывает защищаемое правило, обычно в 1–2 строках, без истории обсуждений.

## База и прогон

1. Лид фиксирует исходное состояние проверок перед работой над кодом/данными. Исполнитель может использовать переданный свежий результат для той же версии и состава дерева; при изменении базы или отсутствии результата проверяет её сам. Не повторять одинаковый полный прогон перед каждой мелкой задачей без изменения базы.
2. При неизвестном исходном падении передать тест, фактический вывод и установленную причину либо отметить, что причина пока неизвестна. Лид определяет блокирующее влияние и согласует известные падения; они явно входят в постановку.
3. После изменения исполнитель собирает затронутые проекты и выполняет применимые проверки. Для изменений игрового кода/данных — оба управляемых набора ниже, плюс нужные Godot-сценарии. Для правок только документации достаточно документных проверок.
4. Проверки с общими выходными каталогами выполняются последовательно. Во время итогового прогона проверяемый состав файлов фиксирован; параллельные правки делают результат устаревшим.
5. Лид проверяет интегрированное состояние перед коммитом: для кода/данных повторяет обязательные управляемые наборы и применимые сборки; нативные результаты повторяет, если интеграция затронула проверенный сценарий. Для документов повторяет документные проверки.
6. Новое падение не списывается на «не связано». Его расследуют; исправление вне согласованного скоупа оформляют отдельной задачей либо согласуют расширение. Аудит авторских данных не исправляют подгонкой данных или ожиданий без решения владельца контента.

## Команды и проекты

Команды выполняются из корня LastBreath. Состав зависимостей проверяется по актуальным csproj; список ниже служит отправной точкой.

| Проверка | Команда |
| --- | --- |
| Сборка игрового тестового проекта и его зависимостей, включая Battle, Core, Crafting и LootGeneration | `dotnet build src/Testing/LastBreathTest.csproj` |
| Main, на который игровой тестовый проект не ссылается | `dotnet build src/Main/LastBreath.csproj` |
| Отдельная сборка Battle при необходимости | `dotnet build src/Battle/Battle.csproj` |
| Игровые управляемые тесты | `dotnet test src/Testing/LastBreathTest.csproj` |
| Тесты инструментов | `dotnet test src/Tooling/Tooling.Tests/Tooling.Tests.csproj` |

При правках инструментов также собрать затронутый проект инструмента: его тесты не доказывают сборку каждого приложения. Версии SDK/языка брать из csproj, global.json и фактически используемого инструментария.

В проекте используется MSTest.Sdk. Не полагаться на привычный `--filter` без проверки поддержки и фактического числа выполненных тестов. Для обычной приёмки запускать полные наборы выше.

Полный Monte-Carlo отчёт лута генерируется при изменении баланса лута с явным `LOOT_SIMULATION_REPORT=1`; обычный прогон не должен переписывать отчёт. В PowerShell временно установить переменную окружения, выполнить тесты и восстановить её прежнее значение в finally. Не смешивать синтаксис присваивания окружения разных оболочек.

Godot запускать исполняемым файлом версии проекта, после сборки нужного приложения, с явными проектом и тестовой сценой. Проверять вывод и итог сценария; код выхода по таймауту сам по себе не означает успех. Подходящие существующие сцены находятся в `src/Main/Tests`; сценарий выбирается по изменению.

## Доказательства и приёмка

Для каждой выполненной проверки: команда/сценарий, версия или состав проверенного дерева, код выхода и итог. Для тестовых наборов — total/failed/skipped из фактического вывода; для Godot — итоговые проверки/ошибки сценария. Для измерений — условия и сравнение. Приложить существенный вывод или путь к логу.

Раздельно фиксировать:

- **Код принят** — ревью требований, реализации и применимых соглашений завершено.
- **Автоматические проверки пройдены** — обязательные проверки выполнены на сдаваемом состоянии; согласованные исходные падения названы отдельно и не считаются зелёным прогоном.
- **Игровой сценарий проверен** — нужный сценарий выполнен; визуальная часть, требующая владельца, подтверждена им либо явно ожидается.

Отсутствие обязательного доказательства блокирует соответствующий этап приёмки. Неприменимая проверка не является дефектом. Известные падения допускаются только в согласованном составе, без новых. Нельзя закрывать фичу как полностью проверенную, если необходимый этап ещё ожидается.
